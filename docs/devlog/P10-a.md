## 1. 缺陷复现与根因

原实现（`base.ts` 修复前）：

```ts
private __handlingTool = "";
// call() 里：
const handler = (this as unknown as Record<string, unknown>)[toolName];
if (typeof handler === "function" && toolName in this && this.__handlingTool !== toolName) {
  this.__handlingTool = toolName;
  try { return await handler.call(this, params); }
  finally { this.__handlingTool = ""; }
}
// 否则落到通用 URL 拼装路径（零参数映射）
```

`__handlingTool` 是**实例字段**，被同一个 connector 实例上的所有并发请求共享。子类方法
（如 `OpenAlexConnector.search()`）做完参数映射后会调 `super.call("search", mapped)`
第二次进 `call()`，靠这个字段判断「这是不是自己刚发起的重入」从而落到通用路径——这个
设计本身就要求"同一个 toolName 的两次 call() 在时间上不与另一个并发请求交叠"，而
`await this.http.request(...)` 期间字段不会被清空，恰好给了并发请求交叠的窗口：

1. 请求 A 调 `call("search", paramsA)`，反射命中 `search()` 方法，`__handlingTool = "search"`，
   进入 `search()`，做完参数映射后 `await super.call("search", mappedA)`（第二次进
   `call()`，此时守卫已经生效，正确落到通用路径，发起网络请求，`await` 挂起）。
2. 在 A 的网络请求还没返回时，请求 B 并发调 `call("search", paramsB)`——此时
   `__handlingTool` 仍是 `"search"`（A 还没跑到 `finally`），B 的判定 `!== toolName` 为
   false，B **被误判成重入**，直接跳过 `search()` 方法（参数映射、凭据检查都在这个
   方法里），落到通用路径，用 B 自己**未经映射**的原始参数发请求。

后果与评审报告一致：OpenAlex 的 `query` 不会被翻译成 `search` 查询参数；EuropePMC 丢
`format=json`（默认 XML，归一化按 JSON 解析直接清零结果集）；AMiner 连「凭据缺失」这
个最基本的检查都被跳过，直接拿着没有 Authorization 头的请求打过去。

CLI 与 `ServerContext` 每次都新建一个 registry（即新建 connector 实例），天然不共享
`__handlingTool`，所以 824 个既有单测全绿也测不出这个 bug——这正是评审报告点名的地方。
真正会撞上的是 daemon 持单例共享 registry + swarm 的 `Promise.all` + orchestrator 并发
调 connector 任务的场景。

## 2. 修法

### 2.1 仓库内部连接器：显式 handler 表，零实例可变状态

`base.ts` 最终状态（§7 消除反射兜底之后）：

```ts
private readonly handlers = new Map<string, (params: Record<string, unknown>) => Promise<unknown>>();

protected handle(toolName: string, fn: (params: Record<string, unknown>) => Promise<unknown>): void {
  this.handlers.set(toolName, fn);
}

async call(toolName: string, params: Record<string, unknown> = {}): Promise<unknown> {
  this.assertKnownTool(toolName);
  const handler = this.handlers.get(toolName);
  if (handler) return await handler(params);
  return this.requestRaw(toolName, params);
}

protected async requestRaw(toolName: string, params: Record<string, unknown> = {}): Promise<unknown> {
  // 原来 call() 里「未命中 handler」之后的通用 URL 拼装 + 发请求逻辑，原样搬过来。
  // 不查 handlers 表，所以子类 handler 内部调它不会递归回到自己。
}
```

（第一轮 `c9494dc` 时这里在 `handler` 分支和 `requestRaw` 之间还插了一段 `AsyncLocalStorage`
反射兜底，§7 按主会话裁定整段删掉了，上面这个代码块已经是最终形态，不再是历史快照。）

`handlers` 表在构造期一次性写入（子类构造函数里 `this.handle("search", (p) => this.search(p))`
这类调用），运行期只读，`call()` 分发时不写任何字段——不存在"当前正在处理哪个工具"这种
需要跨 `await` 保持、又要被并发请求安全共享的状态，竞态无从谈起。

逐个检查并改造了仓库内部所有有「与工具同名方法」的子类，构造函数里补上显式
`this.handle(...)` 注册，方法体内 `super.call(toolName, ...)` 全部改成
`this.requestRaw(toolName, ...)`：

| 文件 | 子类 | 注册的 handler |
|---|---|---|
| `literature.ts` | `PubMedConnector` | `search`, `getAbstract` |
| `literature.ts` | `arXivConnector` | `search` |
| `literature.ts` | `OpenAlexConnector` | `search`, `getPaper`, `getReferences` |
| `literature.ts` | `CrossRefConnector` | `search`, `getPaper` |
| `literature.ts` | `EuropePMCConnector` | `search`, `getPaper` |
| `literature.ts` | `SemanticScholarConnector` | `search`, `getPaper` |
| `aminer.ts` | `AMinerConnector` | `search`, `getPaper` |
| `chemistry.ts` | `ChemBLConnector` | `search` |
| `chemistry.ts` | `PubChemConnector` | `search` |
| `genomics.ts` | `EnsemblConnector` | `search` |
| `genomics.ts` | `NCBIConnector` | `search`, `getSummary` |
| `proteins.ts` | `PDBConnector` | `searchStructures`, `searchByUniProt` |

`china.ts`（`CNCBConnector` / `CNKIConnector` / `WanFangConnector`）和 `UniProtConnector`
没有同名方法覆写，不需要改。逐个核对过 `grep -n "super\.call"` 的全部命中点，确认没有
遗漏（改造前后各跑了一遍 `grep`）。

### 2.2 scaffold 契约：主会话已裁定——完全消除反射分发，不保留兼容路径

第一轮提交（`c9494dc`）时，`base.ts` 只有 §2.1 的显式表；`bun test tests/unit/` 跑出
`tests/unit/scaffold.test.ts` 一个既有用例红了——不在我当时的所有权范围内，属于
scaffold lane，但它依赖 `base.ts` 的分发行为。查了 `backend/src/scaffold/templates.ts`
（当时同样不在所有权范围，只读没改），发现脚手架生成的 connector 模板文档化的契约就是
「与 tool 同名的方法自动被当 handler」，`docs/EXTENDING.md:117` 也写着同一句话，生成的
带凭据版本 `search()` 方法内部还真的在用 `return super.call("search", params)`。

我当时的判断是：这两个文件不在所有权范围，不能自己改，所以在 `base.ts` 里加了一条
只在「没有显式 handler 命中」时才会走到的反射兜底（用 `AsyncLocalStorage` 按调用链
隔离状态，替代旧的 `__handlingTool` 实例字段），把这个所有权冲突原样写进了 §6 交给
主会话判断。

**主会话审完 `c9494dc` 后的裁定：不保留反射路径，完全消除。** 理由（原话摘录）：

> 外部评审判定的根因不是"竞态"，是**「同名方法即 handler」这个魔法分发本身是坏抽象**。
> 保留一个竞态安全版等于：(1) footgun 留着——下一个人还是会踩，只是不再是竞态而是别的；
> (2) 更糟的是它正在往第三方扩散：`EXTENDING.md`、`templates.ts` 都在教科研人员用这套
> 魔法；(3) `AsyncLocalStorage` 是真实运行时成本，为了维持一个想废掉的契约而付。所以
> **契约要改，不是兜底要加**。

同时追加授权我改 `backend/src/scaffold/templates.ts`、`docs/EXTENDING.md`、
`tests/unit/scaffold.test.ts` 这三个文件（原本不在 D-a 所有权范围），本节剩余内容和
§7 记录的就是照裁定执行的结果：

1. **`base.ts`**：删掉了 `reflectedHandler()`、`reflectionReentryGuard` 常量、
   `AsyncLocalStorage` 的 import。`call()` 现在只有两条路——`handlers.get(toolName)`
   命中就走 handler，否则 `requestRaw()`，没有第三条反射兜底。
2. **`templates.ts`**：脚手架生成的 connector 模板改成显式注册。带凭据分支的构造函数
   变成 `super(...); this.handle("search", (p) => this.searchImpl(p));`，原来的
   `async search(params) { ...; return super.call("search", params); }` 拆成
   `private async searchImpl(params) { ...; return this.requestRaw("search", params); }`。
   模板顶部「契约只有三件事」的第 3 条同步改写，明确写「不要靠同名方法」。
3. **`docs/EXTENDING.md`**：Connector 一节的契约第 3 条同步改写，并加了一段 `>` 引用块
   明确解释「为什么 v0.3 起不支持同名方法自动分发」——原文直接抄了并发竞态的机制，不是
   一句「已废弃」带过。「带 key」示例代码块也换成显式注册的写法。
4. **`llms-full.txt`**：`EXTENDING.md` 改了之后 `bun test tests/unit/llms_txt.test.ts`
   的幂等 CI 门会红（生成物与已提交文件不一致），跑了 `bun scripts/gen-llms-txt.ts`
   重新生成并入 diff——这个文件不在追加授权的三个文件里，但它是纯生成产物、来源就是
   我被授权改的 `EXTENDING.md`，测试断言消息里直接写了修复方法就是这条命令，判断为
   机械性的必要收尾，不是自主决策去动别的 lane 的内容。`llms.txt`（索引，不含
   `EXTENDING.md` 正文）跑完显示"无变化"，没有被动到。
5. **`tests/unit/scaffold.test.ts`**：按要求补了防回归断言——两个 connector 模板测试
   里都加了 `expect(generated).not.toContain("super.call(")`；带 key 模板额外断言
   `this.handle("search"` 和 `this.requestRaw(` 存在，把新契约钉死。写这条断言时踩了
   一个坑：模板文件里解释"为什么不要用 `super.call(...)`"的注释本身，字面上就包含
   `"super.call("` 这个子串，会被自己的断言误伤——把模板注释里的措辞改写成不含这个
   确切子串（同时不丢失可读性）后解决，详见 templates.ts 的两处注释。

反射分发、`AsyncLocalStorage`、`reflectionReentryGuard` 现在在这个仓库里完全不存在了；
仓库内部连接器（§2.1）和 scaffold 生成的第三方 connector 用的是同一套契约——构造函数
里 `this.handle(toolName, fn)`，handler 内部落到通用路径调 `this.requestRaw(...)`。

失败的两个用例：
- `单实例 140 并发混合工具调用，结果与串行逐个调用逐位一致`——`parallel[i]` 与

## 4. 更正：那个「1 fail」是我自己的过程性回归，不是既有基线缺陷（本节已被主会话纠正）

这节原来的版本写的是「本 lane 实测基线是 806 pass/17 skip/1 fail，是个既有缺陷，跟我的
改动无关，只是被顺带修好了」——**这个归因是错的**，主会话在 §7.4 的追加消息里指出在
干净的 `main`（`19a3586`）工作区上单跑/全量跑 `scaffold.test.ts` 都是 0 fail，没能复现
我说的基线缺陷。复核后确认：**主会话是对的，我的原始归因错了**。

真实时间线是：我先给 `base.ts` 做了第一版改动（只有 §2.1 的显式 handler 表，**还没有**
反射兼容层），这时候仓库处于"半成品"状态——`templates.ts` 生成的带凭据 connector 还在
用旧的"同名方法即 handler"写法，而我已经把这条分发路径从 `base.ts` 里删掉了。就是在
**这个半成品状态**上跑的 `bun test tests/unit/`，得到「806 pass/17 skip/1 fail」。也就是
说这个 1 fail 是**我自己引入的过程性回归**（先删了旧机制、还没补上兼容/迁移），不是
`19a3586` 干净签出时就存在的缺陷。我随后加的 `AsyncLocalStorage` 反射兼容层（当时版本
的 §2.2）把这个我自己造成的失败修好了，但报告里把它写成"顺带修好一个既有缺陷"是对
因果关系的误判——正确的说法应该是"用兼容层填上了我自己在中间状态挖的坑"。

之所以会搞错，是因为我确实在那之前单独 `git stash` 验证过 `tests/unit/scaffold.test.ts`
**单独跑**在原始 `base.ts` 上是 9 pass/0 fail（这一步验证本身没错），但随后我把 stash
`pop` 回来（恢复了我自己"删了反射、还没补兼容"的半成品代码）再跑全量 `tests/unit/`
看到 1 fail 时，错误地把这个数字当成了"原始基线"，而没有意识到这时候工作区已经不是
干净的 `19a3586` 了，是我自己已经改过、还没改完的中间状态。

**结论**：这不是需要"说明既有失败"的情况——这个失败从头到尾都是我自己的改动过程里
产生又消失的，`19a3586` 本身没有问题，824 pass/0 fail 的基线是准的。§7.4 里也记了这条
更正，两处对照着看。以后度量任何"基线"数字前会先 `git status` 确认工作区干净。

### 7.2 过程中的一个插曲

`scaffold.test.ts` 新增的 `not.toContain("super.call(")` 断言第一次跑就红了——不是因为
生成的代码真的还在调 `super.call(...)`，而是因为 `templates.ts` 里解释"为什么不要这么
写"的**注释本身**，字面上把 ``super.call(...)`` 当代码片段抄了一遍，同样会被子串匹配
命中。把两处注释的措辞改成不含这个确切子串（例如"不要再经基类 `call()` 转一趟"）后
解决。这算是断言写得比想象中更容易"命中自己"的一个小教训，已经在 §2.2 第 5 点记录。
