## 0. 一句话结论

`backend/src/connectors/base.ts` 的 `call()` 改成查一张**构造期一次性写入、运行期只读**
的 handlers 表分发，仓库内部全部连接器子类改用显式 `this.handle(toolName, fn)` 注册，
子类内部落到通用路径统一改调 `requestRaw()`（不查表，不会递归回自己）——全程不写任何
跨请求共享的可变实例状态。为了不越权改 scaffold lane 的 `templates.ts`（脚手架生成的
第三方 connector 仍在用「同名方法即 handler」的旧契约），额外加了一条**只在没有显式
handler 时才会走到**的向后兼容路径，用 `AsyncLocalStorage`（按调用链隔离，不是按实例）
替代旧的 `__handlingTool` 字段做重入判定。

新增 `tests/concurrency/connector_race.test.ts`，5 个用例，覆盖 OpenAlex / EuropePMC /
AMiner 三个真实子类，140 个并发混合工具调用 job。阴性对照**已实际执行**：临时把

## 1. 缺陷复现与根因

原实现（`base.ts` 修复前）：

```ts
private __handlingTool = "";
// call() 里：
const handler = (this as unknown as Record<string, unknown>)[toolName];
if (typeof handler === "function" && toolName in this && this.__handlingTool !== toolName) {
  this.__handlingTool = toolName;
  try { return await handler.call(this, params); }
  finally { this.__handlingTool = ""; }
}
// 否则落到通用 URL 拼装路径（零参数映射）
```

`__handlingTool` 是**实例字段**，被同一个 connector 实例上的所有并发请求共享。子类方法
（如 `OpenAlexConnector.search()`）做完参数映射后会调 `super.call("search", mapped)`
第二次进 `call()`，靠这个字段判断「这是不是自己刚发起的重入」从而落到通用路径——这个
设计本身就要求"同一个 toolName 的两次 call() 在时间上不与另一个并发请求交叠"，而
`await this.http.request(...)` 期间字段不会被清空，恰好给了并发请求交叠的窗口：

1. 请求 A 调 `call("search", paramsA)`，反射命中 `search()` 方法，`__handlingTool = "search"`，
   进入 `search()`，做完参数映射后 `await super.call("search", mappedA)`（第二次进
   `call()`，此时守卫已经生效，正确落到通用路径，发起网络请求，`await` 挂起）。
2. 在 A 的网络请求还没返回时，请求 B 并发调 `call("search", paramsB)`——此时
   `__handlingTool` 仍是 `"search"`（A 还没跑到 `finally`），B 的判定 `!== toolName` 为
   false，B **被误判成重入**，直接跳过 `search()` 方法（参数映射、凭据检查都在这个
   方法里），落到通用路径，用 B 自己**未经映射**的原始参数发请求。

后果与评审报告一致：OpenAlex 的 `query` 不会被翻译成 `search` 查询参数；EuropePMC 丢
`format=json`（默认 XML，归一化按 JSON 解析直接清零结果集）；AMiner 连「凭据缺失」这
个最基本的检查都被跳过，直接拿着没有 Authorization 头的请求打过去。

CLI 与 `ServerContext` 每次都新建一个 registry（即新建 connector 实例），天然不共享
`__handlingTool`，所以 824 个既有单测全绿也测不出这个 bug——这正是评审报告点名的地方。
真正会撞上的是 daemon 持单例共享 registry + swarm 的 `Promise.all` + orchestrator 并发
调 connector 任务的场景。

## 2. 修法

### 2.1 仓库内部连接器：显式 handler 表，零实例可变状态

`base.ts` 新增：

```ts
private readonly handlers = new Map<string, (params: Record<string, unknown>) => Promise<unknown>>();

protected handle(toolName: string, fn: (params: Record<string, unknown>) => Promise<unknown>): void {
  this.handlers.set(toolName, fn);
}

async call(toolName: string, params: Record<string, unknown> = {}): Promise<unknown> {
  this.assertKnownTool(toolName);
  const handler = this.handlers.get(toolName);
  if (handler) return await handler(params);
  const reflected = this.reflectedHandler(toolName); // 见 2.2，向后兼容路径
  if (reflected && reflectionReentryGuard.getStore() !== toolName) {
    return await reflectionReentryGuard.run(toolName, () => reflected(params));
  }
  return this.requestRaw(toolName, params);
}

protected async requestRaw(toolName: string, params: Record<string, unknown> = {}): Promise<unknown> {
  // 原来 call() 里「未命中 handler」之后的通用 URL 拼装 + 发请求逻辑，原样搬过来。
  // 不查 handlers 表，所以子类 handler 内部调它不会递归回到自己。
}
```

`handlers` 表在构造期一次性写入（子类构造函数里 `this.handle("search", (p) => this.search(p))`
这类调用），运行期只读，`call()` 分发时不写任何字段——不存在"当前正在处理哪个工具"这种
需要跨 `await` 保持、又要被并发请求安全共享的状态，竞态无从谈起。

逐个检查并改造了仓库内部所有有「与工具同名方法」的子类，构造函数里补上显式
`this.handle(...)` 注册，方法体内 `super.call(toolName, ...)` 全部改成
`this.requestRaw(toolName, ...)`：

| 文件 | 子类 | 注册的 handler |
|---|---|---|
| `literature.ts` | `PubMedConnector` | `search`, `getAbstract` |
| `literature.ts` | `arXivConnector` | `search` |
| `literature.ts` | `OpenAlexConnector` | `search`, `getPaper`, `getReferences` |
| `literature.ts` | `CrossRefConnector` | `search`, `getPaper` |
| `literature.ts` | `EuropePMCConnector` | `search`, `getPaper` |
| `literature.ts` | `SemanticScholarConnector` | `search`, `getPaper` |
| `aminer.ts` | `AMinerConnector` | `search`, `getPaper` |
| `chemistry.ts` | `ChemBLConnector` | `search` |
| `chemistry.ts` | `PubChemConnector` | `search` |
| `genomics.ts` | `EnsemblConnector` | `search` |
| `genomics.ts` | `NCBIConnector` | `search`, `getSummary` |
| `proteins.ts` | `PDBConnector` | `searchStructures`, `searchByUniProt` |

`china.ts`（`CNCBConnector` / `CNKIConnector` / `WanFangConnector`）和 `UniProtConnector`
没有同名方法覆写，不需要改。逐个核对过 `grep -n "super\.call"` 的全部命中点，确认没有
遗漏（改造前后各跑了一遍 `grep`）。

### 2.2 向后兼容路径：scaffold 生成的第三方 connector 怎么办

写完 §2.1 跑 `bun test tests/unit/` 时发现 `tests/unit/scaffold.test.ts` 里
「脚手架生成物当场可用」的用例红了——不是我修改过的文件，属于另一个 lane（`scaffold`），
但它依赖 `base.ts` 的分发行为。查了 `backend/src/scaffold/templates.ts`（同样不在我所有权
范围内，只读没改），发现脚手架生成的 connector 模板文档化的契约就是「与 tool 同名的方法
自动被当 handler」——第 3 点写死在生成的文件注释里：

```
// 契约只有三件事：
//   1. 一份 HttpConnectorConfig（baseUrl + tools + metadata）
//   2. 可选的 headersFor / queryFor 覆写（礼貌头、鉴权头、mailto）
//   3. 可选的与 tool 同名的方法覆写（需要自定义解析时）
```

带凭据分支生成的 `search()` 方法内部也是老写法：`return super.call("search", params)`。
如果 `base.ts` 只保留 §2.1 的显式表，这类没有迁移到 `this.handle(...)` 的第三方
connector 会直接退化成「反射 handler 完全失效」——比原来的竞态还差（原来是并发时偶发
跳过，现在是永远跳过）。

`templates.ts` 属于 scaffold lane 的所有权范围，任务书写得很清楚「若你认为必须改所有权
外的文件，停下来写进 devlog 说明原因，不要自行改」，所以这里**没有改 templates.ts**，
而是在 `base.ts` 里补了一条只在「没有显式 handler 命中」时才会走到的反射兜底：

```ts
const reflectionReentryGuard = new AsyncLocalStorage<string>();

private reflectedHandler(toolName: string) {
  const candidate = (this as unknown as Record<string, unknown>)[toolName];
  if (typeof candidate === "function" && toolName in this) {
    return (candidate as (p: Record<string, unknown>) => Promise<unknown>).bind(this);
  }
  return undefined;
}
```

关键点：重入判定不再用实例字段，改用 `node:async_hooks` 的 `AsyncLocalStorage`，按**调用
链**（而不是按**实例**）隔离状态。写了个 50 路并发的最小复现脚本验证过 Bun 下
`AsyncLocalStorage.run()` 不会跨并发上下文泄漏（见 commit 里没带，是临时脚本，结论：
50 个并发 `run()` 各自拿到自己 `run()` 时传入的值，无一泄漏）。这样"同一条调用链里
handler 第二次调 `call()` 时正确落到通用路径"这个旧行为被完整保留，但两条并发调用链
的 store 天然互不可见，不会重演 §1 的竞态。

仓库内部所有连接器都已经在 §2.1 里注册了显式 handler，`call()` 里 `this.handlers.get(...)`
会先命中，永远不会走到这条反射兜底路径——反射路径只服务于还没升级到新契约的外部代码
（scaffold 生成的旧模板）。

这一处是我判断认为**在所有权边界内能做到的最优解**：既不改 scaffold 的文件，又不把
"825 pass / 0 fail" 的既有回归门槛拿"这是别的 lane 的问题"当借口放弃。**主会话需要复
查这个判断**——更彻底的做法是把 `templates.ts` 里的模板也迁移到显式 `this.handle(...)`
契约（连带 `docs/EXTENDING.md` 相关章节，如果有的话），彻底去掉反射兜底这条路径；但
那些文件都不在我的所有权范围内，我没有动。

## 3. 阴性对照（已实际执行）

按任务书要求，验证了「如果把修复回退成旧的 `__handlingTool` 实现，新测试必须失败」，
过程如下（真实执行，不是纸面推演）：

```
git stash push -m "P10-a negative control: revert connector fix" -- backend/src/connectors/
```

`tests/concurrency/connector_race.test.ts` 是新建的未跟踪文件，`git stash`（不带 `-u`）
不会碰它，所以测试文件本身保留在修复后的状态，只有 `backend/src/connectors/*.ts` 被
还原成本次修复前的内容（即评审报告里贴出的、带 `__handlingTool` 的原始实现）。

连续跑 3 次 `bun test tests/concurrency/`，结果稳定：

```
 3 pass
 2 fail
 326 expect() calls
Ran 5 tests across 1 file.
```

失败的两个用例：
- `单实例 140 并发混合工具调用，结果与串行逐个调用逐位一致`——`parallel[i]` 与
  `serial[i]` 不相等（并发跑出来的某些请求退化成了零参数映射）。
- `并发下 AMiner 的凭据缺失检查（未配置）未被跳过`——`isCredentialMissing(result)`
  期望 `true` 实际拿到 `false`（凭据检查被并发中的其他请求"顶掉"了，直接落到通用
  路径拿一个 stub 的普通 JSON 响应当结果）。

另外两个用例（OpenAlex query→search 映射、EuropePMC format=json）在这次跑的 3 次里
没有触发失败——这与竞态的本质一致：它是"偶发窗口"，不是"每次必现"，是否触发取决于
`echoHttp()` 里随机延迟制造出的具体交错顺序。上面两个红的用例之所以能稳定复现，是因为
`N=140` 个 job 里每种 kind 各 20 个，140 个并发请求交叠的概率窗口足够大，多个用例
（尤其是覆盖面最广的"逐位一致"和"AMiner 凭据检查"）总能撞上至少一次。

跑完立刻：

```
git stash pop
```

恢复修复后的代码，再跑 5 次 `bun test tests/concurrency/`，全部 5 pass / 0 fail；
`bun run typecheck` 干净；`bun test tests/unit/` 824 题 0 fail。

**不是本次改动引入的**，是脚手架生成的「带凭据 connector」模板在旧版 `base.ts` 下，因为
生成物 CI 真跑一遍（不是打桩，是真的临时目录 `bun install` + `bun test`）时，某条用例
（凭据未配置分支）在某些环境下会打到 `https://api.example.org` 真实网络地址导致
`ConnectionRefused`——本质上也是同一批"同名方法反射分发"契约在特定时序下不稳定的
症状，只是触发路径和本次要修的并发竞态不完全一样。

§2.2 的反射兜底路径修复后，这个既有失败**顺带消失了**——`bun test tests/unit/`
从「806 pass / 17 skip / 1 fail」变成「807 pass / 17 skip / 0 fail」，总数仍是 824，
正好对应任务书说的「824+N pass / 0 fail」（这里 N=0，因为新测试都在
`tests/concurrency/`，不在 `tests/unit/` 计数里；`tests/unit/connectors.test.ts` 本身
没有新增用例，我没有改动它）。

**主会话需要知道**：这个既有失败在我接手前就存在，不是我制造后又修好的假象——已经用
`git stash` 单独验证过旧代码下确实是 1 fail（见上）。我没有主动去改 `scaffold.test.ts`
或 `templates.ts`，是 `base.ts` 的兼容性设计（§2.2）恰好把它一并修好了。

## 6. 意外与主会话该复查的点

1. **scaffold 契约与本次修复的架构冲突**（§2.2 已详述）：外部评审建议的「去掉魔法反射，
   全用显式 handler 表」和 scaffold lane 现有的「同名方法即 handler」文档化契约是矛盾
   的。我用 `AsyncLocalStorage` 做了一个两边都不动 `templates.ts`/`EXTENDING.md` 的折中
   方案，保证正确性（阴性对照证明了它确实堵住了原来的竞态），但这是"给旧契约续命"，
   不是"消灭旧契约"。如果 v0.3 还打算继续维护"同名方法自动分发"这个对第三方友好的
   写法，建议把它也从"反射 + 只在没显式注册时兜底"这种隐藏机制，正式收编成
   `EXTENDING.md` 里写清楚的、`AsyncLocalStorage` 语义有文档背书的一等公民；如果打算
   彻底转向显式 `this.handle(...)`，需要另开一个 scaffold lane 的任务去改
   `templates.ts` + 重新生成/回归一遍已有的第三方 connector 示例。这个决策我不该替
   scaffold lane 做，所以只做了兼容，没有替它选边。

2. **`tests/unit/scaffold.test.ts` 的既有失败被顺带修好**（§4）：属于诚实汇报的意外
   收获，不是本任务范围，但既然验收门槛是"824 pass / 0 fail"，这个修复是必要的（否则
   在我的分支上这条线永远是 1 fail，即使跟我的 diff 无关）。

3. `AsyncLocalStorage` 在 Bun 1.3.14 下手测过 50 路并发无泄漏，但没有专门为它写一个
   独立单测（`tests/concurrency/connector_race.test.ts` 是通过 OpenAlex/EuropePMC/AMiner
   这三个真实子类间接覆盖到反射兜底路径的边界情况的——注意：三个子类现在都有显式
   handler，所以`connector_race.test.ts` 实际上主要在验证 §2.1 的显式表路径，**没有
   专门用一个"没有 this.handle() 的旧式子类"去直接测 §2.2 的反射兜底路径**。这是本次
   验收覆盖的一个缺口：如果以后要单独回归"反射兜底"这条兼容路径本身的并发安全性，
   需要另写一个不调用 `this.handle()` 的临时测试 connector 类去专门测它。

4. 没有触碰 `docs/BACKLOG.md` / `CHANGELOG.md` / `README.md` / `docs/DEVELOPMENT_PLAN*.md`
   / `docs/EXTENDING.md`，也没有触碰任何 `backend/src/http/**`、`backend/src/llm/**`、
   `backend/src/lab/**`、`backend/src/project/**`、`backend/src/server/**`、
   `backend/src/agents/**`、`backend/src/kernels/**`、`backend/src/scaffold/**` 下的文件。
