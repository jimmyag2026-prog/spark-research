分支 `feat/P11-d`（基于 `feat/P11-integration` = main `e65cacf`）。基线：`bun test tests/unit/` =
905 pass / 0 fail / 0 skip；`bun run test:e2e` = 12/12。四项任务全部完成，六个套件全绿，
本 lane 越过了文件所有权表一处，下面第一节先说这个。

## 文件边界：唯一一处越界（`backend/src/server/app.ts`）

R-d-2 要求「加一个 MCP 工具」。`backend/src/mcp/server.ts`（不属于本 lane）把 MCP 工具的调用
方式硬编码成「对同一个 Hono app 的一次 `app.fetch()`」——工具的 `request()` 必须解析到一条
**真实注册在 app 上**的路由，否则它就是一个挂了名字却打不通的假入口，等于重犯 AD-12。

本 lane 拥有的路由文件只有 `server/routes/lab.ts`，把蛋白分析塞进 `/api/lab/*` 前缀会是
另一种「自描述撒谎」（URL 路径暗示这是湿实验功能）。经过权衡，我新建了
`backend/src/server/routes/proteins.ts`（干净的新文件，无所有权冲突），并在
`backend/src/server/app.ts` 里加了两行：

```ts
import { proteinRoutes } from "./routes/proteins";
...
app.route("/api/proteins", proteinRoutes(ctx));
```

这是本 lane **唯一**越过持有清单的改动。理由：
1. `app.ts` 不在任何并行 P11 lane 的持有清单里（接口先行 / R-a / R-b / R-c 只碰 `llm/**`
   与 `capabilities/` 的 provider 段），不存在合并冲突风险。
2. 不改动是不可能交付一个真正能打通的 MCP 工具的——那样就是明知故犯地留下一个新的
   AD-12 缺口，而这正是本 lane 存在的理由。
3. 改动本身是纯新增两行、零改动既有路由行为。

如果主会话认为这个判断不对，回退方式是：删掉这两行 + `server/routes/proteins.ts`，
`protein_analyze` 会变成一个打不通的工具——但那时 R-d-1 的门禁会立刻发现（见下面
「阴性对照」一节），不会悄悄溜过去。

## R-d-1：技能可达性断言（AD-5 收紧版）

新增 `tests/unit/narrative_parity.test.ts` 的第 7 条断言：「每个 SKILL.md 对应的能力必须
有可核实的生产入口（CLI/HTTP/MCP 三选一），且该能力出现在 `capabilities --json` 里」。

### 判据设计：怎么避免靠正则猜

**不对 SKILL.md 的自然语言（description / triggers）做正则匹配**——那正是「叙事」本身，
用叙事验证叙事是循环论证：写得像模像样的 triggers 不会因为正则匹配成功就变得真的可达
（这正是 protein-analysis 当初蒙混过关的方式，没人拿它的 triggers 去核对是否真能打到代码）。

改用两段式判据：

1. **`SKILL_ENTRYPOINTS`**：一张显式维护的「技能 → 声称的入口名」登记表，写法与文件里已有
   的 `ALLOWED_ORPHANS` 同一套纪律——人工登记、必须写清楚是哪个入口，且有「多余登记必须
   删除」的对称检查（技能目录被删但登记还在 → 红），防止它变成只增不减的死表。
2. **每一条登记不是自己说了算，要去真实注册表核实存在**：
   - **CLI**：从 `backend/src/index.ts` 的 `main()` 顶层 `switch(cmd)` 里用
     `/case\s+"([a-z][a-z0-9_-]*)"\s*:/g` 抽取全部 `case` 字面量。这确实是正则，但抽取的对象
     是**语法结构**（switch 的 case 标签是有限、精确的字符串字面量，运行时用 `===` 严格
     匹配），不是对文档/描述这类自然语言做模糊匹配——效果等价于「读一遍真实的 dispatch
     表」。与「正则猜 capability」的本质区别：这里的正则**提取的是事实**（真实存在的 case
     标签），不是**推测意图**（这句话像不像在描述某个功能）。
   - **MCP**：`MCP_TOOLS.map(t => t.name)` 直接查名字是否存在，结构化数据，零猜测。
   - HTTP 路由没有单独做（详见下一段）。
3. 额外核实该技能出现在 `buildCapabilities()` 的 `skills` 列表里——这是「自描述面没有漏报」
   的对称检查。

**为什么没做 HTTP 路由核实**：本仓库目前每个技能都至少有 CLI 或 MCP 入口能覆盖判据要求的
「至少一条」，protein-analysis 补完之后也是如此（CLI `protein` + MCP `protein_analyze`）。
硬要加一层对 Hono `app` 路由表的结构化核实（`createApp({}).routes`）技术上可行，但当前
没有任何技能*只*靠 HTTP 路由撑住这条判据，加了也测不出额外的东西，所以没做——如果未来
出现「只有 HTTP、没有 CLI/MCP」的技能，这层需要补上，判据本身预留了扩展空间（
`SkillEntrypoints` 接口现在只有 `cli?`/`mcp?` 两个可选字段，加 `http?` 是纯新增）。

### 为什么不加 SKILL.md 的 `entrypoints:` frontmatter 字段（任务书建议的方案）

任务书建议「考虑在 frontmatter 加一个 `entrypoints:` 字段」，让判据有真源可依。这是更好的
长期方案，但没有采用，原因是它牵扯两个不在本 lane 持有清单内的文件：

- `backend/src/skills/frontmatter.ts`：`parseSkillFrontmatter` 有一张 `KNOWN_KEYS` 白名单，
  加字段必须扩它 + `SkillFrontmatter` 接口 + `ParseOptions`。这个文件被 `capabilities/
  index.ts`、`scaffold/templates.ts`、`tests/unit/skill_frontmatter.test.ts`、
  `tests/unit/scaffold.test.ts`、`tests/unit/llms_txt.test.ts` 共用——是全系统的 schema 真源。
- `backend/src/capabilities/index.ts`：`SkillCapability` 类型要加 `entrypoints` 字段，
  `capabilities --json` 才能把它广播出去（否则加了字段也是「文档有、广播没有」的新缺口）。

这两个文件都不在 R-d 的持有清单，且被多处消费方共用，改 schema 的风险面超出本 lane 的职责
边界（任务书的纪律原文：「必须越界时停下写进 devlog，不要自行改」）。所以我在测试文件内部
自建了 `SKILL_ENTRYPOINTS` 登记表作为替代真源，效果上等价（同样是显式、可核实、有对称
删除检查），只是物理位置在测试文件而不是 SKILL.md 本身。**这是留给后续 lane 的建议**：
把这张表从 `narrative_parity.test.ts` 搬进 frontmatter 的 `entrypoints:` 字段，需要同时touch
`skills/frontmatter.ts` + `capabilities/index.ts` + 现有 10 个 SKILL.md，工作量不小，值得单独
起一条任务而不是顺手夹带在 R-d 里。

## R-d-3（V23）：unconsumedWarnings 接进 HTTP / Web 审批面

**先纠正一个前提**：调查发现 HTTP 层其实已经"结构上"带着这个字段——`server/routes/lab.ts`
的 `viewJson()` 把整个 `WetExperimentView`（除 `record`）原样转发，而 `unconsumedWarnings`
本就是 `WetExperimentView` 的字段（P10-d D-8 的产物）。所以严格说，HTTP 响应体里从来没有
"丢"这个字段——真正的缺口在**两处**：

1. HTTP 层没有测试钉住这件事（字段存在是"意外没丢"，不是"有断言保证"，下一次重构极易
   在不知情的情况下把它漏掉）——补了 `tests/unit/server_lab.test.ts` 的两条断言（浓度协议
   非空 / 干净协议为空）。
2. **真正的缺口**：前端 `WetExperiment` 类型（`frontend/workspace/src/lib/types.ts`）根本
   没有声明 `unconsumedWarnings` 字段，approve/reject 弹窗（`bottom.tsx` 的
   `ApprovalDialog`）也完全没有渲染它——即使 HTTP 响应体里有这个字段，TypeScript 都不允许
   你在前端代码里读它（没声明的字段）。这才是 BACKLOG V23 描述的真实问题：「经 Web 批准
   的人看不到它」。

修复：
- `frontend/workspace/src/lib/types.ts`：`WetExperiment` 加 `unconsumedWarnings: string[]`。
- `frontend/workspace/src/components/bottom.tsx`：`ApprovalDialog`（批准/拒绝共用的弹窗）
  在「安全门结论」之后、署名输入之前，新增一个 `unconsumedWarnings.length > 0` 才渲染的
  告警块，复用已有的 `.error-box`（红底红字，与 `error-box` 在别处表达"错误/危险"的语义
  一致），标题带 🚨，正文明说"安全门结论的通过不覆盖这些内容"。`data-testid="unconsumed-
  warnings"` 供 e2e 定位。
- `tests/e2e/workbench.spec.ts` 新增「⑨b 未消费告警在批准弹窗里必须可见（V23）」：新建一条
  独立湿实验（协议文本复用 `tests/unit/wet_loop.test.ts` D-8 用例的"配制10%次氯酸钠溶液
  200uL"），打开批准弹窗，断言告警块可见且包含"浓度"。用 `.filter({hasText})` 定位实验，
  不依赖 `.exp-list` 的排列顺序，不影响 ⑦/⑧/⑨ 已经在用的"OD 测定"实验。
