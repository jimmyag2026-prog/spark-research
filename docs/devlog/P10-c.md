## 1. D-6 · config.json 权限收紧到 0600

### 问题

`backend/src/index.ts`（`auth` 命令）和 `backend/src/config/index.ts`（`spark-research config set`，两者其实写的是同一个文件 `~/.spark-research/config.json`）的 `writeFileSync` 都没指定 `mode`，落盘按 umask 默认是 0644。而这个文件里装着 `KIMI_API_KEY` / `OPENROUTER_API_KEY`——项目里最值钱的密钥，保护却比 connector 凭据（`daemon/credentials.ts`，0600，AD-2）弱。

### 做法

照抄 `daemon/credentials.ts` 第 141-144 行附近的写法（只读，没改它）：目录 `mkdirSync(dir, { mode: 0o700 })`、文件 `writeFileSync(path, ..., { mode: 0o600 })`、**显式 `chmodSync(path, 0o600)`**——因为 `writeFileSync` 的 `mode` 只在**创建**文件时生效，一个已经以 0644 存在的文件（老版本留下的、或被别的工具重建过）不会因为这次 `writeFileSync` 自动收紧，必须显式 chmod。两个写入点（`index.ts` 的本地 `saveConfig()`、`config/index.ts` 的导出 `saveConfig()`）都改了。

新增两个函数（`backend/src/config/index.ts`）：

- `checkConfigPermissions(options)`：只读体检，判定逻辑与 `credentials.ts` 的 `checkPermissions()` 同口径（`(mode & 0o077) === 0` 才算 ok），不存在的文件视为 ok（不阻断首次运行）。
- `enforceConfigPermissions(options)`：体检 + 发现过宽立即 `chmodSync` 收紧，返回「发现时」的状态供调用方告警。

**启动时权限自检**接在两处：
1. `config/index.ts` 的 `loadConfig()` 里——每次读配置都会先跑 `enforceConfigPermissions`，过宽就收紧并通过 `options.warn`（默认 `console.warn`，与 `CredentialStore` 同一套注入口径）告警。`applyConfigEnvDefaults()` 内部调用 `loadConfig()`，而 `index.ts` 的 `main()` 一开始就调 `applyConfigEnvDefaults()`——所以 CLI 每次启动都会自检。
2. `index.ts` 的 `main()` 里额外显式调了一次 `enforceConfigPermissions()` 并打印告警，保证即便 `applyConfigEnvDefaults()` 未来被改掉，启动自检这条路径依然独立成立。

### 验收

`tests/unit/config.test.ts` 新增一个 describe 块（7 条）：
- `saveConfig` 写入后 `statSync` 的 mode 是 0600；
- **「文件已存在且是 0644 → 写入后被收紧到 0600」**这条最容易漏的路径：先 `saveConfig` 建文件，`chmodSync` 到 0644，再 `saveConfig` 一次，断言权限变回 0600 且内容确实是新写的（不是权限修了但数据没变）；
- `checkConfigPermissions`：不存在的文件 ok；0600 ok；0644 不 ok 且带 "644" 字样的告警文案，且**只读不改**（不该顺手把文件 chmod 了，那是 `enforceConfigPermissions` 的职责）；
- `enforceConfigPermissions`：发现 0644 立即收紧到 0600 并报告发现时状态；
- `loadConfig` 在读到 0644 时把告警交给注入的 `warn`，权限已经是 0600 时不告警。

### 已知的不完美（留给主会话判断要不要修）

`backend/src/index.ts` 顶部的 `CONFIG_DIR = join(homedir(), ".spark-research")` 是硬编码路径，**不读 `SPARK_RESEARCH_DATA_DIR`**，而 `config/index.ts` 的 `dataDir()` 会读这个 env。两处默认情况下（没设 `SPARK_RESEARCH_DATA_DIR`）指向同一个文件，所以本轮修复覆盖到了；但如果用户设了 `SPARK_RESEARCH_DATA_DIR`，`spark-research auth` 会写到旧路径而 `spark-research config` 系列会读写新路径——这是**预先存在**的不一致，不属于 D-6/D-7 范围，我没有动它（改 `index.ts` 的路径解析逻辑超出「只改 auth/config 写入相关段落」这条边界的谨慎解释），但建议登记进 BACKLOG。

## 2. D-7 · Origin/Host 校验 + Content-Type 强制

### 攻击链

用户浏览器开一个恶意网页 → 该网页发一个 `Content-Type: text/plain` 的跨站 POST（"简单请求"，不触发 CORS 预检，浏览器照样发出去）→ 冒充用户调 `/api/lab/experiments/:id/approve`（`actor` 字段随便填）→ 再调 `/simulate`。当前是模拟器，接了真实 Opentrons 设备之后这条是 P0。

### 做法：两道闸，挂在 `createApp()` 里所有路由之前的 `app.use("*", ...)` 中间件

**闸 1：Content-Type 强制**。写方法（POST/PUT/PATCH/DELETE）必须显式 `Content-Type: application/json`（允许 `; charset=...` 之类的参数），否则 415。这堵住「用 text/plain 绕开预检」那条路——但攻击者当然可以伪造这个头，伪造了就正好落进闸 2。

**闸 2：Origin 白名单**。只在请求**带 Origin header 时**才校验；本地默认信任 `localhost` / `127.0.0.1` / `::1`（含任意端口），可通过新增的 config 项 `originAllowlist`（逗号分隔主机名，`SPARK_RESEARCH_ORIGIN_ALLOWLIST` env 同步）扩展。不在白名单 → 403。

### 判定逻辑（最关键的一条，任务书特别强调过）

**缺 Origin header 的写请求一律放行，不做任何拦截**。这不是漏洞，是刻意口径，理由：

- 现代浏览器对「非同源」的 fetch/XHR 写请求（含用 `text/plain` 绕开预检的那种）与跨站 `<form>` POST 导航，Origin header 都是浏览器强制加的、网页 JS 拿不掉也改不了。**真实的跨站攻击者发不出「没有 Origin」的浏览器请求**——所以「没有 Origin」这个信号本身对判断"是不是浏览器帮外部网站发起的跨站请求"是可靠的。
- 没有 Origin 的写请求只可能来自非浏览器调用方：本机 CLI、MCP server 的进程内 `app.fetch()`（`backend/src/mcp/server.ts` 用 `new Request(BASE_URL + path, init)` 直接喂给同一个 Hono app，从不带 Origin/Host——这不是网络请求，是同进程内的函数调用，只是套了 Fetch API 的壳）、curl、以及仓库里 `tests/helpers/server_scenario.ts` / `tests/helpers/mcp_scenario.ts` 之下几十个既有测试。这些等价于「本机 shell 里跑的东西」，挡住它们不会挡住任何真实攻击，只会把没坏的路径打红。
- 换句话说：Origin 校验防的是「浏览器代替用户身份打本机 API」，对没有浏览器参与的调用方无意义。

判定实现（`backend/src/server/app.ts`）：
```
if (origin !== undefined && !isAllowedOrigin(origin, originAllowlist)) → 403
// origin === undefined → 直接放行，不进入白名单判断
```
`isAllowedOrigin` 对畸形/解析不了的 Origin 一律当不可信（不会因为 `new URL()` 抛错就退化成"当作没有 Origin"放行）。

### 对既有测试的影响排查（改之前先查清楚，而不是改完再救火）

改之前逐一确认了所有会打进 Hono app 的调用路径：
- `tests/helpers/server_scenario.ts` 的 `request()`：POST/PATCH 一律 `body = body ?? {}` 再 `JSON.stringify`，`Content-Type` 恒设——所有 `server_*.test.ts`（experiments/ideation/lab/literature/projects/records/report/session）都走这条路径，天然安全。
- `backend/src/mcp/server.ts` 的 `fetchJson()`：只在 `body !== undefined` 时设 Content-Type；但 `McpToolRunner.call()` 的入口 `args: Record<string, unknown> = {}` 恒有默认值，且 `mcp/tools.ts` 里所有写工具的 `request()` 都是 `body: args`（从不是 `body: undefined`），所以 MCP 路径上 Content-Type 也恒被设，不受影响。
- `tests/unit/server.test.ts` / `server_session.test.ts` 里手写的 `fetch()` 调用逐条查过，POST/PATCH 全部显式带 `Content-Type: application/json`。
- 前端 `frontend/workspace/src/lib/api.ts` 的 `post()` 助手 `body: unknown = {}` 默认值加 `JSON.stringify`，恒产出非空 body，恒设 Content-Type；`tests/e2e/workbench.spec.ts` 里唯二的 `fetch()` 调用是 GET，不受影响。

结论：**改动前排查到的既有测试路径没有一条会被误伤**，事后 `bun test tests/unit/` 验证也确实是 824 pass → 841 pass、0 fail，没有红的。

唯一的副作用：`tests/unit/llms_txt.test.ts` 的幂等性测试一度红了——因为 `CONFIG_SETTINGS`（D-7 新增 `originAllowlist` 项）是 `scripts/gen-llms-txt.ts` 的输入源，改了源没重新生成就会导致 `llms.txt`/`llms-full.txt` 与仓库里已提交的文件不一致。按测试自己给的提示跑了 `bun scripts/gen-llms-txt.ts` 重新生成（这两个文件不在 lane D-c 的禁碰名单里，且是这条测试明确要求的补救动作），diff 干净（只多了 `originAllowlist` 那一行配置说明），重跑后恢复 0 fail。

### 验收：对抗测试（新文件 `tests/unit/server_security.test.ts`，10 条）

以 `POST /api/projects` 为靶子（最简单的真实写端点，201/403/415 语义干净）：

**跨站写请求三种形态全部被拒：**
1. 完全缺 Content-Type（用 `TextEncoder` 编码的字节体而不是 string body，因为 fetch 对 string body 会自动补 `text/plain`，测不出"真的没有"这种情况）→ 415。
2. `Content-Type: text/plain`（就是攻击链里绕预检那个头）→ 415。
3. 伪造外站 Origin `https://evil.example`（Content-Type 正确）→ 403，并额外断言项目**真的没被创建**（不是只报错但底下还是执行了）。

**正常路径不受影响：**
4. `application/json; charset=utf-8` 放行（201）。
5. GET 请求完全不过这道闸。
6. `Origin: http://localhost:9999`（端口与服务器不同）放行。
7. `Origin: http://127.0.0.1:<server 实际端口>` 放行。
8. `config` 的 `originAllowlist` 能扩展白名单（在名单里的放行，不在的仍 403）。
9. 缺 Origin 的写请求（`server_scenario` 的调用形态）放行——这是几十个既有测试隐含依赖的行为，这里显式断言一次。
10. **MCP `McpToolRunner` 的进程内 `app.fetch()`**（用真实的 `makeMcp()` fixture 跑 `project_create` 工具）不带 Origin，写工具照常成功——直接覆盖任务书点名的"极其重要"那条判定。

## 3. 建议主会话复查的点

1. **`index.ts` 的 `CONFIG_DIR` 硬编码路径与 `config/index.ts` 的 `dataDir()` 不一致**（见 §1 末尾）——预先存在的问题，D-6 顺带发现，没有修（超出本 lane 的文件所有权谨慎解释），建议登记 BACKLOG 或指派给拥有 `index.ts` 更大改动权限的 lane。
2. **`originAllowlist` 是新增的 config 项**，落在 `CONFIG_SETTINGS`，会出现在 `spark-research config list` 与 `llms.txt` 里；文案与语义按其它 config 项的口径写的（"改了影响什么"必须非空，见 `config/index.ts` 顶部注释的纪律），主会话可以顺手扫一眼措辞是否需要调整。
3. **`llms.txt` / `llms-full.txt` 被本 lane 重新生成**——不在 D-c 的文件所有权列表里（既不在允许改的清单，也不在禁碰清单），是 `tests/unit/llms_txt.test.ts` 幂等性测试的强制要求（不重新生成就 0 fail 达不到）。如果其他并行 lane（D-a/D-b/D-d）也改了会影响 `CONFIG_SETTINGS`/`MCP_TOOLS`/文档正文的东西，合并时这两个生成文件大概率需要在主会话收口时再跑一次 `bun scripts/gen-llms-txt.ts` 合并 diff。
4. **D-7 的白名单目前只挡「带 Origin 且不在名单」**，没有对 Host header 做独立校验（任务书写的是"Origin/Host 白名单"，但显式强调"缺 Origin 的同源请求必须照常放行"这条更高优先级）。权衡是：Host header 在这几十个既有调用路径里经常也是缺失或不可控的（比如 MCP 的 `new Request()` 不带真实 Host），额外校验 Host 收益有限还可能引入新的误伤面，所以只做了 Origin 这一层 + Content-Type。如果之后要接真实的、可能被 DNS-rebinding 之类手法利用的部署形态，值得再评估要不要加 Host 校验，但那需要先确认 Bun/Hono 在这台机器实际拿到的 Host header 语义。
5. 湿实验 approve/reject 端点（`backend/src/server/routes/lab.ts`）本身没改一行——D-7 的两道闸是全局中间件，天然覆盖它，不需要也没有单独碰这个文件。
