## 交付（四项，全部完成）

### R-a-1：tool calling

`backend/src/llm/providers/openai_compat.ts`：

- 删掉了接口先行阶段「`options.tools` 非空就显式返回 `unsupported`」的占位拒绝——
  现在真的把 `options.tools` 编码成 OpenAI 的 `tools: [{type:"function", function:{name,description,parameters}}]`，
  `options.toolChoice`（`"auto"` / `"none"` / `{name}`）编码成 `tool_choice`。
- 响应侧解析 `choices[0].message.tool_calls`，每个 `function.arguments`（JSON 字符串）
  `JSON.parse` 成 `ToolCall.args`；**解析失败返回 `kind:"parse"` 的显式失败**，不吞掉
  （见下面阴性对照①，实测证明这条纪律真的被测试钉住了）。
- `toWireMessages()`：assistant 带 `toolCalls` 时编码成 `{role:"assistant", content, tool_calls:[...]}`
  （`arguments` 用 `JSON.stringify(tc.args)`）；`tool` 角色消息编码成
  `{role:"tool", tool_call_id, name, content}`（`name` 字段是原有行为，非标准字段但对
  kimi/openrouter/deepseek/qwen 等宽松解析器无害，保留未改）。

### R-a-2：流式（`options.onDelta`）

新增 `OpenAiCompatAdapter.consumeStream()`：传了 `onDelta` 就在请求体里带
`stream:true` + `stream_options:{include_usage:true}`，手写一个最小 SSE 解析器
（按行切 `data: {...}`，`[DONE]` 与空行跳过，解析不了的行当 keep-alive 忽略而不是报错）：

- `choices[0].delta.content` 逐块回调给 `onDelta`，同时累积成最终 `content`。
- `choices[0].delta.tool_calls`（按 `index` 分片、`arguments` 跨块拼接）也累积，
  流结束后复用**同一个** `parseToolCalls()`——非流式与流式两条路径共用一份
  「解析失败必须显式失败」的纪律，没有第二份实现会漂移。
- usage：只有上游真的给了带 `usage` 字段的块（`stream_options.include_usage` 生效时
  最后一块没有 `choices` 只有 `usage`）才如实记录；拿不到就是
  `usageUnavailable:true` + `costUsd:null`，**没有任何路径会填 0**。

### R-a-3：`response_format`

`options.responseFormat === "json_object"` → 请求体带 `response_format:{type:"json_object"}`。
`"text"` 或未传时不带该字段（不是带一个 `{type:"text"}` 去踩上游可能没实现的分支）。

**这条根治 BACKLOG V12**：kimi-k2.6 每轮 2–6% 判定只吐思维链、`content` 里没 JSON 的问题，
根因是调用方从没告诉过上游「我要 JSON」——OpenAI 兼容协议本来就有 `response_format` 字段，
之前只是没接。已用 WebSearch 核实 kimi/deepseek/qwen 三家官方文档都支持
`response_format:{type:"json_object"}`（见下面「核实记录」）。

### R-a-4：ADAPTERS 填实 + 本地端点

`backend/src/llm/router.ts` 的 `ADAPTERS` 补上 `openai` / `deepseek` / `qwen`（都是
`OpenAiCompatAdapter`，只换 `baseUrl` 与 `envKey`）：

| provider | baseUrl | envKey |
|---|---|---|
| openai | `https://api.openai.com/v1` | `OPENAI_API_KEY` |
| deepseek | `https://api.deepseek.com` | `DEEPSEEK_API_KEY` |
| qwen | `https://dashscope.aliyuncs.com/compatible-mode/v1`（中国大陆网关） | `QWEN_API_KEY` |
| kimi（已有） | `https://api.moonshot.ai/v1` | `KIMI_API_KEY` |
| openrouter（已有） | `https://openrouter.ai/api/v1` | `OPENROUTER_API_KEY` |

`implementedProviders()` 现在是 5 个（比接口先行阶段的 2 个多了 openai/deepseek/qwen）；
`anthropic` 仍然缺——那是 R-b 的所有权，本 lane 不碰 `providers/anthropic.ts`。

**本地端点**（ollama / vLLM / 任意自建 OpenAI 兼容服务）：显式前缀路由，
模型名形如 `local/<真实模型名>` 或 `local:<真实模型名>`：

- baseUrl 从环境变量 `SPARK_LOCAL_LLM_BASE_URL` 读，key 从 `SPARK_LOCAL_LLM_API_KEY`
  读（允许为空——很多本地服务不校验；为空时不发 `Authorization` 头，不发一个空 Bearer）。
- `resolve()` 里剥掉前缀后才是发给本地服务器的 `model` 字段
  （`local/llama3.1` → 请求体 `model:"llama3.1"`）。
- 没配 `SPARK_LOCAL_LLM_BASE_URL` 时请求一个 `local/...` 模型会得到可见的
  `kind:"auth"` 失败（消息里点名缺的环境变量），**不会静默落到任何已配置的云端 provider**——
  本地端点是显式 opt-in，不参与「没配 key 就退到任一已配置 provider」的隐式回退，
  否则用户写 `local/foo` 时如果恰好配了 `OPENAI_API_KEY`，会莫名其妙打到 OpenAI 去（模型名对不上，
  大概率 400，但这是一种「意图被吞掉」的失败模式，宁可直接可见地报「本地端点没配」）。

**为什么没进 `SUPPORTED_PROVIDERS`/`Provider` 联合类型**：那张表是「模型名 → provider」的
静态字典，`PROVIDER_MODELS[p]` 对每个 provider 是一份固定模型名清单。本地服务器上的模型名
是用户自己起的，没有固定清单可填；而 `tests/unit/orchestrator.test.ts`（不属于本 lane 所有权）
里有一条既有断言「每个 provider 的模型列表非空」（`listModels()` 遍历 `SUPPORTED_PROVIDERS`）。
如果把 `local` 塞进 `SUPPORTED_PROVIDERS` 又给它一个空数组，会直接踩碎那条断言——为了本地端点
去改一个不属于本 lane 的测试文件的期望不合适，所以选了「前缀路由，完全绕开 Provider 类型系统」
这条侵入面更小的路径。**副作用**：`implementedProviders()` / `capabilities --json`（R-c 接的那条）
不会列出 `local` 这个 provider id——本地端点目前只能通过「知道要用 `local/` 前缀」这个约定发现，
不是自描述的。如果后续要让它在 `capabilities --json` 里可见，需要单独设计（可能是给
`ProviderCapabilities`/`capabilitiesFor` 加一个「本地端点是否已配置」的旁路查询，而不是硬塞进
`Provider` 联合），这里先如实记下这个缺口，不在本 lane 里动手（会牵到 R-c 的 `capabilities/index.ts`）。

**配置来源**：均用环境变量，没有碰 `backend/src/config/`（那是 R-c 的所有权）。
`OPENAI_API_KEY` / `DEEPSEEK_API_KEY` / `QWEN_API_KEY` / `SPARK_LOCAL_LLM_BASE_URL` /
`SPARK_LOCAL_LLM_API_KEY` 目前都不在 `CONFIG_SETTINGS` 里，`spark-research config list`
看不到它们、`config get/set` 用不了。**需要 R-c 或后续把它们收进 `CONFIG_SETTINGS`**
（尤其是 `SPARK_LOCAL_LLM_BASE_URL`——本地端点这条本该是「不用碰环境变量就能玩」的入口，
现在还是得手动 export，跟 P14「配不上云 key 也能玩」的目标有落差，如实记在这里）。

### 核实记录（WebSearch，因为要对外承诺 capabilities，AD-12 不许拍脑袋）

在把 kimi/deepseek/qwen 的 capabilities 默认成全 `true` 之前，用 WebSearch 核实了三家官方文档：

- **Kimi/Moonshot**：`https://api.moonshot.ai/v1` 是 OpenAI 兼容端点；tool calling 全模型支持
  （`tools`/`tool_choice`，最多 128 个工具）；`response_format` 支持 `text`/`json_object`/`json_schema`。
  （[Kimi API Platform 迁移指南](https://platform.kimi.ai/docs/guide/migrating-from-openai-to-kimi)）
- **DeepSeek**：官方文档 `https://api-docs.deepseek.com/guides/function_calling` 与
  `.../guides/json_mode/` 确认 `tools` 参数与 `response_format:{"type":"json_object"}` 均支持
  （json 模式要求 prompt 里出现「json」字样，属于上游约束，不是我们这层要处理的东西）。
- **Qwen/DashScope**：`https://dashscope.aliyuncs.com/compatible-mode/v1`
  （或国际网关 `dashscope-intl.aliyuncs.com`）支持标准 OpenAI SDK 调用方式，
  `response_format:{"type":"json_object"}` 与 function calling 均有官方文档
  （[Alibaba Cloud Model Studio 兼容性文档](https://www.alibabacloud.com/help/en/model-studio/compatibility-of-openai-with-dashscope)、
  [Function Calling - Qwen](https://qwen.readthedocs.io/en/latest/framework/function_call.html)）。
  **国际网关 baseUrl 没有真实账号可验证网络可达性**（测试纪律不许打真实网络），
  用的是中国大陆网关地址，如实记这是「读文档 + 未实测」的状态，不是「已验证可用」。
- **OpenAI**：官方 API，tools/response_format/streaming 三者都是原生能力，不需要核实。
- **OpenRouter**：本身是转发层，不同模型的真实能力不同——沿用接口先行阶段就有的处理方式
  （kimi/openrouter 共用一份 capabilities 默认值），继续按「多数被路由模型支持」处理，
  **这是本 lane 已知的简化**：`capabilitiesFor("moonshotai/kimi-k2.6")`（DEFAULT_MODEL）汇报全
  true 是准的（上面已核实 kimi-k2.6 本身支持），但如果用户通过 OpenRouter 请求一个不支持
  tool calling 的冷门模型，capabilities 仍然会汇报 true——**按 provider 而非按 OpenRouter
  背后的具体模型区分，需要查 OpenRouter 的实时模型目录才能做对，这个粒度本 lane 没做**，
  如实记为后续缺口。

## 贯穿要求：capabilities 与实现同步（AD-12）

移除了接口先行阶段「capabilities 恒报 false」的占位，改成 `OpenAiCompatAdapter` 构造时可传
`capabilities: (model) => ProviderCapabilities` 覆盖；不传时用云端默认值
（`{toolCalling:true, jsonMode:true, streaming:true, usageReported:true}`）。

**最终能力位矩阵**（`router.capabilitiesFor(model)` 的实际返回值）：

| provider/model | toolCalling | jsonMode | streaming | usageReported |
|---|---|---|---|---|
| openai（如 gpt-4o） | true | true | true | true |
| kimi（如 kimi-k2） | true | true | true | true |
| deepseek（如 deepseek-chat） | true | true | true | true |
| qwen（如 qwen-max） | true | true | true | true |
| openrouter（如 moonshotai/kimi-k2.6） | true | true | true | true |
| 本地端点（`local/<model>`） | **false** | **false** | true | **false** |
| anthropic | — 未实装，`capabilitiesFor` 返回 `null`（R-b 的工作） | | | |

本地端点保守上报的理由：本地模型是否支持 function calling / json 模式因模型而异
（llama.cpp/ollama 的旧版本、很多 7B 量化模型不支持 tool calling），我们没有能力在不打真实
网络的前提下逐一探测，AD-12 不允许一刀切报 true。`streaming` 报 true 是因为 SSE 是 OpenAI
兼容协议的通用能力，几乎所有本地服务器实现都支持；`usageReported` 报 false 是因为多数本地
服务器不在 `usage` 字段里给出真实 token 计数（很多直接不回这个字段，或者回 0）。

**代码层面的解耦**：`capabilities()` 现在纯粹是「对外承诺」，不是执行门禁——同一份
`call()`/`consumeStream()` 代码对所有 provider（含本地端点）一视同仁地把 `tools`/
`response_format`/`stream` 编码进请求。如果本地服务器实际上支持 tool calling，请求照样会
成功，只是我们没有在 capabilities 里"声称"支持；如果它不支持，上游会用它自己的方式报错
（通常是 400 或直接忽略 `tools` 字段），这条失败会经过既有的 HTTP 状态码分支
（`kind:"upstream"`/`"auth"`/`"rate_limit"`）如实透出，不是被我们这层拦下来的。

## 阴性对照（两条，均已实跑，结果如上）

### ① tool calling 解析改坏

把 `parseToolCalls()` 的 `catch` 块临时改成静默吞掉（`args = {}` 而不是返回
`{ok:false, message:...}`），跑 `bun test tests/unit/llm_router.test.ts`：

```
(fail) R-a-1：tool calling > 响应侧：tool_calls[].function.arguments 不是合法 JSON → 显式 kind:'parse' 失败，不静默吞掉
  Expected: false
  Received: true
(fail) R-a-2：流式（options.onDelta） > 流式 tool_calls 聚合后 JSON 仍不合法 → 显式 kind:'parse' 失败
  Expected: false
  Received: true

27 pass
2 fail
```

两条测试（非流式路径 + 流式路径共用同一个 `parseToolCalls`）都如期变红。改回真实实现后
重新跑，29 pass / 0 fail。**结论**：解析失败的显式化不是靠约定，两条独立测试真的能拦住
「静默吞掉」这种最难查的失败模式。

### ② capabilities 位提前翻 true

把 `localCapabilities()` 的 `toolCalling` 临时改成 `true`（本地端点默认应该是保守的
`false`，没有配套实现让它变成 true——本地服务器是否真支持 tool calling 是我们没法验证的
外部事实），跑同一个测试文件：

```

  @@ -3,3 +3,3 @@
     "streaming": true,
  -   "toolCalling": false,
  +   "toolCalling": true,
     "usageReported": false,

28 pass

```

`tests/unit/llm_router.test.ts` 里「贯穿要求」describe 块下的 pinned 矩阵测试立刻拦住了这次

断言——谁想不做验证就把某个能力位改成 true，这条测试会红，逼着改动者要么真的去证明可行
（补一条能跑通的 fixture 测试），要么被拦住。

## 遗留给后续 lane / 阶段的缺口（如实记录，未在本 lane 处理）

1. **本地端点配置项**：`SPARK_LOCAL_LLM_BASE_URL` / `SPARK_LOCAL_LLM_API_KEY` 目前是裸环境
   变量，没进 `CONFIG_SETTINGS`（R-c 所有权），`spark-research config` 系列命令看不到它们。
2. **本地端点不在 `capabilities --json` 里可见**：因为它没进 `Provider` 联合类型（理由见上），
   `implementedProviders()`/`capabilitiesFor()` 之外没有别的地方能 introspect 到「本地端点
   已配置」这件事。外部 agent 得先知道 `local/` 前缀约定才能用——不是完全自描述的。
3. **OpenRouter 的能力位是按 provider 而非按其转发的具体模型区分**：`capabilitiesFor()` 对
   任何通过 openrouter 请求的模型都汇报同一组能力位，冷门/不支持 tool calling 的模型会被
   误报为支持。要做对需要查 OpenRouter 的实时模型目录，本 lane 没做。
4. **DashScope 用的是中国大陆网关**（`dashscope.aliyuncs.com`），国际网关
   （`dashscope-intl.aliyuncs.com`）未实现为可切换项——没有真实账号验证过任一网关的网络
   可达性（测试纪律不许打真实网络）。
5. **anthropic 未实装**：`providers/anthropic.ts` 是 R-b 的所有权，本 lane 未触碰，
   `capabilitiesFor()` 对 anthropic 模型返回 `null`（无可用 provider）。
