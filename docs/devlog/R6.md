## 第 12 步 · `llmTimeoutMs` 边界

三次都走 `PUT /api/settings/general/llmTimeoutMs`（网页端 number 输入框打不进 `abc`，该值改用 curl 同端点发，等价于界面背后的那一次写）：

```

value="abc"  → HTTP 422   {"error":"'llmTimeoutMs' 必须是数字，收到 'abc'","nextStep":"填一个毫秒数，例如 120000"}
value=30000  → HTTP 200   {"item":{"key":"llmTimeoutMs","value":30000,"source":"config",…}}

**判断：不过（三分之一不过）。**`abc` 拒得对，`30000` 收得对，但 **`500` 被接受并写进了 config.json**——任务书的期望是拒绝（下限 1000）。下限校验不存在。见 U22（P1）。

附带发现（反证第 4 步）：`llmTimeoutMs` 这一项写完**立刻**在响应里回显新值且 `source` 标 `config`（不是 `env`）。它与 `defaultModel` 的差别正好是「启动时 config.json 里有没有这一项」——这是 U15 根因的关键对照。

### U15 · 启动时 config.json 被灌进 `process.env`，运行中的 server 永远用启动时的旧值；`source` 因此误标成 `env`（P0）

**现场**：T5 第 4 步（网页端设置 ▸ 通用 ▸ 改 `defaultModel`）→ 第 6 步（核台账 `model`）。

**证据**：

```
（1）网页端保存成功，文件也写对了
[XHR] PUT 200 http://127.0.0.1:4321/api/settings/general/defaultModel
$ cat ~/.spark-research/config.json
{ "defaultModel": "moonshotai/kimi-k2.6", "contactEmail": "jimmyag2026@gmail.com" }
$ bun backend/src/index.ts config get defaultModel
  当前值: moonshotai/kimi-k2.6          ← 新起的 CLI 进程读到新值

（2）同一时刻，运行中的 server 还在返回旧值，并把来源说成环境变量
$ curl -s http://127.0.0.1:4321/api/settings/general
{"key":"defaultModel","value":"z-ai/glm-5.3-flash","source":"env","configured":true,
 "nextStep":"当前值来自环境变量 SPARK_RESEARCH_MODEL——在这里改会写进 config.json，但要 unset 掉那个环境变量才会生效"}
网页端刷新后输入框里仍是 z-ai/glm-5.3-flash

（3）SPARK_RESEARCH_MODEL 根本没有人设过
$ if [ -n "${SPARK_RESEARCH_MODEL+x}" ]; then echo YES; else echo NO; fi     → NO
$ ps eww -p 46563 | tr ' ' '\n' | grep -cE '^SPARK_'                        → 0
   （server 进程 exec 时的 40 个环境变量里没有任何 SPARK_ 前缀）

（4）改完模型后发 chat，台账记的是改前的模型（P0 判据直接不过）
$ bun backend/src/index.ts usage --project t5-20260915 --json
"byModel": { "z-ai/glm-5.3-flash": { "calls": 3, … } }
$ cat ~/.spark-research/projects/t5-20260915/usage.jsonl
{"ts":"2026-09-15T08:31:59.803Z","command":"chat","provider":"openrouter","model":"z-ai/glm-5.3-flash","ok":true,…}

（5）根因在源码里（backend/src/config/index.ts:683 `applyConfigEnvDefaults`）
// 礼貌头是唯一「配置必须变成 env」的地方：politeness.ts 从 v0.2 起就只读 env，
// 而 connector 层在很多路径上拿不到 config 句柄。做法是**进程启动时把 config 的值
// 补进 env（已有 env 则不动）**——一次性、显式、优先级不变。
export function applyConfigEnvDefaults(options: ConfigOptions = {}): string[] {
  for (const spec of CONFIG_SETTINGS) {
    if (spec.secret || !spec.envVar) continue;
    if (spec.key === "dataDir") continue;
    const current = env[spec.envVar];
    if (current !== undefined && current !== "") continue;
    const value = config[spec.key];
    if (value === undefined || value === "") continue;
    env[spec.envVar] = String(value);          ← 所有非 secret 项都被灌进去，不只是礼貌头
  }
}
而 resolveSetting（同文件 :556）是「env 非空就赢，并标 source='env'」。

（6）反证：启动时 config.json 里**没有**的项不受影响
$ PUT /api/settings/general/llmTimeoutMs {"value":500}
{"item":{"key":"llmTimeoutMs","value":500,"source":"config",…}}     ← 立刻回显新值，source 标 config
```

**问题**：注释说这条通道是给礼貌头（`contactEmail` / `userAgent`）用的一次性补齐，但循环覆盖了**所有**带 `envVar` 的非密配置项。于是：

1. **运行中的 server 对 config.json 的任何后续改动免疫**——凡是启动时已经在 config.json 里的键，之后无论从网页端、CLI 还是直接编辑文件改，server 进程内读到的永远是启动那一刻的值，不重启不生效。「网页端能改模型」这件事实际上是**假的**。
2. `source` 标成 `env`，`nextStep` 让用户去 `unset` 一个**从来不存在的环境变量**——用户照做会发现 unset 了也没用，然后无从下手。
3. T5 第 6 步（P0）因此不过，形态与 USAGE_LOG **U10 完全同构**：U10 是「`chat()` 不读 `req.model`」，这次是「server 不读改过的 config」。上一轮补的门禁盯的是函数签名与实现，盯不到「进程内状态与磁盘状态分叉」。

**修改方向**：两处二选一或都做。①把 `applyConfigEnvDefaults` 收窄成白名单（只补 `contactEmail` / `userAgent` 这两个 politeness 真的只读 env 的项），其余项由 `resolveSetting` 直接读 config；②写路径（`PUT /api/settings/general/*`、`config set`）在写文件后同步刷新进程内的那份 env/缓存。影响面：`resolveSetting` 是全局读口，改白名单风险小且可被现有单测覆盖；建议同时补一条门禁——**「HTTP 改一个配置项 → 同进程立刻读回新值」**，这条断言能整类地抓住「写了但进程没跟上」。

```

**问题**：任何 `spark-research chat … && 下一步` 的脚本都会在什么都没发生的情况下继续往下走。U12 记的是 HTTP 侧「拒绝返 200」，这里是 CLI 侧的同一个病。

<a id="u22"></a>
### U22 · `llmTimeoutMs` 没有下限校验，500ms 被接受

**证据**：

```
PUT /api/settings/general/llmTimeoutMs {"value":"abc"} → 422 {"error":"'llmTimeoutMs' 必须是数字，收到 'abc'","nextStep":"填一个毫秒数，例如 120000"}
PUT … {"value":500}    → 200  {"item":{…"value":500,"source":"config"…}}      ← 期望拒绝
PUT … {"value":30000}  → 200
$ cat ~/.spark-research/config.json → { …, "llmTimeoutMs": 500 }
```

**问题**：类型校验有，范围校验没有。500ms 的 LLM 超时会让**每一次**调用都超时（基线里单次调用普遍 5–70s），而且失败会被记成 `ok:false`，看起来像上游炸了。任务书写的下限是 1000。

**修改方向**：给 `*TimeoutMs` 一族加上下限（并在错误消息里给出建议值），与现有的类型校验同一处。
