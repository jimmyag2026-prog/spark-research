# W5-2 δ · V31/V32：外部 MCP 工具调用真的进证据图

lane：`W5-2-d`（波次 W5-2，δ 条）· 分支：`feat/W5-2-d`（基于 main `6fe28e5`）

## 为什么这条 lane

「外部工具调用天然进 provenance」是本项目相对 OpenScience 的差异化点，但 v0.4
W4-d 只兑现了一半：每次外部 MCP 工具调用确实落一条执行记录，但记录写在
`extensions/<name>/.mcp_calls.jsonl`，没有进项目的证据图（`project/**` 不在 W4-d
的文件所有权内）。v0.4.0 发布材料把这条列为三件未关闭事项之一。V31/V32 就是去关
它——V31 让外部工具调用再落一条证据图 observation，V32 把 `createExternalToolRunner()`
接进 `AgentToolBus.options.runner`，两者是同一件事的两半（DEVELOPMENT_PLAN_v0.5_MODULES.md
§1.5 第二行）。

## V31：外部工具调用落一条 observation record

`backend/src/extensions/mcp_client.ts`：

- `ConnectExternalMcpOptions` 新增可选字段 `recordSink?: EvidenceRecordSink`
  （`EvidenceRecordSink = Pick<RecordStore, "create">`——只给"写一条 record"这一个
  方法，不给 `update`/`link`，`call()` 从头到尾只创建、不修改任何既有 record）。
- `ExternalMcpSession.call()` 内部**唯一**的记账分发点 `record()` helper，在原有
  `appendMcpCallRecord()`（jsonl）之外，若 `recordSink` 存在，**再**调
  `recordSink.create({ type: "observation", evidence: "sourced", metadata: {...} })`。
  四个分支——成功 / 失败（isError）/ 超时 / 未知工具——全部流经这一个 `record()`
  helper，所以四个分支都会落 observation，与 W4-d 钉死的 jsonl 口径完全同步（同一
  行代码触发，不是并行维护两套逻辑）。
- `recordSink.create()` 抛错时用 `try/catch` 吞掉，不拖垮工具调用本身的返回值——
  jsonl 那一半已经先落盘，observation 是"锦上添花"的第二份记录，不是唯一真源。
- `recordSink` 是**可选**且默认不给：`mcp_client_verify.ts`（`ext verify`）、
  `discoverExternalMcpTools()`（发现探测）都没有、也不该有 project 上下文，不传
  这个字段就是 W4-d 原样行为（只写 jsonl），本次没有改动它们的调用方式。

`backend/src/agents/contract.ts`：

- 新增 `EXTERNAL_TOOL_CALL_OBSERVATION_KIND = "external_tool_call"` 常量与
  `ExternalToolCallObservationMetadata` 接口（导出，供 mcp_client.ts 复用，两处
  metadata 形状不许漂移）。
- `NON_EVIDENCE_RECORD_TYPES` 从 `Set<RecordType>` 放宽成 `Set<string>`，加入
  `EXTERNAL_TOOL_CALL_OBSERVATION_KIND`。**这里没有简单照抄"加进 Set"**：
  `external_tool_call` 不是独立的顶层 `RecordType`（那样要么给 `RECORD_TYPES` 加
  第 10 类，要么放弃 `observation` 复用 `CITATION_INTEGRITY_REVIEW_KIND` 那一套既
  有手法），它复用 `observation` 这个 type，靠 `metadata.kind` 区分"审计痕迹"还是
  "真证据"。所以 `isEvidence()` 现在做两件事：先比对 `record.type`（覆盖 `agent_run`
  这类独立类型），再对 `type === "observation"` 的记录额外比对 `metadata.kind`
  （覆盖 `external_tool_call` 这类共享类型）。这个设计选择在 contract.ts 的大注释
  里写清楚了理由，不是我自己拍的——任务书原话「把 external_tool_call 加进
  NON_EVIDENCE_RECORD_TYPES」按字面（`Set<RecordType>`）做不到（编译不过），字面
  背后的意图是「让外部工具调用记录不计入证据图的进展口径」，这个意图我做到了。

## V32：createExternalToolRunner() 接进 AgentToolBus.options.runner

`backend/src/agents/orchestrator.ts`：

- `OrchestratorDeps` 新增可选字段 `externalTools?: ExternalToolRegistry`
  （`extensions/mcp_client.ts` 的登记表类型）。
- `getToolRunner()` 从同步改成 `async`（`createExternalToolRunner()` 本身是
  `async` 工厂，内部动态 `import("../mcp/server")`，见 mcp_client.ts 文件头注释）：
  注入了 `externalTools` 就走 `await createExternalToolRunner(baseOptions, this.externalTools)`，
  否则原样 `new McpToolRunner(baseOptions)`。两处调用方（`executeTask` 的
  `"subagent"` 分支、`runResearchLoop()`）本来就在 `async` 函数体内，补一个 `await`。
  惰性构造 + 跨调用缓存（`this.toolRunner`）语义不变。
- `createExternalToolRunner()` 产出的仍然是 `McpToolRunner` 的**子类实例**（子类化，
  不是替换）——`mcp:<extension>:<tool>` 这类已注册的外部工具名路由给对应
  session，其余工具名原样交给内置逻辑（父类的"未知工具"分支兜底不变）。
- 没有新的模块级循环依赖：`extensions/mcp_client.ts` 顶层只 import
  fs/path/MCP SDK/`llm/types`/`agents/contract`（类型只读引用）/
  `./types`/`./grants`/`./context`/`./paths`；它对 `../mcp/server` 的依赖是动态
  import。orchestrator.ts 新增的静态 import（`createExternalToolRunner`,
  `ExternalToolRegistry`）不会绕回 orchestrator.ts 自己。

**明确的范围边界**：`externalTools` 只改变"某个 `mcp:` 工具名认不认得、调用是否
真正执行"这一层。子代理能不能拿到某个 `mcp:` 工具名的**授权**仍然是
`SubAgentSpec.grants` 白名单说了算（`agents/toolbus.ts` 的 AD-2 硬规则，本 lane
不许碰这个文件，也没有绕开它的必要）——V32 不会因为某个外部工具被注册进 registry
就自动把它塞进任何子代理的 grants 列表。

## V31/V32 现在是否完全关闭了？还剩什么？

**没有完全关闭，如实说清楚剩什么：**

V31 和 V32 各自作为"机制"是完整、可用、有阴性对照钉死的：给了 `recordSink`，四个
分支都会落 observation 且被 `NON_EVIDENCE_RECORD_TYPES` 正确排除在进展口径之外；
给了 `externalTools`，子代理经 `AgentToolBus` 调用外部工具名时，授权/预算/审计
三层自动生效（本 lane §11 那条测试直接验证了这一点：白名单内成功且落审计记录，
白名单外结构化拒绝，不会因为工具"存在"就绕开 AD-2）。`bun run typecheck` 与
`bun test tests/unit` 全绿（1738 pass / 0 fail，比基线 1725 只涨不跌）。

**但生产路径上，这两个机制目前谁都没有被真正接通**——这不是本 lane 的疏漏，是
文件所有权画的边界决定的：

1. **谁来构造 `ExternalToolRegistry` 并把真实扩展的 session 注册进去**：需要
   在某个时机遍历已装载、已授权的 `mcp_client` 扩展，逐个 `connectExternalMcp()`，
   把 session `register()` 进一张表。这段"连接真实扩展"的逻辑该放哪、什么时候跑
   （daemon 启动时一次性连？每个 session 各自连？），不在本 lane 的文件所有权
   （`extensions/loader.ts`、`daemon/daemon.ts` 都不许碰）。
2. **谁来构造 `OrchestratorAgent` 时传入 `externalTools`**：`grep -rn "new
   OrchestratorAgent("` 命中三处——`backend/src/index.ts`（两处，显式禁止）、
   `backend/src/server/context.ts`（不在本 lane 所有权内）。这两个文件今天都没有
   传 `externalTools`，所以即使 ① 做了，生产环境下 `OrchestratorAgent` 拿到的
   `externalTools` 仍然是 `undefined`，`getToolRunner()` 会走"没给就退回默认"
   那条分支——V32 的机制存在，但目前无人喂它真实数据。
3. **谁来把 `recordSink` 接到真实的 `project.records()`**：`connectExternalMcp()`
   今天的两个生产调用点——`mcp_client_verify.ts`（`ext verify`，本来就没有、也不
   该有 project 上下文）——都没有传 `recordSink`。真正会在"研究循环里调用外部
   工具"这个场景下需要 `recordSink` 的调用点，就是 ① 里要新建的"连接真实扩展"
   逻辑，它需要同时拿到当前 session 绑定的 `project.records()` 传进去。这与 V32
   的缺口是同一个缺口的两面：都卡在"谁来在生产环境里真的把已装载的 mcp_client
   扩展接上 orchestrator/project"这件事上，而这件事横跨 `extensions/loader.ts`
   （或 `daemon/daemon.ts`）与 `server/context.ts`/`index.ts`，不在任何一条
   W5-2 lane 的单独所有权范围内。

**结论**：机制层面（V31 的"记不记证据""如实计不计入进展"、V32 的"路由/授权/预算/
审计"）已经关闭，可以在对外材料里说"外部工具调用有了完整的证据图接入机制，并有
测试钉死语义"。但不能说"外部工具调用现在默认会进证据图"——默认路径下没有人构造
`ExternalToolRegistry` 也没有人喂 `recordSink`，这两个字段目前只有测试在用。这是
下一条收口 lane（很可能是把 `extensions/loader.ts`/`daemon/daemon.ts` 与
`server/context.ts`/`index.ts` 放进同一条 lane 的那种"横切收口"）该做的事——本
devlog 把"要接的两个点分别在哪"钉清楚了，收口不需要重新调研。
