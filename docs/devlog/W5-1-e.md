## 1. 逐处清单与修法

### 1.1 两种修法（都来自 F-c，本 lane 未新发明）

| 资产类别 | 修法 | 为什么 |
|---|---|---|
| `.sql` / `.txt` | 静态 `import X from "./x.sql" with { type: "text" }` | 进程内读**内容**，编译期入二进制即可 |
| `.py`（被外部子进程 spawn） | 静态 import 文本 → **运行期解包到真实临时文件** → spawn 那个真实路径 | 外部 python 面对的是操作系统真实文件系统。**单靠 `with { type: "file" }` 不行**——它给的是 `/$bunfs/root/xxx-hash.py`，外部进程打不开（F-c §3.2；本 lane §5.1 又实机复现了一次） |

### 1.2 本 lane 新增的三个共享件

| 文件 | 作用 |
|---|---|
| `backend/src/assets/embedded.ts` | `materializeAssetTree(key, files)` / `materializeAsset(key, rel, content)`：把内嵌资产解包到 `$TMPDIR/spark-research-assets/<key>-<内容指纹>/`，按内容指纹幂等；另导出 `RUNNING_IN_COMPILED_BINARY` |
| `backend/src/assets/assets.d.ts` | `*.sql` / `*.txt` / `*.py` 的 ambient 声明（tsc 不认识这些扩展名） |
| `backend/src/agents/prompts.ts` | 八个 prompt 的内嵌副本 + `readPromptText(dir, filename)`（**磁盘优先、内嵌兜底**） |

**F-c 没提、但实现时躲不掉的一条**：两个 `runner.py` 都做
`sys.path.insert(0, str(Path(__file__).resolve().parents[2]))` 然后
`from simulation.sim_runtime import ...` / `from simulation.pyref.oscillator import ...`。
它们**不是孤立脚本，是一棵 python 包树里的模块**——只解包 `runner.py` 一个文件，
python 在 import 阶段就 `ModuleNotFoundError`。所以解包单位是**资产树**而不是单文件；
`opentrons_backend.py` / `python_kernel.py`（只 import 标准库）是它的退化情形。
这一点 F-c 的"抽一个 `ensureUnpackedScript(name, content)` helper"的建议签名是不够用的，
本 lane 按实际需要改成了树。

### 1.4 4 处 `.py`

| 位置 | 资产 | 解包内容 |
|---|---|---|
| `lab/wet_backend.ts:112` | `opentrons_backend.py` | 单文件（`backendScript()` 惰性解包——`lab backends` 这类命令不 spawn python，没必要在 import 时就写盘） |

| `simulation/openmm/index.ts:34` | `runner.py` | **整棵树**：`simulation/{__init__.py,sim_runtime.py}` + `simulation/openmm/{__init__.py,runner.py}` |

### 1.5 3 处 prompt `.txt`

三处**共用一个** `readPromptText(dir, filename)`：先读调用方给的真目录，读不到才落内嵌副本。

| 位置 | 原症状 |
|---|---|
| `agents/orchestrator.ts:177` `loadPrompt()` | 二进制里恒 catch → system prompt 静默变 `[prompt missing: core.txt]`（**不崩溃，只是降智**，比 ENOENT 更难发现） |
| `agents/sub_agent.ts:238` `DEFAULT_PROMPT_DIR` + `loadPromptFile()` | 五个子代理（explore/literature/execute/lab/reviewer）的 system prompt 全部读不到 |
| `ideation/coexplore.ts:35` `loadCoExplorePrompt()` | 同样静默降智 |

**顺带**：`orchestrator.ts:720` 传给 `CoExploreSession` 的 `promptDir` 也改成同一个常量
`PROMPT_DIR`（不改也能靠兜底跑通，改了是为了口径统一 + 让 §2 的门禁能钉死）。

**为什么是"磁盘优先"而不是"内嵌优先"**：反过来会让"调用方传自定义 promptDir"这个既有能力
失效（测试、扩展都在用），那是拿一个 bug 换另一个。

### 1.6 3 处危险默认路径（含 V33）

| 位置 | 编译产物里解析成 | 危险等级 | 处置 |
|---|---|---|---|
| **`agents/orchestrator.ts:223`（V33）** | `/workspaces`，紧接着 `mkdirSync(..., {recursive:true})` | **最高：往文件系统根写** | 默认值改成 `join(dataDir(), "workspaces")`——`dataDir()` 是仓库既有单一真源（env `SPARK_RESEARCH_DATA_DIR` > `~/.spark-research`），不另起一套 |
| `scaffold/cli.ts:53` | `/`，然后往 `/backend/src/skills/...` 写生成的源码 | 高：往根写 | **刻意不"修好"**（F-c §5.1 裁定）：脚手架的产出就是往仓库写源码，编译产物里没有仓库。改成 `RUNNING_IN_COMPILED_BINARY` 时**显式抛错**，而不是照着往 `/` 写 |
| `extensions/platform_verify.ts:25` | `/`，`CONTRACT_HELPER` = `/tests/helpers/...`，且 `cwd: REPO_ROOT` 会拿 `/` 当子进程工作目录 | 中：只读 + 已有 `existsSync` 门 | 同上裁定：编译产物里 `REPO_ROOT` 直接置 `null`，让既有的门如实报错，且**永远不会**拿 `/` 去 spawn |

## 2. 测试（只增不减，0 skip）

新增 `tests/unit/embedded_assets.test.ts`（14 条）。文件头部第一段就写明**它的局限**：

> 单元测试跑在源码模式下，`import.meta.dir` 是真实目录，磁盘上那份资产全都在——
> **源码模式下的测试永远抓不到 V27 本身**（这正是它活到 v0.4 的原因）。

所以它测的是源码模式下**可判定**的三件事：

1. **内容一致**：八个 prompt / 三个 schema 的内嵌副本与磁盘那份逐字节相同；prompt 还做
   **集合相等**断言（磁盘多一个 prompt 而 `prompts.ts` 没跟着 import → 那个子代理会在二进制里
   静默降智，这条断言专门防它）。
2. **解包机制真的可用**：`materializeAssetTree` 出来的路径**真 spawn 一次外部 python3**，
   并让它 `from simulation.sim_runtime import VALUE`——验的是"外部进程打得开 + 同包 import 得到"，
   不是形状断言。另外断言 pyref/openmm 的 `entryPointFor()` 落在真实文件上、树里有 `sim_runtime.py`、
   解包出来的 `runner.py` 与仓库那份逐字节一致。
3. **源码级门禁**：生产代码里不再有「读资产的 `import.meta.dir`」（F-c 表里那 10 处逐处核）
   与「`join(import.meta.dir, "../../..")` 这类跳到根的默认路径」（白名单只放 `existsSync`
   门控的 venv 兜底、前端目录，以及被关在 `RUNNING_IN_COMPILED_BINARY` 后面的两处）。

另改 `tests/unit/narrative_parity.test.ts`：把 `backend/src/assets/assets.d.ts` 登记进
`ALLOWED_ORPHANS`。理由写在那条登记里——`.d.ts` 是 ambient 声明，**按语言规则**就不该有 import 边，
由 tsconfig 的 include 收录，孤儿检测（查"运行期有没有调用方"）对声明文件语义上不适用。
⚠️ **这是与 lane α 的唯一足迹重叠**（`narrative_parity.test.ts` 归 α 登记「等接线」），
只加了一条 entry，没动任何既有条目或判据。

## 4. `doctor` 盲区确认消失（F-c §5 的未完成项）

F-c 记的盲区原话是：science 档的可用性探测 `OpenMMPlatform.probeCode()` 是一段**内联 Python
字符串**，不读磁盘上的 `runner.py`，所以"探测"这一步在编译产物里不受 V27 影响；但**真正提交
一次仿真任务**走的是 `entryPointFor()`，那才会去读 `runner.py`。于是 `doctor` 报"science 可用"
对"能不能真跑一次 openmm 任务"是有盲区的。

**确认已消失**，判据是 §3.2 那份输出里首尾呼应的两条：

| 步骤 | 走的代码 | 结果 |
|---|---|---|
| `doctor` / `exp platforms` 报 science ✅ | `probeCode()`（内联字符串，不摸 runner.py） | ✅ |
| `exp run <id>`（真提交一次 openmm 任务） | `entryPointFor()` → **解包出来的 runner.py** → 外部 python 执行 | ✅ 跑完，产出 1503 原子的真实能量数据 |

**两条现在指向同一个结论**——探测说可用，真提交也真的能跑完。盲区之所以消失，正是因为
`entryPointFor()` 现在返回的是解包后的真实路径而不是 `/$bunfs/root/runner.py`。

另有一条**顺带的实证**（同一次验证里跑出来的，值得记）：第一次提交 openmm 任务我给了
`boxSizeNm=1.5`，产物如实报了

```
❌ 仿真失败：OpenMMException: NonbondedForce: The cutoff distance cannot be greater than
   half the periodic box size.（实验 e065d5e1 状态 failed，可 retry）
```

这是一条**真实的物理参数错误**（cutoff 0.9nm > 半个 1.5nm 盒子）——能报出这种错，
说明 runner.py 已经真的执行到构造 OpenMM System 那一步了。换成 `boxSizeNm=2.5` 就跑通了。
比"跑通了"更能证明这条链路是活的。

⚠️ 但盲区消失**不等于** `doctor` 从此能保证"提交任务一定成功"——上面这条参数错误就是反例。
`doctor` 现在也没有、也不该去真的提交一次任务来验证。消失的是**由 V27 造成的那一类**盲区
（探测不摸资产、执行摸资产、于是两者结论可以不一致）；参数是否合法这类盲区跟 V27 无关，仍在。
