## 一、关键设计取舍

### 1. 审批语义在 lifecycle 本体里，不在调用方（K-2 / X-1）

`transition()` 里守着 L-2 的两条 dispatch 入边，**没有第三条**：

- `approved --dispatch--> queued`：必须携带 `approval` 且 `approval.planDigest === ctx.planDigest`
- `planned --dispatch--> queued`：**仅当** `ctx.approvalRequired === false`

于是「无审批也能派发」这件事在**类型与运行期两层都没有入口**：broker 不提供 `force` 参数，`approvalRequired` 是 `validatePlan` 强制的派生值（L-3），调用方伪造 `approvalRequired:false` 的计费 plan 会被 `validatePlan` 当场拒。任务书里说的「后门会活到生产」在这套形状下没有地方安放——这是本 lane 最重要的一条结构性决定。

### 2. 「批了」与「动手了」是两个状态

`awaiting_approval → approved → queued`。approval 在 `approved → queued` 那一次 **CAS 写**里被消费（`approval → consumedApproval`）。崩溃重启后磁盘上的 `approval` 已经是 `null`，`consume()` 抛 `ApprovalRequiredError`——想重派必须重新 `approve`。这与湿实验 D-10 同构，测试里有一条专门的「重启后不能凭旧 approval 重派」（用**全新的 `ComputeJobStore` 实例**读同一个磁盘目录来模拟重启，不是改内存变量）。

### 3. 与 §2 签名的偏离（逐条列出）

| # | 偏离 | 理由 |
|---|---|---|
| D-1 | `LIFECYCLE_EVENTS` 里没有 `release` 事件，`broker.release()` 走 `close`（resource 轴）| §2.1 的事件表是给定的（21 个），`release` 不在其中。L-6 要求「`recoverable` 只能由 delivery=complete 或 release 置 false」——实现里 `deliver_ok`（收割成功）与 `deliver_reject`（人明确放弃产物）两者都把 `recoverable` 置 false，`release()` 因此必须先经过 delivery 终态。语义等价，且比「release 能直接抹掉 recoverable」更严：**放弃产物是一次显式的人的决定，不是资源清理的副作用** |
| D-2 | 新增 `broker.discard(jobId, reason)` | 上一条的必然结果：要让 `release` 在「不想要产物」时也能走通，得有一个显式的放弃动作。§2.5 没有它 |
| D-3 | 新增 `broker.replan(jobId, input)` | §1.1.4 要求「重新 plan() 得到新 digest → 旧 approval 作废，留 `supersededApproval`」，但 §2.5 的 `plan()` 签名是「新建 job」，落不到同一个 jobId 上。`replan()` 是那条纪律的实现位置 |
| D-4 | `ComputeJobStore.create()` 多两个可选参数（`jobId` / `now`） | 测试要确定性；两者都只在**没给**时回退到真实值 |
| D-5 | `approval.consume()` 顺带做 `dispatch` 那一次 lifecycle 转移 | §2.4 只说「同一次 CAS 写入里 approval→consumedApproval」。既然是同一次写，状态转移就必须在同一次写里，否则会出现「审批消费了但状态还没走」的中间态——那正是并发重派的缝 |
| D-6 | `LocalComputeAdapter.capabilities().network = ["none","unrestricted"]`、`secretRefs: true` | 设计 §1.1.6 给的是 `{billable:false, persistentVolume:false, recovery:true, secretRefs:false}`。**改动理由**：如实声明本机进程的能力（它确实能联网、确实能拿到 env 里的密钥）；顺带让 CI 能用 local 走**完整审批链**——若 local 三项全 false，`approvalRequired` 恒为 false，审批链在 CI 里根本跑不到（方案 §0.2 明写「CI 用 local adapter 走完整审批链」）。`billable` 仍然是 false |
| D-7 | 契约测试放 `tests/unit/compute_dispatch_once.test.ts` 而不是 `tests/concurrency/` | 本 lane 的文件所有权表（主会话下发版）只包含 `tests/unit/compute_*.test.ts`。内容与 §四 要求的 N=30 并发对抗一致，只是落点不同——**主会话若要移回 `tests/concurrency/`，整文件搬即可，无依赖** |
| D-8 | `plan.ts` 里 `validatePlan` 在 `buildPlan` 末尾自动跑一次 | §2.2 把两者列为独立函数。不自动跑意味着存在「构造得出但非法」的 plan 对象在内存里流动，没有价值 |

### 5. 上传 deny-list 的最终清单

**目录名**（路径任一段命中即拒）：`.git` `.ssh` `.aws` `.kube` `.gnupg` `.docker` `.config` `node_modules` `.venv` `venv` `__pycache__` `.terraform` `.vagrant`

**路径模式**：`.config/(gcloud|gh|op)/…`、`.local/share/keyrings/…`

**文件名模式**：`.env` 与 `.env.*`、`.netrc`、`credentials(.json)`、`id_{rsa,dsa,ecdsa,ed25519}`、`*.{pem,key,p12,pfx,keystore,jks}`、`.htpasswd`、`secret(s).{json,yaml,yml,toml}`

**双限额**：`UPLOAD_COUNT_LIMIT = 200` / `UPLOAD_BYTES_LIMIT = 256 MiB`（都是导出常量，审批面可显示）。

**两条口径**（设计里没写死，我做了选择，请主会话过目）：
- **显式请求命中 deny-list → 抛 `UploadDeniedError`**（fail-closed，设计明写）；**目录递归展开时命中 → 跳过并记进 `skipped[]`**，可见不静默。
- **gitignore 只作用于递归展开出来的文件**：显式点名的单个文件即便被 git 忽略也照传。理由：数据文件常年躺在 `.gitignore` 里，那不是密钥问题；密钥由 deny-list 硬拦。反过来做会让「我明明点名了它却没传」成为一个静默的坑。

### 6. local adapter 的 exit-code 由**任务侧**写，不是编排侧

`run()` 起的是 `/bin/sh <生成的 runner.sh> <被审批的 argv...>`。runner.sh 的内容是**常量**（不拼接任何 plan 内容），只做三件事：`"$@"`、取 `$?`、原子地写 `exit-code`。

- 为什么要 shim：如果 exit-code 由编排进程在 `await proc.exited` 之后写，那么编排进程被 SIGKILL 的那一刻，一个**已经跑完**的任务会被后来的 `recover()` 误判成「丢了」。W5-3 α 的 SIGKILL e2e 正是要走这条路径。
- 为什么用 `"$@"` 而不是 `sh -c "<字符串>"`：被审批的 argv **不做第二次 shell 展开**（设计 §1.1.3 ①）。有一条专门的测试：`command = ["/bin/echo", "$(id -u) && rm -rf /"]` 跑完后，`run.log` 里必须原样出现这串字符，`runner.sh` 里必须找不到它。

## 五、遗留问题与我不确定的地方

1. **`bun.lock` 没有跟着 `package.json` 更新**。文件所有权只给了 `package.json`，`bun.lock` 不在其中，而它是所有 lane 共享的生成文件（两条 lane 同时改必然冲突）。后果是**本分支上 `bun install --frozen-lockfile` 会失败**：
   ```
   error: lockfile had changes, but lockfile is frozen
   ```
   收口时需要跑一次 `bun install`（不带 `--frozen-lockfile`）并把 `bun.lock` 一起提交。**W5-2 α 真正 import modal 之前必须先做这一步。**
2. **`delivery: rejected` 的语义是我定的**（D-1/D-2）。如果主会话认为「放弃产物」应该是一个独立的 lifecycle 事件而不是复用 `deliver_reject`，改动面在 `lifecycle.ts` + `broker.discard()` 两处，测试跟着改。
3. **local adapter 的 `network` 能力是「声明」不是「强制」**：声明 `network:"none"` 的本地任务事实上仍然能联网（我们没有做 sandbox / netns）。这一点在 modal 上是真约束，在 local 上只是「这次运行不需要网络」的**意图声明**——它影响的是 `approvalRequired` 的派生，不影响子进程真实能做什么。**这是一处名实不符，我选择了如实记在这里而不是假装它是隔离。**若要坐实，得引入 sandbox-exec / netns，超出本 lane。
4. **gitignore 的回退解析器只认三种最常见形态**（目录名 / 文件名 / `*.ext`），否定规则（`!`）与复杂 glob 一律当作「没忽略」。优先路径是 `git check-ignore --no-index`（权威口径），回退只在「工作区不是 git 仓库」时生效。CI 里两条路径都跑得到，但**权威路径的用例覆盖弱**（我只在非 git 目录里构造了回退路径的测试）。
5. **`recover()` 的 `RecoverFailure` 分类目前只有 local 的 `not_found` 一种真实来源**，其余五种（`unauthorized` / `quota` / `ownership_mismatch` / `invalid_request` / `retryable`）只在 broker 侧有分类处置的测试（用假 adapter 注入）。真实分类逻辑是 CB-4 的活。
6. **没有验证的东西，我明确说没验证**：Modal 相关的一切（本波不 import）；桥（`sim_bridge.ts`，W5-3）；CLI/HTTP/MCP 接线面（W5-2 β）；`/api/compute/machine` 的投影（我只提供了 `approvalGate()` / `dispatchGate()` 两个推导源，没有 HTTP 路由）。
