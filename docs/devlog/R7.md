raw/llm 里这一次调用：`response.inline = ""`（`ok:true`、`failureKind:null`、**输出 1200 token**）。

POST /api/session/chat → response 里是完整正文
raw/llm：z-ai/glm-5.3-flash(summarize) 输出 447 token，content 长度 787 字符

`ok=true · chunks=6 · streamedLen=40 · content=" 酶是由活细胞产生的、具有高效催化作用的有机物…"`——增量与全文都正常。

`summarize()` 只检查 `res.ok`，`ok:true` + 空 content 直接当正文返回：

```ts
return { text: res.content };     // orchestrator.ts:1238
```

于是 `review` 照样 `approved:true`，用户拿到一个空回答，**没有任何一处报错**。

但在流式路径上四次里中了四次。

**修改方向**：① `summarize()` 必须把「`ok:true` 但 `content` 为空/只有空白」当失败处理
（现成的失败分支就在上面几行，文案照抄即可），并让 `review` 不 approved——U12 的裁定在这里没被遵守；
② 根因同 U66（上限把 thinking 算进去）；
③ 门禁：注入一个「ok:true、content 空」的 LlmResponse，断言 chat 的 `response` 不得只剩 `[session …]` 前缀。

## U70 · 422 的 nextStep 指向一个该面板没有的 DELETE（低）

```
PUT /api/settings/network/originAllowlist {"value":""}
→ 422 {"error":"'originAllowlist' 不能是空字符串","nextStep":"要恢复默认请用 DELETE，而不是写一个空值"}
DELETE /api/settings/network/originAllowlist
→ 404 {"error":"未知端点 /api/settings/network/originAllowlist"}
DELETE /api/settings/general/originAllowlist
→ 200（同一个 key，换个面板就有 DELETE）
```

`config/index.ts:920` 的这句 nextStep 是**所有面板共用**的，而 `app.delete` 只存在于
`general` / `credentials` / `extensions` 三处。用户在哪个面板被拒，就会在哪个面板找不到 DELETE。
**修改方向**：要么给每个面板补 DELETE，要么把 nextStep 写成具体路径（`DELETE /api/settings/general/<key>`）。
