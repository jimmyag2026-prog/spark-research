## 一、问题回顾

三轮实证（R1/R2）：任务书检索式下里程碑论文沉底——T1 召回 2/8、T2 3/8、T4 1/5@10
（limit 提到 150 仍 2/5），而缺席的论文按 DOI 直加秒中。旧实现
`backend/src/literature/dedupe.ts` 的 `compareMergedPapers` 排序键是「命中源数 →
被引 → 年份 → 标题」，命中源数是**第一**关键字——一篇高被引但只被 1 个源收录的
里程碑论文，会被大量命中 2+ 源但低被引的相关（非里程碑）论文压到后面，哪怕被引
数字差几个数量级。

## 二、设计

### 2.1 四档排序（`backend/src/literature/search.ts`）

`dedupePapers`（不在本 lane 文件所有权内）内部仍然固定用 `compareMergedPapers`
排一次序——不动它，`--rank hits` 需要与 v0.6 逐字节一致，这是最强的保证方式。
本 lane 在它的输出之上加一层：

- `hits`：原样返回 `dedupePapers` 的输出，**不重新 sort**（哪怡语义等价，直接不碰
  是对「逐字节一致」最强的保证，回归测试 `tests/unit/v67_ranking.test.ts` 的
  "applyRank(..., hits) 原样返回 dedupePapers 的输出" 用 `toBe`（引用相等）钉住）。
- `citations`：纯按 `citedByCount` 降序；缺值的论文整体退化到 hits 排序，排在
  已知被引论文之后（不当 0 处理——0 与「没有这个数据」是两件事）。
- `recent`：纯按 `year` 降序；缺值同款退化。
- `blended`（默认）：`score = hits × citationFactor × yearFactor`
  - `citationFactor`：已知被引数走 `1 + weight·log1p(citedByCount)`（log 压量级，
    1000 与 10000 被引不按十倍算）；缺被引数据的论文取本次结果集里**已知被引论文**
    citationFactor 的中位数作代理（`fallbackCitationFactor`）——不是 0（会把「没有
    这个数据」误判成「已证实 0 被引」，在被引普遍 >0 的结果集里比真被引 0 的论文排
    得更差都不奇怪），也不是给最高分（那是另一种编造）。
  - `yearFactor`：指数衰减，半衰期 12 年，`0.5^(age/halfLife)`；缺年份中性 1（不
    按最老处理）。
  - `BLENDED_CITATION_WEIGHT`（=1）与半衰期都是模块内常量，阴性对照①直接改常量
    验证。

### 2.2 CLI（`backend/src/literature/cli.ts`）

`lit search --rank blended|hits|citations|recent`，默认 `blended`。`parseRank()`
校验非法值并列出可选项；结果头新增一行 `result.rankNote`（AD-12：排序依据必须
可见，不能只给一个顺序让用户猜）。`LIT_HELP` / `LIT_SUBCOMMAND_HELP.search` 补了
四档各自的说明与默认值。

### 2.3 类级默认 vs CLI 默认（关键决策，真跑发现）

第一版实现把 `LiteratureSearcher.search()` 的类级默认也改成了 `blended`
（`options.rank ?? DEFAULT_RANK_MODE`）。跑 `bun test tests/unit` 后
`tests/unit/novelty_e2e.test.ts` 的 `P4 × C4 · 语义口径下的双向对照 > (a)` 从绿变红：
`result.embedding.basis` 期望 `"semantic"`，实收 `"lexical"`——语义嵌入静默降级。

根因：`backend/src/ideation/novelty.ts`（不在本 lane 文件所有权内）调用
`this.deps.searcher.search(query, { sources, perSource, limit })` **不显式传
`rank`**。类级默认一改，它检索到的候选集合（`limitPerQuery` 截断发生在排序**之后**）
跟着变了，而语义嵌入的 fixture cassette（`tests/fixtures/embeddings/`）是对着旧
候选集合录制的——新候选集合里出现了 fixture 没有向量的论文，触发嵌入路由的
「缺向量降级」分支。

这不是我能在本 lane 文件所有权内修的 bug（`ideation/novelty.ts` 不在允许列表），
也不该去碰语义 embedding fixture（需要真实 Ollama 重新录制，超出本 lane 范围）。
选择：**类级默认改回 `"hits"`**（v0.6 行为，任何不显式传 `rank` 的内部调用方——
`NoveltyChecker`、`CoExploreSession`、HTTP `server/routes/literature.ts`——都不受
影响），`blended` 只在 CLI 层（`cli.ts` 的 `parseRank()` 不给 `--rank` 时回落到
`DEFAULT_RANK_MODE` 并显式传参）生效。V67 的全部证据（R1/R2）都来自 `lit search`
这个人类入口，不是内部检索候选相关性，这个范围收窄合理。

**如实交代**：这意味着 HTTP/Web 前端（`server/routes/literature.ts:91`
`ctx.searcher().search(query, { sources, perSource: limit, limit })`）与
`NoveltyChecker`/`CoExploreSession` 内部检索目前**没有**享受到 blended 排序改进，
只有 CLI `lit search` 命令行入口默认换挡。这两处都不在本 lane 允许改动的文件里
（`server/*` 明确禁止，`ideation/novelty.ts` 未列入允许清单），收口如果决定要让
它们也用 blended，最小改法是在各自调用点显式加 `rank: "blended"`（`server/routes/
literature.ts:91` 一行；`ideation/novelty.ts` 的 `searcher.search` 调用一行——
但后者要先确认语义 embedding fixture 能不能重新录制，否则 novelty e2e 会重演
本节的降级）。

修复前后对照跑了两次 `bun test tests/unit`（详见下面「六」全量数字），修复后
`novelty_e2e.test.ts` 稳定 11 pass / 0 fail。

## 四、真实召回核验（尽力，如实）

方法：`SPARK_RESEARCH_DATA_DIR` 指向 `mktemp -d` 出的临时目录（脚本见下，未碰
`~/.spark-research`），新建临时项目 `v67-recall`，对 T1/T2/T4 冻结检索式跑
`lit search --sources openalex,crossref,europepmc,arxiv,pubmed --rank hits` 与
`--rank blended`（不用 aminer/semanticscholar——两者在这个 worktree 都未配置凭据，
`lit sources` 核实过，T4 中文里程碑 #1-3 只能靠 aminer 取，结构性不可达，如实排除，
T4 满分基准从 8 降到 5）。命中判据：DOI 精确匹配任务书里程碑表。

### 4.1 默认 `--limit 10`（等价 `perSource=10`，CLI 把两者耦合在同一个 flag 上）

| 课题 | 查询数 | hits 召回@10（并集） | blended 召回@10（并集） | Δ |
|---|---|---|---|---|
| T1 蛋白结构（8 篇基准） | 3 | 3/8（AlphaFold3 / RFdiffusion / binder design） | 3/8（同一批） | 0 |
| T2 单细胞聚类（8 篇基准） | 3 | 3/8（SCANPY / 归一化方法 / batch-effect benchmark） | 3/8（同一批） | 0 |
| T4 钙钛矿稳定性（5 篇可达基准，中文 3 篇因无 aminer key 结构性不可达） | 1（仅英文） | 1/5 | 1/5 | 0 |

**机制解释（为什么 Δ=0，没打到「+2」目标）**：`--limit 10` 同时把 `perSource`
也压到 10——每个源只贡献它自己 top-10（已经是该源自己的相关性排序），5 源合并后
的池子里**跨源命中数很少产生真实差异**（这批查询下，openalex 几乎独占结果，
crossref/europepmc/arxiv/pubmed 与它的重叠很稀疏，多数记录 `sources.length==1`）。
`hits` 模式的排序键是「命中源数 → 被引 → 年份 → 标题」，命中源数一旦全平，
第二关键字就是被引数——**在这个浅池场景下 `hits` 已经退化成准被引排序**，
blended 因此没有额外空间可以纠正。V67 描述的「命中源数把高被引论文压下去」这个
病灶，需要池子里真的出现「多源命中但低被引」的记录才会发作。

### 4.2 补充：`--limit 50`（T1，更深的池子，复现 R1/R2「limit 提到 50」的方法）

同样 3 条 T1 查询、`--rank hits` 与 `--rank blended`，`--limit 50`（perSource 也
是 50，池子更深，跨源重叠开始出现——Q2 的 hits 结果里能看到 `europepmc+pubmed`、
`arxiv+crossref` 这类 2 源命中、被引 0~3 的记录排到了第 1~5 名，AlphaFold3 被压到
第 6 名）。这里**确实复现了 V67 描述的病灶**：

| 里程碑（DOI 尾号） | hits 位次（Q1/Q2，出现的查询） | blended 位次 | 结果 |
|---|---|---|---|
| AlphaFold3（07487-w） | 6 / 27 | **1 / 4** | 两档下都在 top10 内，blended 排名显著更靠前 |
| RFdiffusion（06415-8） | 20 / 28（**top10 之外**） | **6 / 5**（**top10 之内**） | recall@10 净增 1（真实找回） |
| luciferases 设计（05696-3） | 38 | 11 | 大幅提前但仍差 1 名未进 top10 |
| Illuminating protein space（06728-8） | 40 | 12 | 大幅提前但仍差 2 名未进 top10 |
| protein binder 设计（38328-5） | 44 | 13 | 大幅提前但仍差 3 名未进 top10 |

T1 在 `--limit 50` 下 recall@10 并集：hits 1/8 → blended 2/8（RFdiffusion 从
top10 外拉回 top10 内）。其余三篇被引优势更弱、原始位次更靠后（38/40/44），
blended 把它们拉到 11~13 名，已经很接近但没跨过 10 这条线——排序机制本身工作
正常（三篇的相对顺序都被大幅前移），只是这批真实数据里它们的被引/命中比不够
压过池子里其它候选。ESMFold / Foldseek / ProGen2 三篇在 T1 三条查询、两档排序、
`limit 50` 的池子里**完全没有出现**（覆盖问题，不是排序问题——这三篇需要
V65/V8 覆盖侧或不同检索式解决，不在本 lane 范围）。

**如实交代**：`--limit`/`perSource` 耦合在同一个 CLI flag 上是既有架构（v0.6 就
如此，不是本 lane 引入），不在 `cli.ts` 允许改动范围内新增独立的 `--per-source`
flag（任务书只允许「加 `--rank` 解析与帮助文案、note 显示」）。这导致「recall@10」
这个目标在 CLI 默认深度下很难看出差异——真正体现 V67 价值需要更深的检索池。
收口如果要把「+2」目标打实，建议方向是解耦 `perSource` 与最终展示 `limit`（新
flag 或让 `perSource` 有独立的、比 `limit` 更深的默认值），这是一个真实的后续
项，不是本 lane 排序公式本身的缺陷。
