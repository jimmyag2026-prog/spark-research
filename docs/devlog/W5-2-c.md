## 一、限速器（V26）

### 设计

`backend/src/http/ratelimit.ts`：

```ts
export interface HostRatePolicy { rps: number; burst: number; source: string; verifiedDate: string; note?: string }
export const HOST_RATE_POLICIES: Readonly<Record<string, HostRatePolicy>>;
export class RateLimitedHttp implements HttpClient {
  constructor(inner?: HttpClient, policies?: Readonly<Record<string, HostRatePolicy>>, now?: () => number);
  request(url, init?): Promise<HttpResponse>;
  bucketOf(host: string): { tokens: number; lastRefill: number } | null;
}
export function rateLimitedHttp(inner?: HttpClient): HttpClient;
```

标准令牌桶，**键控是 `new URL(url).host`，不是 connector**：容量 = `burst`，冷启动满桶
（允许一次性打 `burst` 个请求不等待），此后按 `rps`（token/秒）持续回填，封顶 `burst`。
数学性质：对任意长度 T 秒的窗口，可消耗令牌数上限是 `burst + rps*T`——T=1s 时就是
`HOST_RATE_POLICIES` 里 `rps + burst` 的口径，`tests/concurrency/host_ratelimit.test.ts`
断言的正是这条不变式。

`acquire()` 拿不到令牌时用 `setTimeout` 轮询等待（间隔按「还差多少令牌/回填速率」折算，
封顶 50ms 避免单次睡过头导致排队请求被延迟释放）；检查 token 数与扣减发生在同一段不含
`await` 的同步代码里，JS 单线程语义保证并发调用之间不会插进来，不需要额外加锁。

**首批策略表**只登记了 `eutils.ncbi.nlm.nih.gov`（`rps:3, burst:3`，来源
https://eutilities.github.io/site/API_Key/usageandkey/ ，即 NBK25497 现行发布位置，
2026-09-10 web search 核实：匿名上限 3 rps，带 key 可到 10 rps）——这是本波唯一有「多个
connector 真的共享同一台主机」风险的场景（pubmed / ncbi / clinvar 三者）。本波新增的
biorxiv / reactome / string-db 各自的 host 在仓库里没有第二个消费方，且官方文档都没给出
可核实的具体限速数字，按「没写来源的数字不许进表」的纪律，没有编一个假策略——无策略的
host 走 `request()` 的直通分支，行为与未接限速器时一致。

### 接线点

`backend/src/connectors/registry.ts` `ConnectorRegistry` 构造函数：

```ts
constructor(options: ConnectorOptions = {}) {
  this.options = { ...options, http: options.http ?? rateLimitedHttp() };
}
```

生产路径（`new ConnectorRegistry()` 不带 `http`）天然带限速；测试/fixture 场景显式传入
`http`（StubHttp/FixtureHttp）时原样使用，不会被多包一层限速器，测试确定性不受影响。

**实测发现的真坑**（做 §5 recording 时撞上，不是纸上谈兵）：bioRxiv 的 DOI 本身含
`/`（如 `10.1101/2021.01.01.20248001`），而 `HttpConnector.requestRaw()`
（`connectors/base.ts`，不在本 lane 文件所有权范围，未改动）的 `{param}` 路径替换
统一走 `encodeURIComponent`，会把 doi 内部的 `/` 转义成 `%2F`。真实打
`api.biorxiv.org/details/biorxiv/10.64898%2F2026.08.11.744243` 返回 404，去掉转义打
`.../10.64898/2026.08.11.744243` 返回 200（`curl` 实测复现，见下）。**staged 阶段的
单测桩断言过 `%2F` 形态是"正确拼接"——那是从未跑过真实网络时的想当然，是典型的
"结构对了，没打过真实网络就不知道有坑"。** `getByDoi()` 改成不走 `requestRaw()`，自己
按 `/` 分段各自 `encodeURIComponent` 后拼 URL（`encodeDoiSegments()`），保留分隔符
字面 `/`；这是四个新 connector 里唯一绕开 `requestRaw()` 通用路径的方法，因此
`connector_race.test.ts` 专门加了一组测试验证它在并发下不会串位（结构上不可能，因为
全是局部变量拼 URL，没有跨请求共享状态，但按纪律要求真跑测试兜底）。

```
$ curl -s -o /dev/null -w "%{http_code}\n" "https://api.biorxiv.org/details/biorxiv/10.64898%2F2026.08.11.744243"
404
$ curl -s -o /dev/null -w "%{http_code}\n" "https://api.biorxiv.org/details/biorxiv/10.64898/2026.08.11.744243"
200
```

## 三、bioRxiv 默认集判断（V34 门禁）

**判断：进 `DEFAULT_SEARCH_SOURCES`，不进 `DEFAULT_SOURCE_EXCLUSIONS`。**

理由链：

1. `literature_source_parity.test.ts`（W5-1 ζ 的门禁）的判据很窄：只认
   `apiKeyRequired: true` 或 `status: "placeholder"` 两种合法排除理由。bioRxiv 免 key、
   API 真实可用（不是占位实现），**没有**合法的排除理由——唯一能让它"合法"缺席默认集
   的办法是把 `status` 谎报成 `"placeholder"`，那是为了让门禁变绿而放宽门禁本身，
   任务书明确不许，我也认为这么做是错的（这正是 V34 那次事故的重演：能力做好了，
   用一个假理由把它排除在默认值之外）。
2. bioRxiv 官方 API 结构性没有全文检索端点（只有"最近 N 篇"和"按 DOI 精确查"），
   如果止步于 staged 阶段的两个原语（`getRecent`/`getByDoi`），它就没法用统一检索
   通用的 `"search"`/`"getPaper"` 工具名接口，进默认集会让 `LiteratureSearcher.search()`
   对它的调用变成"打一个不存在的工具名 → 每次都 failed"——这才是真正不该进默认集的
   理由，但这理由不在门禁承认的两类合法排除里，说明**正确的修法是把能力做真，而不是
   找理由排除**。
3. 于是在 connector 层（不是 `literature/search.ts`，理由见下）组合出 `search`/
   `getPaper` 两个复合工具：`search` 拉最近 N 篇窗口（默认 200）+ 客户端 token 重叠
   打分过滤；`getPaper` 只认 DOI 形态的 id，转发到 `getByDoi`。这不是为了糊弄门禁而
   造的假通过——是一个真实、诚实的能力：caveat 里明确写清楚"查不到 ≠ 不存在，可能
   只是超出窗口"，`literature/search.ts` 的 `fetchOne()` 对 bioRxiv 的非 DOI id 同样
   跳过（不打注定失败的请求，与 crossref/openalex 同一处理）。
4. 为什么复合工具做在 connector 层而不是 `literature/search.ts`（虽然任务书把
   `search.ts` 也划进了本 lane 的文件所有权，允许在那里做）：因为其余 6 个 literature
   connector 无一例外都在**自己的类内部**实现 `search`/`getPaper`（arXiv 在类里把
   `query→search_query` 拼前缀、PubMed 在类里做 esearch→esummary 两跳编排），
   `search.ts` 对所有源走同一套 `registry.call(source, "search"/"getPaper", ...)`
   泛化调度，不为单个源特判。在 `search.ts` 里给 biorxiv 开一个 if 分支会破坏这个
   一致性（7 个源，6 个走统一调度 + 1 个特判），而在 connector 自己的类里实现
   `search`/`getPaper` 则完全遵循现有惯例，`search.ts` 只需要一处改动（`fetchOne()`
   的 DOI-only 跳过判据加一个 source 名——见下）。
5. bioRxiv 的独特价值：它是刚挂出、还没被 europepmc/openalex 二次索引的最新预印本的
   唯一来源——这类内容在其余 6 个源里查不到不是因为不存在，是因为索引滞后。进默认集
   能让统一检索覆盖到这块盲区，代价是每次检索多打一个源（一次 HTTP 请求，无 API 悬崖）。
   权衡下来利大于弊，所以判断是进默认集。

**连带影响（如实记录，不是意外）**：把 `biorxiv` 加进 `LITERATURE_SOURCES`/
`LiteratureSource` 联合类型后，`backend/src/literature/dedupe.ts` 的
`SOURCE_PRIORITY: Record<LiteratureSource, number>` 编译期报错（穷尽类型检查）——
这个文件不在本 lane 的文件所有权清单里，但不加这一行整个仓库 `typecheck` 会红，
影响所有其他 lane。做了最小必要的一行补丁（`biorxiv: 1`，与 arxiv 同档：预印本，
未经同行评审，元数据权威性低于 crossref/openalex 这类正式出版物注册方），在文件内
留了注释说明这是被迫的最小改动，不是要动 dedupe 逻辑本身。

`literature/search.ts` 的改动：`fetchOne()` 里 crossref/openalex 的"非 DOI id 跳过"
判据加了 `source === "biorxiv"`（同一条件分支多一个 source 名，不是新逻辑）。

## 六、遗留问题

1. **bioRxiv 的 `search` 只覆盖"最近 N 篇"窗口（默认 200）**，不是全文检索——这是
   API 本身的结构性限制，不是本 lane 的实现缺陷，caveat 里已写清楚，`fetchOne()`
   对非 DOI id 会跳过而不是打注定失败的请求。如果未来有用户报告"bioRxiv 明明有这篇
   但搜不到"，大概率是超出窗口，不是 bug——但目前没有一个显式的"扩大窗口"用户旋钮
   （`windowSize` 参数存在，但统一检索路径（`search.ts`）目前没有把它透传出去，
   调用方目前只能直接用 connector call 绕过统一检索来调大窗口）。
2. **ClinVar 的 AD-5①（消费方接入）比另外三个弱**：genomics/pathways 域目前没有
   专属的 CLI 子命令或 skill——四个新 connector 与 ensembl/ncbi/chembl/pubchem 等
   已有的 genomics/chemistry connector 一样，是"注册进 registry、能被 MCP/HTTP 通用
   路径调用、出现在 capabilities 里"这种接入方式，不是"有一个用户能直接敲的命令"。
   这与仓库现状一致（genomics/chemistry 域本来就没有专属 CLI），不算本 lane 引入的
   新缺口，但如实记录：如果 V26/C2 的验收标准是"用户能直接用起来"而不是"能力已注册"，
   这里还差一层。
3. **`dedupe.ts` 的一行改动**不在本 lane 文件所有权清单里（见第三节"连带影响"）——
   是把 `biorxiv` 接入 `LiteratureSource` 联合类型后编译器穷尽性检查强制要求的最小
   改动，已在文件内注释说明，未改动 dedupe 逻辑本身。如果这条改动有争议，收口时需要
   单独确认。
4. **HOST_RATE_POLICIES 目前只有一条**（`eutils.ncbi.nlm.nih.gov`）。reactome/
   string-db 官方文档提到的"批量请求建议节奏"没有编成具体 rps 数字——如果未来
   reactome/string-db 各自被第二个 connector 共用（比如接入更多 pathways 源打同一
   host），需要重新调研一次可核实的数字再补策略，不能照抄 eutils 那条。
