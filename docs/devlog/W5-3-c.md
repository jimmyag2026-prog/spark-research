# W5-3 γ · V45：「agent 运行时连接外部 MCP 扩展」这条流程

lane：`W5-3-c`（波次 W5-3，γ 条）· 分支：`feat/W5-3-c`（基于 main `a8e95f2`）

## 为什么这条 lane

「外部工具调用天然进 provenance」是本项目相对 OpenScience 的差异化点。
v0.4.0 发布时如实交代它只兑现了一半（V31/V32）。W5-2 δ 补上了机制的两半：
`mcp_client.ts` 的可选 `recordSink`（每次外部调用落一条证据图 observation）与
`orchestrator.ts` 的可选 `externalTools`（注入了就走 `createExternalToolRunner()`）。

δ 主动交代：**生产里没有任何调用方传这两个参数**。主会话追查后发现比这更彻底——
`connectExternalMcp()` 与 `discoverExternalMcpTools()` 的调用方只有 `ext verify` /
`ext add-mcp`，**agent 运行路径上一个都没有**。所以这不是「忘了传参数」，
是**没有那条流程可传**。本 lane 就是去建那条流程。

## 追查时发现的第二件事（先说，因为它改变了接线方案）

任务书给的接线目标是「agent 开跑时连接」。但 `runResearchLoop()`——那个看起来最像
"agent 开跑"的入口——**自己也没有生产调用方**：

```
$ grep -rn "runResearchLoop" backend | grep -v backend/src/agents/orchestrator.ts
（零命中）
```

CLI 的交互模式与 `chat <msg>`、HTTP 的 `POST /session`、SSE 三条路走的全是
`chat()` → `processRequest()`。**只把外部 MCP 接在 `runResearchLoop()` 上，等于把一条
新建的流程接到另一条同样没人走的流程上**——V45 会以「接了，但仍然没有生产调用方」
的形式复现它自己要解决的那个病（这个仓库已经栽过 7 次「建好了但没有生产调用方」，
`index.ts:144` 那段注释在数第 7 次）。

所以**两条路都接**：
- `processRequest()` —— 生产路径（CLI 交互 / `chat` / HTTP `/session` / SSE 都走它）
- `runResearchLoop()` —— 契约化研究循环（W3-a 交付，等它自己的接线）

`runResearchLoop()` 没有生产调用方这件事**不属于本 lane 的范围**，本 lane 不擅自给它
造一个 CLI 入口（那会动别的 lane 的足迹，也不是任务书要的）——如实记在下面的
「遗留问题」里。

## 生命周期设计

六个阶段，代码里逐条标了序号：

| 阶段 | 落点 | 说明 |
|---|---|---|
| ① 发现 | `extensions/loader.ts` `discoverInstalledMcpClients()` | **纯文件系统**：readdir + 读 extension.json/mcp.json。零子进程、零代码执行 |
| ② 连接 | `extensions/loader.ts` `ExternalMcpRuntime.attach()` | 每个扩展一个子进程，逐个隔离 |
| ③ 注册 | `ExternalToolRegistry.register()` → `createExternalToolRunner()` | 经 orchestrator 的 `runnerFor()` |
| ④ 绑定 | `attach({ recordSink: project.records() })` | V31 在生产里真的生效的那一刻 |
| ⑤ 收尾 | `attachment.close()`，在 `finally` 里 | 中途抛异常也收，不留孤儿进程 |
| ⑥ 隔离 | `attach()` 内逐扩展 try/catch + orchestrator 侧再兜一层 | 坏扩展只产生一条 `failed` 记录 |

### 模块图：为什么实现放在 `loader.ts` 而不是 `mcp_client.ts`

`loader.ts` 已经单向 import `mcp_client.ts`（`loadMcpClientConfig`）。把
`ExternalMcpRuntime` 放进 `mcp_client.ts` 会变成 `loader ⇄ mcp_client` 双向环——
`mcp_client.ts` 文件头那段注释记的就是这个仓库被环咬过一次的真实事故
（`McpToolRunner` 的 TDZ，`bun backend/src/index.ts --version` 当场炸）。教训不重演。

于是分两处：
- `mcp_client.ts` 只放**契约面**（`ExternalMcpProvider` / `ExternalMcpAttachment` 等
  纯类型 + 一个零依赖的 `emptyExternalMcpAttachment()`）。
- `loader.ts` 放实现。
- `orchestrator.ts` 只认 `ExternalMcpProvider` 这个**接口**（`import type`，编译期擦除），
  **不 import `loader.ts`**——V45 没有给 orchestrator 的模块图添加任何新的运行时边。
  谁来 `new` 那个实现是生产接线点（`index.ts` / `server/context.ts`）的事。

实测：`bun backend/src/index.ts --version` → `0.4.0`；
`bun build --compile` 后的单二进制 `--version` / `ext list` 都正常。

### 惰性策略（约束二）

三层，逐层有测试钉住：

**L0 · 构造零 I/O。** `new ExternalMcpRuntime(...)` 只记住几个选项，不 readdir、不 spawn。
所以在 `index.ts` / `server/context.ts` 里无条件构造它是安全的。
钉住它的用例：`构造 runtime 本身零 I/O：不 discover、不 connect`。

**L1 · 只有 agent 运行路径会 `attach()`。** 触发点只有两个：`processRequest()` 与
`runResearchLoop()`。`lit search` / `ext list` / `report export` / `capabilities` 这些
命令**根本不构造 `OrchestratorAgent`**（`index.ts` 的 dispatch 各走各的 `run*Command`），
所以它们连这段代码都到不了，行为与 v0.4 逐字节一致。
钉住它的用例：`不注入 externalMcp：整条流程不存在——零发现、零连接`。

**L2 · 没有 mcp_client 扩展就一个子进程都不起。** `attach()` 先做纯文件系统的发现；
`ready.length === 0` 时直接返回空句柄，**连 `ExternalToolRegistry` 都不建**
（`registry: undefined` 让 orchestrator 退回裸 `McpToolRunner`）。
没装扩展的用户为这条流程付出的全部代价 = 敲 `spark-research chat` 时多一次
`readdir(~/.spark-research/extensions)`。
钉住它的用例：`【阴性对照④】扩展目录里没有任何 mcp_client 扩展时…`。

### 发现步骤的两条纪律

1. **先看 manifest 的 kind，再决定要不要 `loadExtension()`。**
   `loadExtension()` 对 `kind ∈ {skill, platform, backend, rule}` 会 `await import(entry)`——
   那是**同 UID 的任意代码执行**。"看看有没有外部 MCP 扩展"这个动作绝不能顺手把用户装的
   别的扩展全跑一遍（与 `capabilities.ts` 头部"只读端点不该顺手执行代码"同一条纪律）。
2. **不传 `trust: true`。** TOFU 的确认动作属于用户（`ext add-mcp` / `ext verify --trust`）。
   没确认过的 mcp_client 扩展在发现阶段被 skip 并带上原因，不会被"agent 跑了一次"这个
   动作静默地顺便信任了——那等于把「启动任意本地命令」从用户手里挪到模型手里。

### 并发：一轮一张表，不共享可变状态

`OrchestratorAgent` 在 HTTP 服务下是**单实例、多 session 并发**的（`ServerContext.agent`）。
所以：

- `ExternalToolRegistry` **每次 `attach()` 新建一张**，不是全局共用。共用的话，后一轮
  register 同名扩展会顶掉前一轮的 session，前一轮收尾又会把后一轮的条目摘掉；更糟的是
  `recordSink` 是**连接时**绑定的，共用 session 等于把 B 项目的外部工具调用记进 A 项目的
  证据图。
- `attachExternalMcp()` **不改任何实例状态**（不动 `this.externalTools`、不动
  `this.toolRunner`）。这一轮的工具面通过返回的句柄逐层传参往下走
  （`runnerFor(external)` / `executeTask(..., external)`）。
- 带外部工具的 runner 按句柄记忆在一个 `WeakMap<ExternalMcpAttachment, ...>` 里：一轮里
  派多个子代理不会造多个 Hono app，不同轮各查各的。

代价：真装了外部扩展的用户，每轮 agent 运行会重起一次子进程（而不是长驻）。
这是有意的取舍——长驻要解决"一个 session 的 sink 绑给了另一个 session"这个正确性问题，
不是本 lane 能顺手做对的事。记在「遗留问题」。

### 授权：外部工具名进子代理 grants

`AgentToolBus` 的授权白名单是 `SubAgentSpec.grants`，默认表（`sub_agent.ts` 的
`SUB_AGENT_DEFAULTS`）里当然没有 `mcp:` 前缀的名字——不补的话就是「连上了但
`AgentToolBus` 一律 `not_granted` 拒绝」，等于没接。

口径（明确的取舍，不是顺手放行）：
- 能出现在这张表里的扩展，用户都已经显式 `--trust` 过它的 `mcp.json`（TOFU，指纹变了要
  重新确认）——"启动这个外部命令"这件事本身就是用户批准的。
- 工具名带 `mcp:<扩展>:<工具>` 前缀，不可能与内置工具名撞车，也不会顶替任何内置工具。
- `AgentToolBus` 的预算与审计两层照旧生效（W5-2 δ 的 `经 AgentToolBus 调用` 用例已验证）。
- **只给非只读子代理**：`review` 类 `readOnly: true`，`sub_agent.ts` 的
  `assertReadOnlyGrants()` 会对不在只读白名单里的工具名直接抛错拒绝构造。外部工具的副作用
  我们一无所知，把它当只读工具塞进去既过不了那道断言、本身也是错的判断。

### AD-2：凭据仍然只在 daemon 进程内

没有新增任何取凭据的路径。`ExternalMcpRuntime` 只把 `contextDeps.credentials`
（生产上就是 `daemon.credentials` 那一个 `CredentialStore` 实例的**引用**）原样递给
`connectExternalMcp()`，后者走的仍然是既有的
`resolveMcpChildEnv()` → `buildExtensionContext()`——「manifest 声明过 **且**
`ext grant` 批准过」的交集才可能被解析出值。本 lane 的任何数据结构里都不出现凭据值。

### AD-10：`external_tool_call` 仍在非证据集合里，一个字没动

`agents/contract.ts` 未被本 lane 修改（不在文件所有权内，也不该改）。
外部调用是**审计**不是**进展**：算进证据的话，子代理每调一次外部工具就等于"有进展"，
`NoProgressGuard` 会被静默废掉——P12 那次 `agent_run` 事故（停止条件失效、所有测试却全绿、
只有一条断言从 1 变成 2）的翻版。阴性对照③专门去撞这条。

## 接线点

| 文件 | 改了什么 |
|---|---|
| `backend/src/extensions/mcp_client.ts` | 新增契约面类型 + `emptyExternalMcpAttachment()`。既有逻辑一行未动 |
| `backend/src/extensions/loader.ts` | 新增 `discoverInstalledMcpClients()` + `ExternalMcpRuntime`。既有 `loadExtension()` 一行未动 |
| `backend/src/agents/orchestrator.ts` | `OrchestratorDeps.externalMcp`；`attachExternalMcp()` / `runnerFor()` / `externalGrantsOf()`；`processRequest()` 与 `runResearchLoop()` 各拆出一个内层方法以便 `try/finally` 包住 |
| `backend/src/index.ts` | `externalMcpFor(daemon)`，接在 `interactive()` 与 `chatOnce()` 两个构造点 |
| `backend/src/server/context.ts` | 构造 `OrchestratorAgent` 时注入 `ExternalMcpRuntime`，`pathOptions.root` 跟着 `deps.root` 走 |
| `backend/src/daemon/daemon.ts` | **没改**——见下 |

**为什么没动 `daemon.ts`**（它在本 lane 的所有权内，但没有该改的东西）：本来想在那里放一个
`daemon.externalMcpRuntime()` 工厂以体现"凭据在 daemon 里"。但 `SparkResearchDaemon` 已经
公开 `readonly credentials: CredentialStore`，两个接线点直接拿它就行；加那个方法只会给
`daemon → loader → mcp_client → contract` 添一条新的模块边，收益为零，而这个仓库刚好被
这类环咬过一次。不改。

**`server/context.ts` 的 `pathOptions.root` 必须跟着 `deps.root`**：与上面 `TaskRegistry`
同一条纪律（W4-c 在 devlog 里专门警告过）。反过来的话，`server_scenario` / `mcp_scenario`
那一大票测试会去扫**开发者本机真实的** `~/.spark-research/extensions`——那里可能真的装着
mcp_client 扩展，测试就会在开发机上 spawn 真实的外部进程。

## V31 / V32 / V45 现在完全关闭了吗？

v0.4.0 与 v0.5 的发布材料都承诺过把这件事说清楚，所以逐条说。

### V45：**关闭**

「agent 运行时连接外部 MCP 扩展」这条流程现在存在，而且有生产调用方：
`index.ts` 的 `interactive()` / `chatOnce()`、`server/context.ts` 构造的 `ServerContext.agent`
（HTTP `/session` 与 SSE 都用它）。六个阶段全部落地并有测试。

### V31（外部工具调用进证据图）：**关闭**，但有一条不对称要交代

`recordSink` 在生产路径上被绑到 `project.records()` 了，端到端用例断言的是"证据图里
查得到这条 observation"（不是"函数被调用了"）。

**不对称**：留痕只覆盖「**调用**发生了」，不覆盖「**连接**失败了」。一个扩展连不上时，
根本没有工具调用可留痕，所以那条记录只落在 session 执行日志与 `onEvent`（CLI 里是
`console.warn`），**不进证据图**。要不要给"外部扩展本轮不可用"也落一条 record，是一个
产品判断（多一类噪声 record vs 多一份可追溯性），本 lane 不擅自决定。

### V32（ToolBus 换成 external tool runner）：**没有完全关闭**

执行链路是通的：`mcp:<扩展>:<工具>` 这样的名字经 `AgentToolBus`（授权/预算/审计三层）
→ `createExternalToolRunner()` → `ExternalToolRegistry` → 子进程，全程有测试。授权那一层
也补上了（外部工具名进非只读子代理的 grants）。

**但模型看不见这些工具。** `backend/src/agents/toolbus.ts:189`：

```ts
specs(): ToolSpec[] {
  ...
  return MCP_TOOLS.filter((tool) => granted.has(tool.name)).map(...)
}
```

给 LLM 的 tools 列表是从 `MCP_TOOLS`（内置工具表）过滤出来的，`mcp:` 前缀的名字**不在
那张表里**，所以永远不会出现在 `llm.call(messages, { tools: bus.specs() })` 的 tools 参数里。
换句话说：**真实模型不会自己想到去调一个它从没被告知存在的工具**，除非任务文本里恰好
出现了那个全限定名。本 lane 的测试是用 mock LLM 直接发出那个工具名的调用，
**证明的是"发出来就能执行"，不是"模型会发出来"**——这一条必须说清楚，否则又是一次
"半兑现"。

`ExternalToolRegistry.specs()` 就是为了拼进那张列表而存在的（它自己的注释写着"供收口拼进
喂给模型的 tools 列表"），但拼接点在 `AgentToolBus.specs()` / `runSubAgent()` 里，
**这两个文件都不在本 lane 的文件所有权内**（`agents/toolbus.ts` 是 W1-a 交付，
`agents/sub_agent.ts` 是 W2-a 交付）。所以：

> **对外口径：在 `AgentToolBus.specs()` 能把外部工具拼进模型可见列表之前，
> 不许宣称「agent 能自主使用外部 MCP 工具」。可以说的是：外部 MCP 工具的调用链路
> 已经打通、每次调用都进 provenance。**

**给收口的 BACKLOG 条目**（`docs/BACKLOG.md` 不在本 lane 的文件所有权内，所以这里只把
文字备好，由收口方登记，避免多 lane 争用同一个文件）：

> **V47｜外部 MCP 工具对模型不可见（V32 的最后一块）**
> W5-3 γ 打通了外部 MCP 的完整运行时链路（发现→连接→注册→绑 sink→收尾），授权层也补上了
> （外部工具名进非只读子代理的 grants）。但 `backend/src/agents/toolbus.ts:189` 的
> `specs()` 是 `MCP_TOOLS.filter(...)`——给 LLM 的 tools 列表只从内置工具表过滤，
> `mcp:<扩展>:<工具>` 这类名字永远不会出现在其中，**模型不会自己想到去调它**。
> `ExternalToolRegistry.specs()` 就是为拼进那张列表而建的，拼接点在
> `agents/toolbus.ts` / `agents/sub_agent.ts`（W1-a / W2-a 的所有权）。
> 在这一条关掉之前，**不许**宣称「agent 能自主使用外部 MCP 工具」；可以宣称的是
> 「外部 MCP 工具的调用链路已打通，每次调用都进 provenance」。

## 遗留问题

1. **V32 的模型可见性缺口**（上面那条）——需要动 `agents/toolbus.ts` 的 `specs()`，
   排下一波。这是 V32 最后剩下的一块。
2. **`runResearchLoop()` 仍然没有生产调用方。** 本 lane 绕开它的办法是同时接
   `processRequest()`，但那条契约化研究循环本身还是"建好了没人走"。不属于本 lane 范围。
3. **子进程按轮起停，不长驻。** 一轮 agent 运行起一次、跑完收掉。长驻能省启动开销，但要
   先解决"`recordSink` 是连接时绑定的，长驻 session 会把 B 项目的调用记进 A 项目"这个
   正确性问题——不是顺手能做对的事。
4. **`ext verify` / `ext add-mcp` 与本流程各连各的。** 两边都调 `connectExternalMcp()`，
   但 `ext verify` 不带 `recordSink`（它没有也不该有 project 上下文），这是有意的，
   不是漏接。
5. **发现步骤每轮重扫一次。** `readdir` + 每个 mcp_client 扩展一次 `loadExtension()`
   （只读文件 + sha256）。没有缓存——缓存要解决失效问题（用户中途 `ext add-mcp` 了怎么办），
   而当前开销小到不值得为它引入一个可能过期的缓存。
6. **失败隔离的"可见记录"是尽力而为的。** `onEvent` 在 CLI 里落成 `console.warn`，
   在 HTTP 侧目前**没有出口**（`server/context.ts` 构造 runtime 时没传 `onEvent`）——
   orchestrator 侧的 `this.record(sessionId, "external_mcp", ...)` 执行日志两边都有，
   但 HTTP 用户不会在响应里看到"某个扩展连不上"。要不要把它做进 `/session` 的响应体，
   属于 API 形状的事，没擅自定。
