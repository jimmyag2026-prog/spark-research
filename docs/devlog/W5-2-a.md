## 〇、必须先说清楚的一句话

**这条 lane 交付的适配器从未连过一次真实的 Modal。**

- 做了：`ModalGateway` 接口、录制/回放层、`check()`、用**假 gateway** 过 W5-1 α 那套**一字未改**的契约测试、fixture 回放骨架。
- 没做：真实 Modal 录制（用户暂不提供 token），以及 `ModalGateway` 的**真实实现**（Modal SDK 客户端）。
- 因此对外材料的准确说法是：**算力抽象层与审批链已落地并有 local 实现；Modal adapter 的契约已立、真实链路未验证。**
  v0.5.0 发布时**不许**宣称「支持 Modal 远端算力」。

这句话在三处被机器盯着，不是靠自觉：`ModalComputeAdapter.description` 里写着「真实链路未验证」（有断言）；
`status().transport` 会报 `not_wired`（有断言）；`narrative_parity.test.ts` 里有一条「等真实录制」登记（有门禁）。

## 二、关键设计取舍

### 1. 为什么需要 `ModalGateway`（而不是复用 `http/fixture.ts`）

Modal SDK 走 gRPC，没有 HTTP 请求可拦，`http/fixture.ts` 那套「录响应、回放给 HttpClient」的机制套不上。
所以 adapter 里所有 SDK 调用收口到一个接口上，测试注入假实现或一份录制。这是设计 §1.1.6 点名的「CB-4 唯一的新机制」。

设计点名了六个方法（`createSandbox / getSandbox / readVolume / writeVolume / deleteVolume / listByTag`），
我**加了三个**，逐条写在接口注释里，也在这里说明（不偷偷扩契约）：

| 方法 | 为什么非有不可 |
|---|---|
| `cancelSandbox` | 契约测试「cancel 让运行中的任务终结在 cancelled」没有它过不去 |
| `readLogs(id, fromOffset)` | `RunHooks.onLog` 要求日志增量流回；同时 `collect` 要把整段日志落成 `<jobDir>/run.log` |
| `probe()` | `ComputeAdapter.check()` 要一个**不产生任何远端资源**的只读探测 |

### 2. exit code 的真源是**任务侧的标记**，不是控制面

与 local adapter 同一条纪律（`adapters/local.ts:44-56`），但这里理由更强——中间隔着一个网络：

- 沙箱入口是常量 shim（`/workspace/.spark/runner.sh`），`"$@"` 把被审批的 argv 原样接住，**不做第二次 shell 展开**；
  shim 跑完把退出码写进**持久卷**上的 `.spark/exit-code`。
- `collect()` 拿卷上的标记与控制面 `getSandbox().exitCode` **对账**：缺标记、或两边打架 → `reconcileError` 非空 → broker 标 `delivery=failed`。
  「控制面说结束了」和「任务说我跑完了、退出码是 3」是两件事，中间隔着 OOM kill、节点抢占、控制面自己的重试。**不许猜。**
- `recover()` 同样先看卷上的标记再看控制面（有一条用例故意把控制面记录改成 `running`，标记仍然压过它）。

shim 内容与 local 的那份一致，是**有意的重复**：local 的是 `private const`，而「不改 W5-1 α 的文件」是本 lane 的硬边界。

### 3. 「假 gateway」到底假在哪、真在哪

`FakeModalCloud`（测试文件内）把「远端」在本地演一遍：持久卷 = 一个目录，沙箱 = 一个子进程，
挂载点 `/workspace` 被翻译成那个目录。它足够真实到能撑起契约的每一条断言——审批链、一次性消费、
跨实例接回（状态落磁盘，新 adapter 实例能读到）、取消、收割、release、密钥不落盘。

**它不能证明的事**：Modal 真的这样回话。gRPC 的错误分类、卷的一致性语义、沙箱的状态迁移、
超时到底由谁先触发——这些一条都没验证过。所以有 §四 的那份任务书。

### 4. 约束一的落点：`status()` 每次调用都重读

```
status() = f(credentials.get("modal") 当下的值, config().environment 当下的值, 有没有 gatewayFactory)
```

没有任何编译期常量参与，也**不缓存到实例字段**——把答案缓存进构造函数就等于要求用户重启进程。
用例里用真实的 `CredentialStore`（`~/.spark-research/credentials.json`，0600，§1.1.7 说的「复用既有存储，不另起一套」）
在**同一个 adapter 实例**上跑：写 token 之前报 `needs_credential`，`store.set()` 之后立刻报 `available`。

`MODAL_GPU_CATALOG` 是**能选哪些 GPU**的清单，**不参与**可用性判定（有一条用例专门钉这件事）。
而且**这份清单未经核实**——本 lane 没 token、没对着 Modal 定价页核对过。它的作用只是 fail-closed 地收窄。

### 5. 约束二的落点：三值，不是布尔

| 情形 | `availability` | `credentialConfigured` | 为什么 |
|---|---|---|---|
| 没配 token | `needs_credential` | `false` | 能力在、审批链在，只差一把钥匙——和「openmm 没装」不是一回事 |
| 配了 token、真实 gateway 没实现 | `unavailable` | `true` | 报「可用」就是 AD-12 明令禁止的形状（本仓库刚因此修了 V34 与二进制的「技能 0 个」） |
| 两者都齐 | `available` | `true` | 才走 `gateway.probe()` |

字面量与 `capabilities/index.ts` 的 `Availability` 对齐（`available` / `needs_credential` / `unavailable`），
lane β 可以 1:1 映进 `ComputeTargetCapability`；**刻意不 import 那个文件**——算力层不该反向依赖自描述层。
`check()` 的 `detail` 里同时给出 `status` / `credentialConfigured` / `missingKeys` / `environment` / `transport` / `guidance`，
lane β 不需要自己做任何判断。

配置指引照 V19（`lab approve` 拒绝消息）与 V36（`lit add` 失败消息）的质量口径写：
缺哪些**字段名**（永远没有值）→ 写哪个文件 → 权限要求 → `config.json` 的两个键（`computeTarget` / `modalEnvironment`）
→ 明说「不需要改代码、不需要重新编译」→ **并且如实告知「本版本只填 token 还跑不起来」**。
最后这一条不好听，但不说就是误导。

### 6. 凭据纪律

- adapter **从不持有** token：`gatewayOrThrow()` 在调用时刻从 `CredentialProvider` 读出来，直接当**参数**交给工厂。
- `RecordingModalGateway` 有两条写死的 redaction：① `secretEnv` 整段换成字段名清单；
  ② 凡是流经录制器的密钥**值**，在之后任何 payload 里出现都换成 `«redacted»`——**日志是最容易漏的那条路**
  （任务自己 `printenv` 一下密钥就录进 fixture 了）。有一条用例拿 needle 钉这件事。
- 测试里的凭据一律是假值（`modal-test-token-not-real` 之类），fixture 里 grep 不到任何凭据样字符串。

## 四、**有 token 之后还需要做什么**（这就是补真实录制的任务书）

按依赖顺序。**第 1 条不做完，只填 token 是跑不起来的**——这是本交付最重要的一条如实告知。

1. **实现 `createRealModalGateway(auth: ModalAuth): ModalGateway`**（新增在 `modal_gateway.ts` 或同目录新文件）。
   好消息是 SDK 已经在仓库里：W5-1 α 已把 `"modal": "0.9.0"` 加进 devDependencies，`node_modules/modal` 在位。
   下面这张映射是**读 `node_modules/modal/dist/index.d.ts` 得出的**（不是凭记忆），但**一次都没有运行过**：

   | 我们的方法 | SDK 面（已在 `.d.ts` 中确认存在） |
   |---|---|
   | 客户端构造 | `new ModalClient({ tokenId, tokenSecret, environment })`——字段名与我们的 `ModalAuth`／credentials.json 的键**完全一致**（`ModalClientParams`，index.d.ts:8095-8099） |
   | `createSandbox` | `client.apps.fromName(name, { createIfMissing: true })` → `client.sandboxes.create(app, image, params)`；`sandbox.setTags(tags)` |
   | `getSandbox` | `client.sandboxes.fromId(sandboxId)`；终态用 `sandbox.wait()` / poll |
   | `cancelSandbox` | `sandbox.terminate()`（有 `{ wait: true }` 重载返回退出码） |
   | `readLogs` | `sandbox.stdout` / `sandbox.stderr`（`ModalReadStream`）——**注意**：我们的接口是「按 byte offset 增量拉」，SDK 是流，这里需要一层缓冲适配，是这条任务里最需要设计的一处 |

## 五、我对契约层的两点看法（**没有改，只写在这里**）

1. **孤儿表撑不住「等真实录制」这笔债。** `ALLOWED_ORPHANS` 有一条对称检查：条目一旦不再是孤儿就必须删除。
   于是 lane β 把 `compute/cli.ts` 接上 modal adapter 的那一刻，我这条登记会被**强制删除**——
   连同「等真实录制」的提醒一起消失。这正是约束三要防的失败模式。
   我的处理：在 `tests/unit/compute_modal.test.ts` 加一条门禁，**只要 fixture 里没有 `provenance:"real-modal"` 的录制，
   `narrative_parity.test.ts` 里就必须出现「等真实录制」五个字**（不限定在哪一节——注释也算，本仓库本来就有
   「曾在此登记……」的注释传统）。接线时的正确做法因此是「把债从表里挪进注释」，而不是「删掉了事」。
   **这不是对契约层的修改**，是在我自己的文件里加一道锁。

2. **`AdapterCapabilities` 没有放 `credentialConfigured` 的位置。** §2.11 的 `ComputeTargetCapability` 有这个字段，
   但那是 capabilities 层（lane β）的类型；`AdapterCapabilities`（`target.ts`，W5-1 α 所有权）没有。
   我**没有改 target.ts**，改成在 `ModalComputeAdapter` 上另开一个 `status(): ModalStatusReport`，
   并把同样的信息塞进 `check().detail`。lane β 从这两处任取其一都能填满 `ComputeTargetCapability`。
   如果收口时觉得应该把 `credentialConfigured` 提进 `AdapterCapabilities`，那是 W5-1 α 那个文件的所有者该做的决定。

## 七、遗留问题与我不确定的地方

- **最大的一条**：约束一说「启用 Modal 必须零代码改动」。我能保证的是**判定路径**纯配置——
  没有任何编译期常量参与「能不能用」，凭据/环境都在运行期读，有阴性对照钉着。
  但**传输层还不存在**，所以「填了 token 就能跑」这件事**现在不成立**。
  我选择的处理是让它**报得难看但准确**（`unavailable` + 「只填 token 还跑不起来」），而不是让它看起来像能用。
  §四·1 就是补齐这个缺口的任务书。
- 假 gateway 的沙箱是本机子进程，所以「密钥进了子进程、没落盘」这条契约断言在 modal 这边测的仍然是**本机**行为。
  真实 Modal 走的是 Secret 注入，语义未验证。
- `readLogs` 的 byte-offset 增量语义是我定的；SDK 侧是流，两者之间的适配层（§四·1 表里那一行）
  可能会反过来要求改这个接口签名。如果真要改，改的是我这两个文件，不影响契约层。
- 卷的读写在真实 Modal 上大概率要经 `sandbox.filesystem`（卷对象本身不提供直接读写 API），
  这意味着 `collect()` 在沙箱已经消失之后可能需要**另起一个短命沙箱**来读卷——
  这与设计 §2.3 「collect **不依赖沙箱还活着**」的措辞不冲突（依赖的是卷不是那个沙箱），
  但它会产生一次额外的计费启动，收口时需要有人拍板这是否可接受。
- `wallSeconds` 取自控制面的 `startedAt/finishedAt`；真实 Modal 的计费口径是否与这两个时间戳一致，未核实。
  这会直接影响 `actualCostUsd`，属于「算错钱」的类别，冒烟时必须对账。
