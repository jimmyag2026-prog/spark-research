## 1. V34 · `DEFAULT_SEARCH_SOURCES` 没跟上 arxiv/pubmed 的接通

### 症状（外部验收实测）

- `lit search --sources arxiv` ✅ 能用
- `capabilities --json` ✅ 报 arxiv 可用
- `lit add 1706.03762` ❌ 「未找到」

因为 `lit add` 不带 `--sources` 时走 `DEFAULT_SEARCH_SOURCES`，而那张表还是 P2 时代的
`[openalex, crossref, europepmc, semanticscholar]`。W3-d 早就把 arxiv / pubmed 接通了，
归一化也接了，**只有这张默认值表没跟着改**。

### 改法（两半）

**前一半**（`backend/src/literature/models.ts`）：默认集补上 `arxiv` / `pubmed`，变成 6 个源。

**后一半才是重点**——加门禁。AD-12 核的是「arxiv 在不在连接器注册表」，
W3-d 之后它一直是绿的；它核不了「默认值有没有包含它」。所以新增：

- `DEFAULT_SOURCE_EXCLUSIONS`（models.ts）：一张**带理由**的显式排除表；
- `tests/unit/literature_source_parity.test.ts`（新建，8 条断言）：
  **已实装的源必须在默认集里，或在排除表里带理由。**

门禁的真源选择是关键：**以 `ConnectorRegistry` 的 literature 域清单为准，不以
`LITERATURE_SOURCES` 常量为准**。后者本身就是一份手写副本，拿它当真源等于自证自明——
「注册表里加了源、两张手写表都没跟上」这一类恰恰抓不到，而 V34 就是这个形状。

排除**不是**随手写个理由就行。门禁只承认两类合法排除：
`apiKeyRequired: true`（放进默认集只会让每次检索多一行必然 skipped 的噪音）、
`status: "placeholder"`（占位实现，调用必然失败）。
**一个免 key、状态 available 的源没有合法排除理由，只能进默认集。**
这条是防「把排除表退化成万能豁免表」的闩——少了它，V34 可以靠「把 arxiv 写进排除表」
糊过去，门禁照样绿（见阴性对照 2）。

跑门禁时它当场抓出了两个我原本没想到的源：**cnki / wanfang 在注册表里但不在
`LiteratureSource` 联合类型里**。它们是占位实现（无公开 API），属合法排除，
于是也补进了排除表并各自写明理由。`DefaultSourceExclusion.source` 因此故意是 `string`
而不是 `LiteratureSource`——占位源本来就不该能被 `--sources` 选中，但它确实在注册表里，
门禁要求它给出理由。

### 实机核验（真实网络，非 fixture）

```
$ SPARK_RESEARCH_DATA_DIR=/tmp/spark-smoke-itEA bun backend/src/index.ts lit add 1706.03762
✅ 已入库（项目 smoke）
  [c954ea7a] Attention Is All You Need
  来源 arxiv
  证据图 record: de909d42-d35c-43c1-a518-5995d61daddd
```

外部验收报「未找到」的那条命令，**不带 `--sources`**，现在直接成功。

## 2. V35 · 长任务在 CLI 层完全不可见（外部验收头号卡点）

### 症状

`lit read --all` 跑 8 分钟零输出、无进度、无 job id、断开后无法查状态——
验收者只能杀进程再用 `lit list` 反推它其实在工作。

### 判断：这不是缺功能，是**能力不对等**

`backend/src/server/tasks.ts` 早就有完整的 `TaskRegistry`：状态机、progress 事件、
只增事件日志，W4-c（V11）还做了落盘与进程重启后 hydrate。MCP 层有 `task_status`。
**三条入口里只有 CLI 没接。** 所以做法是**接线，不是新建**——另起一套 CLI 专用的进度机制
就等于把 V34 的形状（同一件事两份实现，改一处漏一处）再犯一遍。

### 改法

新建 `backend/src/cli/progress.ts`（本 lane 独占的新文件）：

- `runCliTask()`：把一段长活丢进 `TaskRegistry.start()`，订阅事件、渲染进度行、等 settle，
  返回**类型化的返回值** + 任务快照；
- `renderTaskEvent()` / `renderTaskSnapshot()` / `renderTaskList()`：渲染逻辑独立导出，
  测试直接核实渲染结果，不靠抓 stdout 猜；
- `cliTaskRegistry(root)`：落盘到 `<项目>/tasks/`，与 server 用同一套目录布局。

`backend/src/literature/cli.ts` 接三个点：

1. **`lit read --all`** → 一个 `lit-read` 任务，逐篇发 progress；
2. **`lit review`** → 一个 `lit-review` 任务，两阶段（写草稿 / citation-integrity）发 note；
3. **新增 `lit tasks [<id>] [--json] [--limit N]`** —— 这是第三条腿：
   进度看得见还不够，**断开之后要查得回来**。快照由 V11 的落盘机制留在磁盘上，
   新进程用同一个 root 建 registry 就 hydrate 回来，所以这条命令只读、不重跑任何东西。

`backend/src/literature/reading.ts`：`GenerateCardOptions` 加 `onProgress`，
`generateMany()` 逐篇回调。**成功和失败两条路径都发**——只在成功时发进度，
等于让一串失败在终端上看起来和「卡住了」一模一样，那正是 V35 要修的症状。

### 两个 CLI 专属的决定（写在 progress.ts 文件头，没有改 tasks.ts）

- **默认不设超时**（`timeoutMs: 0`）。TaskRegistry 默认 600s 是给 HTTP/MCP 兜底的——
  那边没有真人守着。CLI 不一样：真人在终端前，Ctrl-C 随时可用，而且本改动**之前**
  `lit read --all` 压根没有任何超时。套上 600s 会让一个 30 篇的合法长跑在第 10 分钟
  被我们自己掐断——**为了让长任务可见而引入一条新的失败路径，方向是反的**。
  挂死本身由进度行的 `+Xs` 时间戳暴露（卡住时最后一行时间戳不动），这正是 V35 要的效果。
- **`--json` 模式静音进度**。进度行走 `out`，而 `--json` 的 stdout 必须是一段可解析 JSON；
  把进度混进去等于把一个可用性修复变成一个解析 bug。有一条测试专门锁这件事。

- 单篇 `lit read <id>` **不套任务**：一步的活套任务只会多两行噪音。

### 输出形态

```
⏳ 任务 4f0c1a2b 已启动（精读卡 ×3）· 断开后用 spark-research lit tasks 4f0c1a2b 查状态
   +0.4s [1/3] ✅ Highly accurate protein structure prediction with AlphaFold
   +1.2s [2/3] ✅ Accurate prediction of protein structures and interactions
   +2.0s [3/3] ❌ Paper 3 on protein structure prediction
✅ 任务 4f0c1a2b 完成（用时 2.0s）
```

## 3. V36 · 失败消息不给下一步

样板是 `lab approve` 的 V19 拒绝消息（`backend/src/lab/cli.ts:229`）：它把
「为什么拒绝 → 这是什么机制 → 真人该怎么做 → 自动化该怎么做」四件事一次说全。

`lit add` 旧消息只有一行「未能在 a/b/c 中找到标识符 'X'」——说了**哪里错了**，
没说**该试什么**。外部验收的原话是「靠猜绕过去」。

新增 `classifyIdentifier()` + `addNotFoundGuidance()`（`literature/cli.ts`，均导出可单测）。
关键是内容**由本次实际发生的事推出来**，不是一段万能套话：

1. **标识符形态 → 该由哪个源解析 → 那个源这次在不在检索集里。**
   这一条正是 V34 的复发面（arXiv id 配一组不含 arxiv 的源），命中时直接给出可粘贴的命令。
2. **skipped 与 failed 分开说**，而且 skipped 内部还要再分：
   「缺凭据」（去配凭据，这些源本次根本没发出请求）与「不认这个 id 形态」
   （换源，不是「查过了没有」）——**两种处理动作完全不同，合成一句话等于把判断推回给用户**。
3. **兜底那条永远在**：不确定标识符就 `lit search "<关键词>" --add`。

`lit tasks <未知 id>` 的失败消息也按同一条纪律写了下一步。

实机输出：

```

## 4. V38 · BibTeX 导出把「Last F」形态的作者名解析错

Europe PMC / PubMed 归一化出来的作者名是 `"Jumper J"` / `"Varadi MG"`（**姓在前、名缩写在后**），
而 OpenAlex / CrossRef 给的是 `"John Jumper"`（姓在后）。
`authorSurname()` 旧实现无条件取最后一段当姓 → `"Jumper J"` 的姓被解析成 `"j"`：

- 引用 key 变成 `j2021highly` 而不是 `jumper2021highly`（外部验收发现的那条）；
- **更隐蔽的一条**：`dedupe.ts` 的跨源姓氏比对也跟着错位——同一篇论文，
  openalex 侧姓 `jumper`、europepmc 侧姓 `j`，两边对不上。

判据：最后一段**只由 1~3 个大写字母（可带点）组成**就判为名缩写，姓取它前面的部分。
**只认大写是关键**——`"Jan van der Berg"` 的 `Berg`、`"Xu Li"` 的 `Li` 都含小写字母，
不会被误判；真正的缩写（`J` / `JA` / `J.A.` / `MG`）一定全大写。
一个过于激进的判据会把 `"Jan van der Berg"` 的姓改错，那是把一个引用 key bug 换成另一个，
所以测试里「**不能误伤**」那组比「修好了」那组更长。

`models.ts` 导出 `isInitialsToken()` 供 `export.ts` 的 `toCSLName()` 复用——
两处各写一份正则就是 V34 那类问题的翻版。

## 5. V39 · `lit review --help` 直接执行而不是显示帮助

新增 `LIT_SUBCOMMAND_HELP`（9 条子命令各一段：用法行 + 做什么 + 相关的下一步命令），
在 `switch` **之前**统一拦截。放 switch 前而不是各 case 里，是因为放进 case 会漏掉
新加的子命令——本次加 `tasks` 就会当场踩到。

**写这条门时自己踩了一次 V39 本身的形状**：第一版按 `flags.help === true || flags.h === true`
判，结果 `lit export -h` 照样真的执行了——`-h` 是单横线，`parseFlags` 的
`if (!arg.startsWith("--"))` 把它当**位置参数**收走了，`flags.h` 从来不会被置上。
更糟的是那条测试当时没给 `root`，于是 `-h` 打到了**真实工作区**的文献库上（只读，无写入）。
改成直接扫 `rest.includes("--help") || rest.includes("-h")`，并给所有帮助类用例
一个隔离的空临时 root（真执行必然退 1，只有「打完帮助就返回」才可能退 0）。

实机核验：

```
$ bun backend/src/index.ts lit review --help
用法: spark-research lit review [--topic 主题] [--out 文件] [--no-judge] [--session id]

  由已有精读卡生成综述草稿，并逐条核验引用（citation-integrity）。
  ...
  前置: 至少一张精读卡（lit read <paper-id> 或 lit read --all）

## 9. 越界说明（一处，最小编辑）

## 11. 遗留问题 / 不确定的地方

1. **`semanticscholar` 现在需要 key（E-4 之后 `apiKeyRequired: true`），却留在默认集里。**
   我**没有**把它移出去：它已经在默认集里多个版本，无 key 时会被优雅判成 skipped（不是 failed），
   移出去属于行为变更而非 V34 的范围。但按 §1 的排除规则，它**有资格**被排除——
   这是一个悬着的口径问题，留给收口拍板。门禁不会因此变红（规则只禁止排除「免 key 且 available」的源）。
2. **默认 6 源的延迟**：`lit search` / novelty check 的默认扇出增加约 50%。
   没有实测过延迟数字（要打真实网络），只是结构性推断。
3. **`lit tasks` 是项目内作用域**：跨项目的任务查不到（快照落在 `<项目>/tasks/`）。
   外部验收的场景（同一项目内断开后重连）够用，但如果将来要「列出所有项目的任务」，
   需要一个 workspace 级 registry——本 lane 没做。
4. **`lit read --all` 的进度粒度是「篇」**，一篇内部的两次 LLM 重试不可见。
   要更细就得在 `reading.ts` 的重试循环里发 note，我判断收益不抵噪音，没做。
5. **`lit search` 没接任务/进度。** 理由见 §8.3：它是并发的，不是那条 8 分钟路径；
   而且给它接进度必须动 `search.ts`（W5-2 γ 的文件）。
6. **BACKLOG 未勾**：`docs/BACKLOG.md` 的 V34/V35/V36/V38/V39 五行仍是待办状态。
   BACKLOG 不在本 lane 的文件所有权内，留给收口统一勾。
