## 2. 关键决策

### D2-1 · 超时默认值定成多少，以及为什么

`backend/src/config/` 是只读的（P9 已收口的用户配置面），我确认过 `CONFIG_SETTINGS` 里没有任何一条对应「HTTP/LLM/kernel/task 超时」——唯一相关的是 `mcpTimeoutMs`（300s，语义是「MCP 工具**同步等待**长任务的上限」，命中就退化成返回任务句柄，是完全不同的语义，不能复用）。按任务书指示，走「env 覆盖 + 常量默认」这条已有先例（对照的是 `backend/src/lab/wet_backend.ts` 的 `DEFAULT_TIMEOUT_MS = 120_000`，同样是「config 面没有入口，模块自己兜一个默认值」的模式）：

| 层 | 默认值 | env 覆盖 | 理由 |
|---|---|---|---|
| HTTP（`NativeHttp`） | 30s | `SPARK_HTTP_TIMEOUT_MS` | connector 单次请求正常在数百 ms～几秒内完成；30s 够覆盖冷启动+重试，又不会让一次挂起的上游拖垮整条检索链路太久 |
| LLM（`LLMRouter`） | 120s | `SPARK_LLM_TIMEOUT_MS` | 对照 wet_backend 的子进程超时惯例；长文本生成需要更大余量 |
| kernel（`PythonKernel`/`KernelManager`） | 120s | `SPARK_KERNEL_TIMEOUT_MS` | 同上，与 wet_backend 保持同一量级认知（都是「一次外部执行整体等多久算挂」） |
| server 长任务（`TaskRegistry`） | 600s（10 分钟） | `SPARK_TASK_TIMEOUT_MS` | 这层包的是**任务体整个生命周期**（可能内含多轮 review 修正循环、多次 connector/LLM 调用），比单次工具调用需要更大余量；比 `mcpTimeoutMs`（300s）宽，因为语义不同——那个只是「要不要退化成句柄」的阈值，这个是「真的判定为挂死」的最后兜底 |

四层都做成**可选参数**：调用方不传就吃默认值，已有调用点不需要改一行代码——这是任务书对 D-2 明确要求的「向后兼容」（尤其 HTTP 层：lane D-a 同期在改 `connectors/base.ts`，绝不能要求它同步跟进传参）。

### D2-2 · 超时错误如何做到「可见、结构化、能分辨超时 vs 上游报错」

- **HTTP**：`HttpTimeoutError extends Error`，专门的错误类型，`timeout: true` 字段，`instanceof` 可判。与「上游返回了 4xx/5xx」结构上不同——后者是一个合法的 `HttpResponse`（`ok:false` 但有 `status`），前者是请求根本没落地。
- **LLM**：**没有改 `LlmResponse` 的类型形状**（任务书明确要求不做 AD-12 那种类型层根治）。区分靠 `content` 文案前缀：超时是 `"[error] timeout: ..."`，网络层其它失败是 `"[error] network: ..."`，HTTP 状态码错误是 `"[error] HTTP <status>"`，无 key 是 `"[error] No API key configured..."`——四种文案互不重叠，调用方靠字符串就能分类而不需要猜。
- **kernel**：`KernelTimeoutError extends Error`，`timeout: true`；`KernelResult` 新增可选的 `timedOut?: boolean` 字段（这是 `KernelResult`，不是 `LlmResponse`，不受「不要改类型形状」的约束）。
- **server task**：`TaskTimeoutError extends Error`，`timeout: true`；`TaskSnapshot.error` 从 `{message}` 扩成 `{message, timeout?: boolean}`（可选字段，向后兼容——没有超时的失败路径这个字段就是 `undefined`，见 `tests/unit/tasks.test.ts` 里「任务体自己抛错」那条用例）。

四层用同一个模式（`Xxx extends Error` + `readonly timeout = true`），刻意统一但没有抽成一个共享基类——四个模块分属四个不同的所有权边界（HTTP 是我改的，但被 lane D-a 的 connectors 消费；kernel 被 orchestrator 消费；task 被 routes 消费），提前抽象一个跨层的 `TimeoutError` 基类会在还不确定下游怎么用之前引入一个新的公共契约，这个决定应该留给看得到全局消费方的人（主会话/P11），不该由本 lane 单方面定。

### D3 · kernel stderr 死锁的真正机制，以及为什么不能只加大缓冲区

`python_kernel.py::execute()` 内部把 `sys.stdout`/`sys.stderr` 重定向进 `io.StringIO()`，用户代码打的 `print(..., file=sys.stderr)` 会被这层重定向捕获，通过 stdout 上的 JSON 协议正常传回——**这部分从来没坏过**。真正的坑是 OS 级的 fd 2：任何绕过这层 Python 级重定向、直接写原始文件描述符的输出（`os.write(2, ...)`、native 扩展库的底层日志、子进程继承 fd 后自己写的东西）会落到 `Bun.spawn` 那个真实的 `proc.stderr` pipe 上，而 `manager.ts` 从来没有读过它。管道内核缓冲区（常见 64KB）写满后，子进程会永久阻塞在 `write(2)` 系统调用里——不是「丢数据」，是**整个 Python 解释器卡死**，包括它正在处理的那次 `execute()` 请求，从而拖死整个 kernel。

修法是照抄 `backend/src/lab/wet_backend.ts:206` 附近「持续消费 stream」的思路（我**只读**了 wet_backend.ts，没有改它——那是 lane D-d 的文件），但做了一处必要的适配：wet_backend 跑的是**一次性子进程**（跑完就退出），用 `new Response(proc.stderr).text()` 等它跑完一把读全量就行；`PythonKernel` 是**持久 REPL 进程**（跨多次 `execute()` 调用不退出），不能等它退出才读，必须是一个从 `ensureProc()` 起就持续跑的 `for await (const chunk of proc.stderr)` 循环，和 `startReader()`（读 stdout 协议）并列。只保留最后 8KB 作为诊断尾部（`stderrTail`），排空动作本身不需要也不该无界持有内存——这个尾部会拼进「进程意外退出但没有响应」这条错误消息里，比之前纯粹一句 `"process exited without response"` 更好排查。

**验收**：`tests/unit/kernels_manager.test.ts` 第一个 describe block，向 kernel 打 2MB `os.write(2, ...)`（比要求的 1MB 门槛更高留了余量），断言这次调用不靠踩超时兜底就能正常返回，且之后同一个 kernel 还能继续正常 `execute`。这个测试我做过反向验证：临时把 `startStderrDrain` 去掉重跑，测试会挂死（不是失败，是真的卡住直到 15s 超时兜底触发才失败）——证明这条测试确实在验证这个机制,不是摆设。

### D5 · dispose(id) 与超时杀进程的交互坑（一个容易漏掉的正确性问题）

D-2 的 kernel 超时实现是「杀掉挂起的子进程，同一个 `PythonKernel` 对象透明地在下次 `execute()` 时重新拉起一个干净进程」。这里有个容易踩的坑：原来的 `proc.exited.then(() => { this.closed = true; ... })` 是不管三七二十一，只要进程退出就把整个 `PythonKernel` 标记成**永久关闭**——如果直接照抄这段逻辑，超时杀进程 → 触发 `exited` → `closed=true` → 下一次 `execute()` 直接抛 `"process exited"`，等于超时之后这个 kernel 就废了,达不到「隔离这一次挂起的执行,kernel 本身还能继续用」的要求。

修法：`ensureProc()` 里用局部变量 `proc` 闭包住这次 spawn 的进程,`exited` 回调里判断 `if (this.proc !== proc) return`——只有「退出的还是当前正在用的这个进程」才标记永久关闭;如果 `this.proc` 已经被 `killAndReset()` 换成了别的(或者 `null` 之后又被新 `execute()` 重新 spawn 了),旧进程稍后异步落地的 `exited` 就不该反过来影响新进程的状态。这个改动没在原始任务书里被点名,是实现 D-2 kernel 超时时顺带发现并修的——不修的话 D-2 的「隔离」验收测试(超时后同一个 kernel 还能继续用)会直接失败。

`KernelManager.dispose(kernelId?)`:不传参数=全量销毁(保留给进程退出用,`backend/src/index.ts` 里三处 `daemon.kernelManager.dispose()` 调用不用改,继续拿到原来的语义);传 id=只删那一个。`orchestrator.ts` code task 的 `finally` 块从 `dispose()` 改成 `dispose(kernelId)`。

**验收**:`tests/unit/kernels_manager.test.ts` 的 `KernelManager.dispose(kernelId)` describe block(按 id 销毁只影响那一个、不传参数仍全量销毁、对不存在的 id 是安全空操作),以及任务书明确要求的 `tests/concurrency/kernel_isolation.test.ts`(该目录之前不存在,是本 lane 新建的)——直接对 `KernelManager` 交错操作 + 经由 `OrchestratorAgent` 两个并发 session 交错跑 code task,断言早结束的 session 不会把还在跑的另一个 session 的 kernel 带走。**做过反向验证**:临时把 `orchestrator.ts` 的 `dispose(kernelId)` 改回 `dispose()` 重跑这个测试,会挂死在 20s 测试超时上(不是失败,是真的等到测试框架自己判超时)——证明这条测试确实在验证这个修复,不是摆设。

### D4(战术版)· 四处 llm.call() 调用点

任务书点名的是 290/318/412 三处(`plan()` / `executeTask` 的 `analysis` 分支 / `summarize()`)。实际读代码时发现 `executeTask` 的 `subagent` 分支(原 366 行)是**同一个模式的第四处**——同样不检查 `res.ok`,同样会把路由层的错误文案当 subagent 产出放行。这处不在委托范围内点名,但和已点名的 `analysis` 分支是同一段代码复制出来的两份(几乎逐行一样),只修三处、放过第四处说不通,所以一并修了。四处改动逻辑都很轻(只加一个 `if (!res.ok)` 分支),没有引入新的抽象,符合"战术版"的范围约束。

四处具体怎么处理:

- **`plan()`**:失败时记一条 `plan-llm-failed` 到执行日志(可见,不是静默),落到既有的 `defaultPlan()` 兜底(单个 `analysis` 任务)。选择"降级到 defaultPlan 而不是直接抛异常中断整个 `processRequest`"是因为:(a) `defaultPlan()` 这个兜底路径本来就存在,只是之前是"误打误撞"地生效(错误文案巧合解析不出方括号数组才落到这条路径,换一种错误格式,比如文案里恰好带一对方括号,就会把错误文本当计划解析)——现在是显式检查、显式选择这条路径,不是新增行为,是把一个隐性正确的行为变成显性正确;(b) 抛异常中断整个会话是一个更大的行为变更,超出"战术版"授权,而且 `processRequest`/`chat()` 目前没有为"规划阶段整体失败"设计对外契约,仓促加一个会牵连 `OrchestrationResult` 的类型形状。
- **`analysis` / `subagent` 分支**:检查 `res.ok`,失败时 `ExecutionOutcome.ok=false`,`output` 里显式标注 `[llm call failed, not a model output]` 前缀(区分「LLM 调用本身失败」与「模型认真产出了一段看起来奇怪的内容」)。
- **`summarize()`**:这是最要紧的一处——它的返回值就是用户最终看到的 `OrchestrationResult.summary`,也是 reviewer 读的正文。失败时**不把 `res.content` 塞进 summary**(错误文本本身可能带有误导性描述,不该出现在面向用户的产出里,这是任务书原话"summary 不得包含错误文本"的字面要求),也不静默吞掉——具体错误进执行日志(`summarize-llm-failed`)供排查,summary 只留一句固定的、无法被误读成模型产出的结构化失败说明:"[orchestrator] LLM 调用失败,未能生成结果摘要(这是调用失败,不是模型产出)。请检查 LLM 配置(API key / 网络)后重试。"

`plan()`/`summarize()` 签名都加了 `sessionId` 参数(用于记执行日志),两处调用点(`processRequest` 里的初次调用 + review 修正循环里的重复调用)同步更新。

**没有改** `LlmResponse` 的类型形状(按任务书要求,类型层根治 AD-12 留给 P11)。`coexplore()` 方法内部用的是 `ideation/coexplore.ts` 里的 `CoExploreSession`,那个模块不在本 lane 所有权范围内,没有动。

## 4. 意外发现

1. **D-5 与 D-2 的交互 bug**(见 §2-D5):如果只照抄"杀进程"却不修 `exited` 回调的判断条件,会做出一个「超时后 kernel 就报废」的错误实现,表面上看起来完成了「杀掉挂起的执行」,但同时破坏了「隔离该次执行、kernel 本身继续可用」这条同样在任务书里的要求。这个坑不写测试根本发现不了(必须显式验证"超时之后同一个 kernel 还能再用一次")——`tests/unit/kernels_manager.test.ts` 里专门有一条用例覆盖这个。
2. **`executeTask` 的 `subagent` 分支是 D-4 未点名的第四处同款漏洞**,已一并修,见 §2-D4。
3. **`python_kernel.py` 用 `eval()`/`exec()` 分流来决定要不要产出 `result`**——多行代码(比如带 `import`)只能走 `exec()`,没有返回值(`result` 恒为 `None`)。这不是本 lane 引入的行为,是既有实现;写 `tests/unit/kernels_manager.test.ts` 的 stderr 灌入用例时踩了一次坑(最初断言 flood 代码的 `result`,后来发现这类多行代码本来就不产出 `result`,改成只断言 `status`)。跟本次改动无关,记一笔供后续参考。
4. **确认了 `TaskRegistry` 的超时兜底不会造成"孤儿 promise"的未处理拒绝**:`withTimeout()` 无论超时与否都对内层 `promise` 挂了 `.then(onFulfilled, onRejected)`,所以任务体最终(哪怕在超时之后很久)才 resolve/reject,也不会变成 unhandled rejection——只是这个结果不再被任何人消费。这是"任务体本身没有真正被取消,只是调用方不再等它"的固有限制,四层里 HTTP/LLM 靠 `AbortController` 真正中止了底层请求,kernel 靠杀进程真正中止了子进程,只有 server task 这一层做不到"真正取消"(`run()` 是一个不透明的 async 函数,没有通用的取消协议)——这个限制在任务书的描述里本来就隐含("即便任务体自己没有任何超时逻辑也要兜底"暗示了兜底层管不到任务体内部的取消)。

## 5. 建议主会话复查的点

1. **`tests/concurrency/` 目录是本 lane 新建的**,不在原始"文件所有权"清单里显式列出(清单只列了 `tests/timeout/**` 为新建目录)——但 D-5 的验收标准原文明确写了 `tests/concurrency/kernel_isolation.test.ts` 这个路径,判断是"任务书里的具体验收要求"优先于"文件所有权清单的字面覆盖范围",所以建了。如果这与其它 lane(比如同样在处理并发场景的 lane)有冲突,请复查。
2. **LLM 超时/错误文案是拼在 `content` 字符串里做区分的,没有改 `LlmResponse` 类型**——如果 P11 做 AD-12(类型层根治 `ok=false ⇒ content=""`)时要保留"能分辨超时 vs 上游报错"这个能力,现在的字符串前缀约定(`"[error] timeout:"` / `"[error] network:"` / `"[error] HTTP <status>"`)值得迁移成一个结构化字段,而不是继续解析字符串前缀。
3. **四层的超时错误类型(`HttpTimeoutError`/`KernelTimeoutError`/`TaskTimeoutError`)没有抽成共享基类**,是刻意留白(见 §2-D2-2 的理由),如果后续要统一处理"任何一层的超时",可能需要一个跨模块的 `isTimeoutError()` 判断函数或者共同接口——现在四个类都有 `readonly timeout = true` 字段,鸭子类型上是兼容的,但没有显式声明。
4. **`SPARK_HTTP_TIMEOUT_MS`/`SPARK_LLM_TIMEOUT_MS`/`SPARK_KERNEL_TIMEOUT_MS`/`SPARK_TASK_TIMEOUT_MS` 四个新 env var 没有进 `backend/src/config/` 的 `CONFIG_SETTINGS` 表**(那个文件对本 lane 只读)——意味着 `spark-research config list` 里看不到这四项,用户要调超时只能自己设环境变量,文档(`docs/EXTENDING.md` 第六节)目前也不知道它们存在。如果这四个超时值需要变成正式的用户配置项,需要 config 层的所有者(P9 相关 lane 或主会话)补一版。
5. **V3(poll 的进程 start-time 交叉核验)完全没有处理**,原因见 §2-V3——如果这段逻辑确实在本 lane 的某个所有权文件里(我没搜到),需要另行指出具体位置。
6. **本 worktree 没有 `.venv`**,所有 Python kernel 相关测试用的是系统 `python3`(3.9.6,仅 stdlib)。我核对过这些测试**没有被跳过**(见 §0),但没有在带 `.venv`/`numpy`/`pandas` 的环境里跑过——如果 `_jsonable()` 那条 numpy/pandas 分支相关的行为在超时/respawn 场景下有什么特殊之处,本次没有覆盖到,建议主会话在带 venv 的环境上补跑一次 `tests/unit/kernels_manager.test.ts` + `tests/timeout/kernel.test.ts` + `tests/concurrency/kernel_isolation.test.ts` 确认。
