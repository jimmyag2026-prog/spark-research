### R-c-1：单价表与成本核算

**关键设计决定**：不改 `openai_compat.ts`（不属于本 lane 所有权，R-a 的文件）。
`Usage.costUsd` 在 adapter 层继续保持诚实的 `null`——成本核算发生在
`BudgetLedger.record()` 里：拿到一次 `Usage`（可能带 token 数但 `costUsd:null`）后，
账本查 `registry.priceFor(provider, model)` 把 token 换算成美元。`LlmResponse` 本身
不被这一层污染，事后核算与响应本体分离。

非官方页直读"，不冒充成官方数字。

**保守估计（如实标注在 `note` 字段里）**：
- DeepSeek 是峰谷分时计价（谷值=峰值一半），`ModelPricing` 只能存一个数——取**峰值价**，
  因为 `BudgetLedger` 是用来防超支的，宁可把成本算高也不要因为谷值时段的低价而低估
  真实花费、致使预算上限迟迟不触发。
- Qwen-max 只存了 <32K 上下文的基础档价；32K-128K/128K-256K 有阶梯加价（$2.4/$12、
  $3/$15），本表不按上下文分档，长上下文请求的真实成本会被低估——已知简化，记在
  `note` 里。
- OpenRouter 是转发层，价格因模型而异，本表只收 `DEFAULT_MODEL` 这一个已核实条目，
  其余任何经 openrouter 请求的模型查不到价格（`priceFor` 返回 `null`），不用
  DEFAULT_MODEL 的价格去顶替。

**核价时发现的模型清单陈旧问题**（如实记录，**未修复**——`PROVIDER_MODELS` 在
`router.ts`，不属于本 lane 所有权，需要主会话或后续 lane 处理）：
- `PROVIDER_MODELS.kimi = ["kimi-k2", "moonshot-v1-32k", "moonshot-v1-8k"]`——
  WebSearch 核实这三个模型名已于 **2026-08-31 被 Moonshot 官方全部退役**（现在请求
  404）。给一个已经 404 的模型名编报价毫无意义，`PRICING.kimi` 因此改为对**当前在售**
  的 `kimi-k2.6`/`kimi-k3` 定价（`providerForModel()` 的启发式兜底 `low.includes("kimi")`
  会让任何带 "kimi" 字样的模型名路由到 kimi provider，所以这两个名字实际可达，只是不在
  `PROVIDER_MODELS.kimi` 那个静态清单里）。`PROVIDER_MODELS.qwen` 里的 `"qwen3"` 同样
  不是一个可计价的具体 SKU（DashScope 拆成 qwen3-235b-a22b/qwen3-32b/... 一堆不同尺寸
  型号），本表对 `"qwen3"` 不收录，如实返回 `null`。

**config 可覆盖**：新增 `CONFIG_SETTINGS.llmPricingOverridesJson`（env
`SPARK_LLM_PRICING_JSON`），JSON 格式 `{"<provider>:<model>": {inputPerMillionUsd,
outputPerMillionUsd}}`，覆盖优先于内置表。**格式错误时整体回退到内置表**（不是部分
生效）：`parsePricingOverridesJson()` 把具体错误原因暴露出来，`priceFor()` 本身不抛
异常。

**`BudgetLedger`**（`llm/budget.ts`）：累计 calls/inputTokens/outputTokens/wallMs/
knownCostUsd/unknownCostCalls，支持 `maxCalls`/`maxInputTokens`/`maxOutputTokens`/
`maxTotalTokens`/`maxWallMs`/`maxCostUsd` 六个上限。接口设计考虑了「一个预算句柄跨
多次调用传递」（v0.3 方案原文）：`record()` 是有状态方法，调用方创建一次账本、
之后每次 LLM 调用后 `record()` 一次；`child()` 派生子账本用于 P12 的「每个子代理
有自己的预算，同时受一个全局上限约束」场景——子账本的 `record()` 会转发给父账本，
父账本能看到全局汇总，拦住「每个子代理都没超，但加起来超了」的情况。

**成本判定的诚实性**：只要有一次调用的成本未知（`usageUnavailable` 或查不到单价），
聚合 `costUsd` 就整体报 `null`——不能诚实说出一个确定总数。但 `maxCostUsd` 的**超限
判定**用 `knownCostUsd`（已知部分之和，是真实总花费的下界）：已知部分单独就已经超过
上限时，无论未知部分多少，"总花费 ≥ 已知部分 > 上限"这条逻辑推论必然成立，判定为
确定超限不需要等未知部分也查清楚；反过来已知部分没超但存在未知调用时，两个方向的
判定（"确定超"/"确定没超"）都不成立，所以都不报，只暴露 `unknownCostCalls` 让调用方
自己决定。

`assertWithinLimits()` 超限时抛 `BudgetExceededError`；`isExceeded()` 供 P12 的
`stopReason:"budget"` 判定使用（明确区别于 `done`，v0.4 方案 P12 行 191 的要求）。
`record()` 本身**不**抛异常、不强制停机——账本是观测组件，是否硬停由调用方
（未来的 ToolBus/子代理循环）决定。

### R-c-2：provider 能力位进 `capabilities --json`

`backend/src/capabilities/index.ts` 新增 `providers: ProviderCapabilityInfo[]` 与
`localEndpoint: LocalEndpointCapability` 两段。

**`providers` 段形状**（每个已实装 provider 一条）：

```ts
interface ProviderCapabilityInfo {
  id: string;
  models: readonly string[];
  configured: boolean;                    // 如实：没配 key 就是 false
  capabilities: { toolCalling: boolean; jsonMode: boolean; streaming: boolean; usageReported: boolean };
}
```

**实现里的一个坑**：不能直接对真实 `process.env` 调用 `router.capabilitiesFor(model)`
去探测每个 provider——`LLMRouter.resolve()` 在 preferred provider 没配 key 时会
**隐式回退**到任何一个已配置的 provider，用真实 env 探测一个没配 key 的 provider 时，
拿到的可能是别的 provider 的能力位（配对错了，且不会报错，是最隐蔽的一种漂移）。
解法：给每个 provider 探测时构造一个**只把这一个 provider 的 key 设成占位值**的临时
`new LLMRouter({ [envVar]: "probe-placeholder-key" })`——`capabilities()` 是纯本地
计算不发网络请求，占位 key 拿到的能力位是真实的；`configured` 单独用 `CONFIG_SETTINGS`
的 `resolveSetting(envVar, options)`（真实 env/config）查，两件事分开查不会互相污染。
新增测试直接验证了这条（`每个 provider 的能力位与直接探测该 provider 一致——不会因为
隐式回退串味`）。

**一致性测试（AD-12 要求）**：`tests/unit/capabilities.test.ts` 新增
`正向：provider 集合与真实实现的 implementedProviders() 一致`，断言
`manifest.providers.map(id)` 恒等于 `implementedProviders()`。

**本地端点可见性**（主会话中断恢复时特别提醒的一条）：`local/<model>` 前缀路由
不进 `Provider` 联合类型（R-a 的设计决定，理由见 P11-a.md），所以不能塞进
`providers` 数组（那会破坏上面那条一致性不变式）。处理方式：单独开一段
`localEndpoint`，取法与上面同一招——构造
`new LLMRouter({ SPARK_LOCAL_LLM_BASE_URL: "http://localhost:0/probe-placeholder" })`
探测 `local/probe-model`，拿到的是 `router.ts` 里 `localCapabilities()` 的真实返回值
（本文件不手写重复一份，避免两处漂移）；`configured` 查 `SPARK_LOCAL_LLM_BASE_URL`
是否已设置（key 允许为空，不计入这个判定）。这样外部 agent 从 `capabilities --json`
就能自描述地发现"可以接本地模型"这条路，不必先知道 `local/` 前缀约定。

人看的表格（`capabilities/cli.ts`）加了对应的「LLM Provider」段，含本地端点一行。

### R-c-3：消化 R-a 留下的配置缺口

**`effect` 里额外记的一个真实缺陷**（非本 lane制造，但既然写新条目就如实标出）：
`config.json` 里存的 secret 值目前**不会**被 `router.ts` 读取——`router.ts` 的
`LLMRouter` 直接读 `process.env`，而 `applyConfigEnvDefaults()` 显式跳过 `secret`
项（AD-2：凭据永不桥接进 env）。也就是说 `spark-research config set OPENAI_API_KEY
...` 会让 `config list` 显示"已设置"，但**实际调用仍然需要 `export
OPENAI_API_KEY=...`**。这个缺口对 `KIMI_API_KEY`/`OPENROUTER_API_KEY` 同样存在
（早于本 lane），本 lane 只是在新增条目的 `effect` 里如实写清楚，没有改动这两个
既有条目的文案（不属于"新增"）。

**`defaultProvider.allowed` 同步**：R-a 已把 openai/deepseek/qwen 填进 `ADAPTERS`，
之前 `allowed` 还是 `["kimi","openrouter"]`——widened 到
`["kimi","openrouter","openai","deepseek","qwen"]`，并在
`tests/unit/config.test.ts` 加一条一致性测试断言集合恒等于 `implementedProviders()`。
