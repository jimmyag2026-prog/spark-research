## 一、V72 · 中文无作者论文的 BibTeX key 嵌入原始汉字

### 1.1 问题回顾

BibTeX key 生成在 `backend/src/literature/export.ts`。此前有一条 `E-5` 决定
（v0.3 阶段）把 `keepAsciiAndHan()` 改成保留 `\p{Script=Han}`，让中文作者/标题不再
退化成 `anon`/`untitled`——但外部验收 R1-T3 指出，key 里嵌原始汉字会破坏部分下游
BibTeX 工具链（`\cite{张伟2022深度学习...}` 这类 key 不是所有 BibTeX 实现都能安全
处理）。BACKLOG V72 的裁定：key 应转拼音，或者降级为 `anon<year>`；key 只允许
`[A-Za-z0-9_-]`——本质是覆盖 E-5 的决定。

### 1.2 修法

`backend/src/literature/export.ts`：把 `keepAsciiAndHan()` 改名 `asciiOnly()`，
正则从 `[^a-z0-9\p{Script=Han}]` 改回 `[^a-z0-9]`（退回 E-5 之前、pre-Unicode 的
实现）。之所以直接砍掉而不是转拼音：中文姓名/标题的拼音转换需要一张可靠的
汉字→拼音映射表（多音字、姓名异读都要查表校正），"不引入 npm 依赖"这条硬约束下
没有零依赖的可靠实现——任务书本身也点名允许这个选择（"没有零依赖的可靠拼音表就
不做拼音"）。

结果：
- 作者姓氏含非 ASCII、砍完为空 → `anon`（既有兜底，未改）。
- 标题首词含非 ASCII、砍完为空 → `untitled`（既有兜底，未改）。
- 中英混合姓氏（如 `"Wei 张#Zhang!"` → 姓段 `"张 zhang"`）→ 砍掉汉字/符号/空格后
  剩 `"zhang"`（非空）就直接用，不整体降级成 `anon`——这是比"一见非 ASCII 就整体
  降级"更贴近原始实现、且逐字节兼容英文回归的选择。
- 冲突仍靠既有的 `assignBibtexKeys` 的 `a/b/c` 后缀区分（多篇中文文献同样退化成
  `anon<year>untitled` 时不会互相覆盖）。
- 英文作者（含 V38 的「Last F」形态）的 key 逐字节不变：ASCII 输入本来就不含被
  正则砍掉的字符，`asciiOnly` 与旧的 `keepAsciiAndHan` 在纯 ASCII 输入上行为
  完全一致。
- `toBibTeX`/`toCSLJSON` 输出的其余字段（`title`/`author`/`journal` 等）仍然原样
  保留汉字——只有 key 本身被 ASCII 化，不影响可读性与可核对性。

### 1.3 阴性对照

| 改法 | 断言 | 真跑结果 |
|---|---|---|

## 二、V71 · `review findings` 不显示刚落的 citation-integrity soft finding

### 2.1 复现与定位

BACKLOG V71 的假设是"查询过滤面或类型映射有洞"。实测下来**这个假设不成立**：

1. 直接用 `FindingsStore.reviewTarget()` 写入一条 `checker=citation-integrity,
   severity=soft` 的 finding，再用 `FindingsStore.list({project})` /
   `list({project, open:true})` 查——两种都能看到，`severity` 原样是 `soft`。
2. 走完整 CLI 路径（`runReviewCommand(["findings", "--project", ...])`）同样能
   看到，输出里 `soft`/`citation-integrity` 都在，没有被升级成 `hard` 或漏显示。
3. 已有测试 `tests/unit/reviewer_findings_wiring.test.ts`（8/8 绿，未改动）本来
   就覆盖了"`ReviewerAgent.review()` 接了 `FindingsWiringConfig` 时，
   citation-integrity 的 soft finding（`citation_conflict`）能正确 upsert 并被
   `list()` 查到"这条路径——如果查询侧真有过滤/类型映射的洞，这个既有测试应该
   已经红了，但它一直是绿的。

真正的洞在**写入侧**：`backend/src/literature/cli.ts` 的 `lit review` 命令
（生成综述草稿 → 跑 `citationIntegrity()` → 逐条 finding 在 `check.findings`
里）只把结果**汇总计数**写进一条 `records.create({ type: "observation", ... })`
（"N 条 hard finding，M 条 soft finding"），**从未调用**
`project.findings().reviewTarget(...)` 把逐条 finding upsert 进 `findings.db`。
`review findings` 读的是 `findings.db`（`findings_store.ts` 顶部注释：故意不与
`records.ts` 共表共库），这张库里从来没有这些 citation-integrity finding 的行，
自然"看不到"——不是查询条件挡住了它，是它压根没被写进去过。

同样的模式还出现在 `backend/src/server/routes/literature.ts`（HTTP 侧的
citation-integrity 检查，也只算 `hard`/`soft` 计数、不落 `findings.db`），但那个
文件不在本 lane 的诊断范围内，这里只记一笔，不展开。

`agents/orchestrator.ts` 的 `reviewSession()`（chat 会话的审阅路径）倒是正确接了
`FindingsWiringConfig`（`project.findings()` + `project.slug`），但它从不传
`CitationCheckConfig`——`ReviewerAgent.checkCitations()` 在没配置时直接
`{ran:false, findings:[]}`，所以这条路径压根不会产生 citation-integrity finding，
更谈不上"写了但查不到"。

### 2.2 交付

`backend/src/reviewer/findings_store.ts` / `backend/src/reviewer/cli.ts`
**未作改动**——如实交代：诊断结论是这两个文件本身没有 bug，本 lane 的允许footprint
里没有可以合理落的"修复"。改的是 `backend/src/literature/cli.ts`（任务书禁止
本 lane 改动），诊断 + ≤5 行 diff 见下，交收口按任务书接上：

```diff
--- a/backend/src/literature/cli.ts
+++ b/backend/src/literature/cli.ts
@@ 写完 citationReviewRecord 之后、`if (hard.length > 0)` 之前插入：
+        project.findings().reviewTarget({
+          project: project.slug,
+          target: { kind: "record", id: draft.recordId ?? draft.artifactId ?? "" },
+          checker: CITATION_RULE,
+          hits: check.findings.map((f, i) => ({
+            severity: f.severity, fingerprint: `${CITATION_RULE}-${i}`, evidence: f.message,
+          })),
+        });
```

这条 diff 只是把"洞"补上、让 `review findings` 能看到，**不是**生产质量的最终
实现——真正接上去时至少还要做两件事（留给 B-2/收口判断怎么做更合适）：
1. fingerprint 不该用数组下标（同一份草稿改一个字重新生成，下标会错位，复核闭环
   会失效）——`agent.ts` 里已经有一套按 finding 的 `detail` 字段算稳定 fingerprint
   的 `citationFindingIdentity()`/`computeFingerprint()`，理想情况是把它提出来给
   两处（`agent.ts` 生产路径 + `literature/cli.ts` 的 `lit review` 路径）共用，
   而不是各写一份。
2. `target.kind` 用 `"record"` 还是 `"artifact"`：`draft.recordId` 与
   `draft.artifactId` 何时非空取决于 `ReviewDraftGenerator` 的构造参数（见
   `literature/cli.ts` 现有注释），需要 B-2 确认这条命令的实际调用形态。

### 2.3 新增测试

`tests/unit/v71_review_findings_citation.test.ts`（新文件，3 个测试，均用真实
`citationIntegrity()` 产出的 soft finding，不是手写的 stub）：

1. `reviewTarget()` 写入之后，`review findings`（不带 `--open`）默认就能看到，
   输出含 `soft`/`citation-integrity`，且不含 `hard`（severity 没被显示层升级）。
2. `--open` 口径下同样可见（soft finding 首次出现就是 `open`，属于"仍需要关注"）。
3. 阴性对照（见下）：只算出 finding、不调用 `reviewTarget()`（复刻
   `literature/cli.ts` 今天的真实行为）→ `review findings` 看不到，输出是
   "还没有任何 finding"。

`Finding` 语义未改：soft 全程仍是 `soft`（测试里有显式 `not.toContain("hard")` 断言
钉住这一点）。

### 2.4 阴性对照（真跑）

把测试 1（"落库之后可见"）里的 `seed.reviewTarget({...})` 调用删掉（只保留
`new FindingsStore(dbPath)` 然后直接 `close()`，等价于"算出了 finding 但没写
findings.db"，也就是 `literature/cli.ts` 今天的真实行为）：


`review findings` 看不到 soft finding 的完整解释，不需要在查询侧改任何东西。
