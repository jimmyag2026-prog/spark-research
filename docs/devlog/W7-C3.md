# W7-C3 · 词表外试剂原文进编译产物（BACKLOG V60）

> 分支 `feat/W7-C3-reagent`（`33d8223` 起）。跨层改动（编译器 + CLI 审批渲染 + 前端审批弹窗），纪律 13：全套跑了 e2e。

## 问题

词表（`backend/src/lab/protocol.ts` 的 `REAGENT_PATTERNS`，只有 5 类）外的试剂，编译产物里变成
`未识别试剂#step-1`（`opentrons_protocol.ts:215/241`）。v0.5 只止住了「两种未知试剂塌缩到同一
reservoir 孔」，用户写的原文没有进产物——人在 `lab approve` 时看不到自己写的是「硝酸」，批的
hash 里那两个字已经不存在（AD-6 署名审批失去对象）。

## 交付与设计取舍

1. **解析器**（`protocol.ts`）：新增 `ProtocolStep.unrecognizedReagentText?: string`。
   只在这一步的动作是 `prepareReagent`/`addSample`（唯二会往
   `opentrons_protocol.ts` 的 `reservoir.wellFor(name)` 送试剂名的动作；`serialDilute`
   的试剂显示走既有的 `"stock"` 兜底，BACKLOG 原句只点名了 215/241 两行，这次不动）
   且 `extractReagents()` 一个词表内试剂都没匹配上时才尝试抠原文，用新函数
   `extractReagentRawText()`：从原句里**减掉**已经确定识别出的结构（体积数字、命中这条
   ACTION_RULE 的最长动作关键词），剩下的残留当候选原文；抠不出非空残留、或残留恰好是
   `GENERIC_LIQUIDS`（样品/PBS/缓冲液…，本就不是受管化学品）时不猜，字段留空
   ——同一条纪律：宁可漏、不瞎报。
   **刻意不放进 `ProtocolStep.params.reagents`**（`ReagentSpec[]`）：那个数组是
   `safety.ts` 四条规则的输入源，塞一条没有 `reagentId` 的假条目会改变它们的迭代对象。
   原文单独放在 `ProtocolStep` 上，`safety.ts` **一行未改**。

2. **编译产物**（`opentrons_protocol.ts`）：新增 `CompiledStep.unrecognizedReagent?: { rawText?: string }`。
   占位符**仍然按 `step.id` 唯一化**（既有的防塌缩断言必须继续成立）——
   `unrecognizedReagentLabel(step)` 生成 `未识别试剂#${step.id}（原文：${raw}）`，原文只是
   追加在唯一 key 后面给人看，不参与唯一性判定；两步就算原文写的是同一个词，`step.id`
   不同仍然分到两个不同的 reservoir 孔（保守，不猜「这两步说的是不是同一种试剂」）。
   `summary` 字段额外追加「（词表外，安全规则未覆盖）」。

3. **CLI**（`cli.ts` 的 `printView`，仅渲染）：遍历 `view.compiledSteps`，对
   `unrecognizedReagent` 非空的步骤打印一行 `⚠️ <stepId>：词表外，安全规则未覆盖（原文：…）`。

4. **前端审批弹窗**（`frontend/workspace/src/components/bottom.tsx` 的 `ApprovalDialog`）：
   步骤列表里追加一个 `Badge tone="rejected"`「词表外，安全规则未覆盖」+ 原文文本。
   `frontend/workspace/src/lib/types.ts` 的 `WetExperiment.compiledSteps` 只加了一个可选字段
   `unrecognizedReagent?: { rawText?: string }`。

5. **HTTP 透传**：**未改 `backend/src/server/*`，也不需要改**——`backend/src/server/routes/lab.ts`
   的 `viewJson(view)` 是把 `WetExperimentView`（减去 `record`）整个 spread 进 JSON 响应，
   `compiledSteps: CompiledStep[]` 走的是直通序列化，不是手工挑字段的映射。新字段
   `unrecognizedReagent` 因此自动出现在 HTTP 响应里，前端读到的是真实运行时数据。
   实跑核对：`grep -n "compiledSteps" backend/src/server/routes/lab.ts` 只匹配到
   `viewJson(view)` 的调用点，没有任何手工字段挑选逻辑。

6. **`unconsumedWarnings` 措辞去重**（交付第 4 点）：`scanUnconsumedSignals` 里「窄范围验收 A」
   那条告警原文是「编译产物里只会出现占位符」——这句话现在不准确了（占位符会带原文）。
   改成「编译产物会把你写的原文保留下来（未识别试剂 + 原文），但 chemical_compatibility 与
   concentration_limit 两条规则依旧完全看不见它」。**告警本身没删**，只改了已经不准确的那半句。

## 与任务书的偏差 / 如实交代

- **`serialDilute` 的 `stockName` 未接原文**：BACKLOG V60 原句只点名了
  `opentrons_protocol.ts:215/241`（prepareReagent/addSample），`serialDilute` 的
  `reagentNamesOf(step)[0] ?? "stock"`（line ~293）不在这两行里，本次未动。如果后续要覆盖
  梯度稀释的词表外原液，需要同一套 `unrecognizedReagentText` 机制补一处。
- **续句（continuation）里的词表外试剂未接原文**：例如「加入10µL硝酸，其中再补加柠檬酸」
  第二个子句通过 `mergeReagents(previous, reagents)` 合并进上一步，若 `reagents.length===0`，
  当前实现不会往 `previous.unrecognizedReagentText` 补写原文（只有顶层新建的步骤才会尝试抠）。
  范围收窄的理由：续句原文归属更容易与前一步的原文混在一起，风险高、单测覆盖不到就不该做，
  这次没做，留给下一轮。
- **`extractReagentRawText` 是启发式残留提取，不是分词器**：对结构简单的从句效果好（本次单测
  与 e2e 的例子都验证过），复杂从句（例如同一子句里出现多个非结构化修饰语）可能抠出带噪声的
  残留或抠不出任何东西——后一种情况直接不显示原文，不会显示错误的原文，符合「宁可漏不瞎猜」。
- **HTTP 层没有额外测试**：`server_lab.test.ts` 全绿（85 pass 在 lab 四个测试文件里），但没有专门
  为 `unrecognizedReagent` 透传写新的 HTTP 层单测——这次靠「viewJson 是直通序列化」的代码阅读
  加已有测试的整体绿，判断风险可接受；如果收口需要更硬的证据，我可以补一条。
