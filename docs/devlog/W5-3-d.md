## 为什么这条 lane

来自第二次零上下文外部验收的三条发现（`docs/BACKLOG.md` S10/S11/S12）。最要紧的是
S11：验收者想回答「它到底进没进证据图」，试了 `report stats`（不含 artifact）、

最后只能自己开 sqlite 查 `records.db`。§三·补.8 定了做法：**扩 `report`，不新建命名空间**
——`report` CLI 已有 `export`/`stats` 且已在 `index.ts` 接线，`RecordStore` 已有
`list`/`get`/`edgesOf`/`listEdges`（只读），扩它一次消掉三处枢纽争用。

## S11：`report records` + `report show`

`backend/src/report/cli.ts`：

- `report records [--type <t>] [--limit N] [--json]`：列出证据图里的原始 record，
  **不按类型特判**——`RecordStore.list()`/`count()` 本来就跨全部 9 种类型（含
  `artifact`、`agent_run`），不加白名单就是全量，天然含 artifact，不需要为它单独开口。
  - `--type` 未知类型：可见错误 + 列出合法值，不是静默空列表。
  - `--limit` 非正整数：可见错误。
  - 空结果、超出 limit 都有人类可读提示（「共 N 条 / 本次显示前 M 条」）。
  - 人类输出末尾提示 `report show <recordId>` 作为下一步。
- `report show <recordId> [--json]`：单条详情（类型/证据标签/创建时间/标题/artifactId/
  origin/metadata/content）+ `edgesOf()` 给出的入边出边。
  - id 不存在：**可见失败**（`err()` + `return 1`），带下一步指引（`report records`），
    绝不返回一个「看起来正常」的空壳。这是最容易在收口时被「顺手改成更友好」而
    悄悄退化成静默失败的地方——阴性对照 #3 就是照这个场景写的。

两个命令都走 `RecordStore` 现成的只读 API，**没有新写路径**，`backend/src/project/records.ts`
一行没动。

`index.ts` 不需要改——`case "report"` 早就是 `runReportCommand(process.argv.slice(3))`
这种「整段转发」的形状，子命令名在 `report/cli.ts` 内部分发，新增子命令不触碰枢纽文件。
`tests/unit/narrative_parity.test.ts` 同理不需要动（那是 skill 入口清单，不是 CLI 子命令
清单）。

### 展示层通用性（与 lane α 的约定）

`report records`/`report show` 完全按 `ResearchRecord` 的既有字段渲染
（`type`/`evidence`/`title`/`artifactId`/`origin`/`metadata`/`content`/`edgesOf()`），
**没有为任何 `kind` 字面量（含算力相关的）写特判**。检查过 α 承诺导出的
`COMPUTE_OUTPUT_OBSERVATION_KIND`（`backend/src/compute/` 下 grep 无匹配，
`git log` 也没有——α 这条 lane 在本次收工时还没交付），所以现在没有可 import 的常量，
也没有必要 import：因为渲染本来就是通用的，不依赖任何具体 `kind`。若收口时发现某个
算力产出类型需要更友好的展示（比如按 `metadata.kind` 分组、特殊格式化数值），
**常量在 α 的 devlog 承诺位置** `backend/src/compute/`（预期是 `contract.ts` 或
`cli.ts` 同级），届时从那里 import，不在这里另写一份字符串。

## S10：附录 A「证据索引」空表

`backend/src/report/export.ts`：

诊断——附录 A 的 `recordIds` 只收「正文（问题/思路/实验/结论/待验证）点名引用过」的
record（每次 `ref(track(id))` 才会进这个 Set）。项目里存在但**从未被叙事引用**的
record（没被任何 idea 链接的论文、没被任何结论引用的精读卡、没被结论证据链引用的
artifact）永远不会出现在附录 A——即便正文统计行写着「论文 5 · 精读卡 5」。这不是
bug（附录 A 的语义本来就是"正文引用回链索引"，不是全量目录），但空表 + 非零统计
会让读者以为报告坏了。

判断：**填不对**（会改变"附录 A = 引用索引"这个已被测试钉死的语义——
`report_export.test.ts` 里「每条证据都能拿 record id 回到 records.db」等测试依赖
`recordIds` 就是叙事引用集合，不是全量）；改成**空的时候说明**：

1. 无论表是否为空，都先加一行说明本表的范围，并指向 `report records`/`report show`
   去看全量。
2. `recordIds.size === 0` 时不再渲染空的 `| ... |` 表头+空表体，改成一句明确的话：
   「正文暂无点名引用的证据——上面各节还没有 record 落进叙事里，不代表证据图是空的。」

2. **`rev` 编号跳变无解释** —— 确认属实，**没有信心给出"修"的方案**，如实说：
   - 机制：`backend/src/compute/job_store.ts:170` 每次 `update()`（不带
     `expectedRev` 时）或 CAS 成功都会 `rev: record.rev + 1`；`broker.ts` 在
     plan→approve→run→collect 的每一步都各自调用一次 `update`/`replacePlan`
     （如 `broker.ts:154,167,234` 等），所以一条 job 的生命周期天然产生多次 rev
     递增，中间态不对外可见。
   - 这不是 bug（CAS 语义本身要求每次写入 rev+1），是"UX 该不该解释"的产品判断——
     可能的两条路：(a) `printJob`/`report show` 里加一句"rev 只是并发写入计数器，
     不代表操作步数"；(b) 保持沉默但在 `compute --help` 里提一句。**我不确定哪个
     对**，没有把握写死，留给收口判断，也不在我的文件所有权内（`job_store.ts`/
     `broker.ts` 都是 α 的 `compute/**`）。

3. **local 任务收割完 `resource=active` 悬挂，从不提示 `release`** —— 确认属实，
   定位到精确行：
   - 文件：`backend/src/compute/cli.ts`
   - `run`/`approve`/`status` 三个 case（552/599/643/661 行附近）都在人类输出分支
     调用了 `out(\`下一步：${nextActionFor(job)}\`)`；`nextActionFor()`
     （457-475 行）本身已经正确处理「`delivery === "complete"` 且
     `resource !== "closed"` → 建议 `release`」这条分支。
   - 但 **`case "collect"`（688-705 行）的人类输出分支从没调用 `nextActionFor`**
     ——只有 `printJob(job, out)`，没有"下一步"提示。这就是悬挂的根因：collect
     成功后 delivery 变 complete，但用户看不到"现在该 release 了"的提示，直到
     `resource=active` 的槽位越攒越多。
   - 建议替换文本（688-705 行内，`printJob(job, out);` 之后加一行）：
     ```

     ```
   - `--json` 分支（695-697 行）同理可以加 `next: nextActionFor(job)` 字段，
     与其它 case 的 json 形状对齐。

4. **`chem depict` 人类输出不给文件路径** —— 确认属实，定位到精确行：

5. **`--gpu` 在 local 上的报错「（可选：无）」措辞怪，不给下一步** —— 确认属实，
