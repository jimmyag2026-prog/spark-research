## 交付（四项，全部完成）

新建 `backend/src/llm/providers/anthropic.ts`：`AnthropicAdapter implements ProviderAdapter`，
不复用 `openai_compat.ts`——Anthropic 的 Messages API 与 OpenAI 的 `/chat/completions` 在
七个维度上不同，硬套只会把两边都写脏：

| 维度 | OpenAI | Anthropic（本文件的实现） |
|---|---|---|
| 端点 | `/chat/completions` | `${baseUrl}/v1/messages` |
| 鉴权 | `Authorization: Bearer` | `x-api-key` + `anthropic-version: 2023-06-01` |
| system 提示 | messages 里的 `role:"system"` | 顶层 `system` 参数，从 messages 里抽出、多条用 `\n\n` 拼接 |
| 工具定义 | `tools[].function.parameters` | `tools[].input_schema` |
| 工具调用（非流式） | `message.tool_calls[].function.arguments`（字符串，要 `JSON.parse`） | `content[]` 里的 `{type:"tool_use", id, name, input}`（`input` **已是对象**，不解析） |
| 工具调用（流式） | `delta.tool_calls[].function.arguments` 字符串分片 | `content_block_delta` 的 `input_json_delta.partial_json` 字符串分片（**这条反而跟 OpenAI 同构**：都要拼接后 `JSON.parse`） |
| 工具结果 | `role:"tool"` + `tool_call_id` | `role:"user"` 消息，content 里放 `{type:"tool_result", tool_use_id, content}`；**连续多条 tool 消息合并成一个 user 消息里的多个 tool_result 块**（Anthropic API 要求，P12 的 ToolBus 并发调用多个工具时会产生这种形状） |
| 必填参数 | — | `max_tokens` 必填（`CallOptions` 没有对应字段，见下面「已知缺口」） |
| 流式 | 单一 `chat.completion.chunk` 事件 | 多种命名事件：`message_start` / `content_block_start` / `content_block_delta`（`text_delta` / `input_json_delta`）/ `content_block_stop` / `message_delta`（带 `stop_reason` 与 `usage.output_tokens`）/ `message_stop` / 中途 `error` |

### R-b-1：tool calling

- 请求侧：`ToolSpec[]` → `tools[].input_schema`（不是 `function.parameters`）；`toolChoice`：
  `"auto"` → `{type:"auto"}`，`"none"` → `{type:"none"}`，`{name}` → `{type:"tool", name}`。
- 响应侧：`content[]` 过滤 `type==="tool_use"` 的块 → `ToolCall[]`，`input` 直接用（已是对象）；
  但**仍然校验**它确实是个非 null、非数组的对象——校验失败显式 `kind:"parse"` 失败，
  不静默塞 `{}`（`parseToolUseBlocks()`，阴性对照①已验证这条纪律真被测试钉住）。
- assistant 历史消息带 `toolCalls` 时，编码成 `content: [{type:"text",...}?, {type:"tool_use", id, name, input}]`；
  `tool` 角色消息编码成 `role:"user"` 的 `tool_result` 块，**连续的 tool 消息合并成一个 user 消息**
  （见 `toAnthropicRequest()` 里的 `pendingToolResults` 累积逻辑）。

### R-b-2：流式（`options.onDelta`）

新增 `AnthropicAdapter.consumeStream()`：手写最小 SSE 解析器，只解析 `data:` 行（载荷自带
`type` 字段，与开头 `event:` 行冗余，不需要单独跟踪 `event:` 行）：

- `content_block_delta` 里 `delta.type==="text_delta"` → 逐块回调 `onDelta`，同时累积成最终 `content`。
- `delta.type==="input_json_delta"` 的 `partial_json` 按 `index`（`content_block_start`/`content_block_delta`
  共享的块索引）分片累积，流结束后交给 **独立的** `parseStreamToolCalls()`（与非流式的
  `parseToolUseBlocks()` 是两个函数——线格式不同：流式是要拼接再 `JSON.parse` 的文本片段，
  非流式是响应体里已经解析好的对象）解析，失败同样显式 `kind:"parse"`。
- usage：`message_start` 事件的 `message.usage.input_tokens` + `message_delta` 事件的
  `usage.output_tokens` 合并成最终 usage；两者都没见到时 `usageUnavailable:true`，**不填 0 冒充**。
- **中途 `error` 事件**（Anthropic 常见失败模式：连接已建立、流已开始后才报错，比如
  过载）显式返回失败，**不把已经攒到的半截 content 当成功返回**——这是本 lane 在
  `openai_compat.ts` 的模式之外新加的一条防线（OpenAI 兼容协议的流式错误通常在 HTTP
  层面就能拦到，Anthropic 的 `error` 事件是流内错误，位置不同）。

### R-b-3：`response_format`——如实不支持，不假装

**选择：`capabilities().jsonMode` 如实报 `false`，且 `call()` 在发起网络请求之前显式检查
`options.responseFormat === "json_object"`，命中则直接返回 `kind:"unsupported"` 的失败**（阴性
对照测试验证了这一点：`requests` 数组长度为 0，即失败发生在打网络之前）。

**为什么不选「预填 assistant 消息」的偏方**：这是社区常见的绕过手法（在 messages 末尾加一条
`{role:"assistant", content:"{"}` 之类的前缀，诱导模型续写出 JSON），但代价没有被充分验证过就
不该对外承诺：
1. 与 tool calling 组合时行为不明确——如果同时传了 `tools`，模型应该吐 `tool_use` 块还是
   续写文本？两者语义冲突，之前没人验证过 Anthropic 在这种组合下的真实行为。
2. 与流式组合时，"预填前缀"要在 `onDelta` 回调里对调用方隐藏还是暴露？如果隐藏，
   `consumeStream()` 就要在返回前对 `content` 做字符串前缀操作，这类隐式改写正是
   `redactSecrets`/AD-13 想根治的那类"响应被中间层悄悄动过手脚"的问题。
3. 就算做了，也只是"引导"模型更可能吐 JSON，**不是**协议级保证——跟 OpenAI 的
   `response_format:{type:"json_object"}`（服务端强制校验）在可靠性上不是一个量级，
   如果 capabilities 报 `true`，调用方会误以为拿到了同等强度的保证。

**结论**：宁可显式报 `false` + 显式拒绝，把"这条路目前没走通"钉死成一个可测试的事实，
也不做一个只有部分组合下有效、且把责任转嫁给调用方去发现的半成品。真要支持，需要先
对"prefill × tools"「prefill × streaming」两组组合做实测（要打真实网络，不满足本 lane
的测试纪律），留给后续 lane。

### R-b-4：能力位

```ts
capabilities(_model: string): ProviderCapabilities {
  return { toolCalling: true, jsonMode: false, streaming: true, usageReported: true };
}
```

与模型名无关（Anthropic 全系列 Messages API 形状一致，不像 OpenRouter 转发不同上游模型
那样需要按模型区分）。

## 最终能力位矩阵

| provider | toolCalling | jsonMode | streaming | usageReported |
|---|---|---|---|---|
| anthropic（`AnthropicAdapter`，任意 claude-* 模型） | **true** | **false** | **true** | **true** |

`jsonMode: false` 的理由见上面 R-b-3 的完整取舍记录；这不是"还没做"，是"评估过偏方的
代价后决定不做，如实报告"。

## 失败处理 / AD-13 / 凭据脱敏

- 唯一的失败构造入口是 `providers/types.ts` 的 `failure()`，本文件所有失败分支都走它，
  保证 `ok:false ⇒ content===""` 且 `error` 必填（AD-13）。
- HTTP 非 2xx：解析 Anthropic 的错误体 `{type:"error", error:{type, message}}`；
  `classifyHttpError()` 把状态码/错误类型映射到 `kind`：401/403/`authentication_error`/
  `permission_error` → `auth`（不可重试）；429/`rate_limit_error` → `rate_limit`（可重试）；
  529（Anthropic 专用的 overloaded 状态码）/`overloaded_error`/其余 5xx → `upstream`（可重试）；
  其余 4xx → `upstream`（不可重试）。
- 网络层失败（fetch 本身 reject）：`AbortError` → `timeout`；其余 → `upstream`（可重试）。
- 错误消息统一过 `redactSecrets()`（`llm/types.ts` 导出，只读引用，未修改该文件）再截断
  拼进 `message`——已用一条专门测试验证 API key 不会出现在 HTTP 500 错误体回显里。

## 已知缺口 / 遗留记录

1. **`max_tokens` 硬编码为 `DEFAULT_MAX_TOKENS = 4096`**：`CallOptions`
   （`backend/src/llm/types.ts`，不在本 lane 文件所有权范围内）没有 `maxTokens` 字段，而
   Anthropic 的 `max_tokens` 是必填参数。当前用一个保守常量；如果后续要做成可配置，需要在
   `CallOptions` 上加 `maxTokens?: number`，那是 types.ts 的改动，本 lane 没有做（对齐
   R-a devlog 里"本地端点配置项不在 CONFIG_SETTINGS"同一类"跨所有权边界的缺口如实记录"）。
2. **`jsonMode` 报 `false`，未实现"预填 assistant 消息"的 JSON 模式偏方**：理由见 R-b-3，
   这是评估后的决定，不是遗漏。若后续要做，需要先用真实网络验证"prefill × tools"与
   "prefill × streaming"两组组合的实际行为（违反本 lane 的测试纪律，留给能打真实网络做
   集成验证的阶段）。
3. **孤儿模块登记（`ALLOWED_ORPHANS`）**：`anthropic.ts` 目前没有生产调用方（`router.ts` 的
   `ADAPTERS` 接线由主会话在 P11 收口时统一做，见下面「给主会话的接线说明」），触发了
   `tests/unit/narrative_parity.test.ts` 的孤儿模块门禁。主会话已授权本 lane 在该文件里
   **只追加一条登记**（未改动任何断言逻辑）：

   ```ts
   "backend/src/llm/providers/anthropic.ts":
     "**等接线**：v0.4 P11 lane R-b 交付的 Anthropic 适配器。router.ts 的 ADAPTERS 注册由主会话在 " +
     "P11 收口时统一接线（R-b/R-c 都不持有 router.ts，避免两条 lane 在同一文件上撞车）。" +
     "接线完成后必须删除本条——门禁的『多余登记必须删除』对称检查会强制这件事。",
   ```

   **主会话接线时必须删除这一条**——门禁本身有「在册条目若已不再是孤儿，要求把它从表里
   移除」的反向检查（同一测试文件里紧邻 `ALLOWED_ORPHANS` 的 `stale` 断言），接线完成后
   `router.ts` 会 import `anthropic.ts`，这条注册条目届时会变成"多余登记"而非"孤儿"，
   不删会转而触发反向检查报错。

## 给主会话的接线说明

`router.ts` 的 `ADAPTERS`（不在本 lane 文件所有权内，本 lane 未触碰）需要加一行：


  （`["claude-sonnet-4-5", "claude-opus-4-5"]`），不需要改动模型名字典，只需要把
  `ADAPTERS.anthropic` 这一条从"缺失"补上。
