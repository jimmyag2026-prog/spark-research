## 一、与 lane δ 共享的常量（收口要核对的那一条）

**路径与名字（收口按这个核）**：

| 常量 | 值 | 声明位置 |
|---|---|---|
| `COMPUTE_OUTPUT_OBSERVATION_KIND` | `"compute_output"` | `backend/src/compute/broker.ts` |
| `COMPUTE_OUTPUT_ARTIFACT_KIND` | `"compute_output_file"` | `backend/src/compute/broker.ts` |
| `COMPUTE_OUTPUT_EVIDENCE` | `"computed"`（`EvidenceLabel`） | `backend/src/compute/broker.ts` |

δ 需要按「算力产出」筛 record 时，一律：

```ts
import { COMPUTE_OUTPUT_OBSERVATION_KIND } from "../compute/broker";
```

**不许**在 `report/**` 里再手写一份 `"compute_output"` 字符串（V46 的教训：并行 lane 之间的
手写副本，单条 lane 的门禁看不见）。

为什么放在 `broker.ts` 而不是新建一个 `compute/evidence.ts`：任务书的文件所有权只给了
`compute/{sim_bridge,cli,broker}.ts` 三个落点，而写这条 record 的代码就在 broker 里——
常量与它唯一的生产写入方同文件，是最不容易漂的摆法。`broker.ts` 的 import 全是类型或无副作用模块，
`report/cli.ts` import 它不会拖起任何运行期行为。

## 二、S2：算力产出进证据图

### 2.1 两个写入时机，各自的理由

| 时机 | 落什么 | 为什么是这里 |
|---|---|---|
| 执行进终态（`ComputeBroker.settle()`） | 一条 `observation`（`kind=compute_output`，`evidence=computed`） | 「这次算力运行本身」就是一条真实的观察。失败/超时也落——「跑过、没跑出来」同样是观察，藏起来才是不诚实 |
| 收割成功（`ComputeBroker.collect()` 的 `deliver_ok` 之后） | harvest 文件**各一条** `artifact` record + `observation --derives_from--> artifact` 边 + 回填 observation 正文/metadata | 产物这会儿才真的落到本地。收割之前就登记 artifact 等于登记一个还不存在的文件 |

**落点在 broker 而不是 cli**：`compute collect` 有两个生产入口（CLI 与
`server/routes/compute.ts` 的 `POST /jobs/:id/collect`），两者都走 `openComputeScope()`
拿同一个 broker。写在 CLI 里，HTTP 那条路就会静默地不落证据——V46 的形状。
`openComputeScope()` 里那一行 `evidence: new ComputeEvidenceRecorder(...)` 是**唯一的接线点**。

K-3 没有被破坏：整条 job 生命周期只落这两处 record，**不是每次 poll 落一条**
（那会重演 v0.4 W3 的 `NoProgressGuard` 被静默废掉）。

### 2.2 observation 的 metadata 里为什么有 `runId`

`reviewer/conclusion_rules.ts` 的 `evidence_without_execution` 判据读的是
`metadata.runId / metadata.experimentId`：两个都没有 = 「手工登记的观察」（soft finding）。
一次算力运行的执行锚点就是这个 job，所以 `runId = jobId`，如实填。
不填的话，S2 修了一半——observation 有了，但基于它写的结论仍然带一条 soft。

### 2.3 桥路径不走这条

`job.experimentId !== null` 时 `ComputeEvidenceRecorder` **整个让路**：那批产物由
`ExperimentLoop.ingestOutputs()`（artifact）与 `analyze()`（observation）登记，
两边都落会让同一批文件在图上出现两次。桥路径的 broker 因此**刻意不注入 evidence**
（`experiment/compute_driver.ts` 的构造函数里有注释说明）。
`tests/unit/compute_e2e.test.ts` 有一条专门断言桥跑完之后 `compute_output_file` / `compute_output`
两种 record **一条都没有**。

## 三、CB-6 桥

### 3.1 形状（与设计 §1.1.9 逐条对齐）

```
exp new --target local|modal        → ExperimentMeta.computeTarget（不改状态机，不加状态）
exp run  (state=design)             → platform.prepare()（归一化仍在本地做）
                                    → sim_bridge.planFromPrepared() → broker.plan()
                                    → 状态停在 dry_run，写 computeJobId，⏸ 交给人
人：compute approve --run / compute run <jobId>
exp run --resume                    → driver.status()（读 job.json，不是 platform.poll）
                                    → broker.collect() → sim_bridge.materializeHarvest()
                                    → 回填成 <runs>/<runId>/{run.json,done.json,产出}
                                    → platform.collect() 与 ingestOutputs() **原样工作**
```

`simulation/**` **零改动**（lane β 的地盘，只读）；`EXPERIMENT_STATES` **零改动**。
`ExperimentMeta` 只加两个可选字段，老 record 缺省 = 本机跑，不迁移
（`tests/unit/experiment.test.ts` 有一条专门删掉这两个键再跑通整条闭环的用例）。

### 3.2 三个设计取舍

1. **`experiment/compute_driver.ts` 是「编排」，`compute/sim_bridge.ts` 是「翻译」。**
   loop 不 import 任何 `compute/**`，算力层的 import 全关在 driver 里。
   任务书把 `compute_driver.ts` 放在 `backend/src/experiment/` 下（设计 §1.1.1 的表里写的是
   `tests/helpers/compute_driver.ts`，作 SIGKILL 的被杀进程）——**按任务书办**，
   于是它成了生产代码里的驱动窄口；SIGKILL 用例要的那个「被杀的进程」改由测试自己写进临时目录
   （测试文件是本 lane 所有，不需要动 `tests/helpers/`）。分歧照实记在这里，不擅自改设计文档。

2. **桥必须先把上传面组装成一个真实目录。** runner 的包树（`materializeAssetTree` 解出来的临时目录）
   与归一化参数（`prepared.stageDir/params.json`）本来在两个不同的根下，而 `ComputePlan.uploads`
   是「相对同一个 workspaceRoot 的一组路径 + size + sha256」。不合并成一个根，`preflight()`
   就没有可重验的对象——而 preflight 正是「人批的那份清单和真正上传的东西是不是同一份」的唯一判据。
   落点：`<experiments>/compute/bridge/<specHash>/`，按 specHash 幂等。

3. **没注入 driver 就显式失败，不悄悄退回本机跑。** 退回去 = 绕过审批门。
   目前只有 CLI（`exp` 命令）接了 driver；HTTP 的 `scope.dryLoop()` 在 `server/context.ts`（lane γ 的文件），
   所以 HTTP 只做 `target` 字段透传，真要用 HTTP 驱动算力实验会撞到这条显式报错。见 §六遗留 3。

### 3.3 `awaiting_compute`：等的是人，不是机器

`ResumeResult.action` 加了第五种。第一版没加，把 `execution=planned` 读成 `still_running`——
`exp run` 直接挂满 15 分钟的默认超时（实测撞到，见 §五的调试记录）。
算力任务停在 `planned` / `awaiting_approval` / `approved` 三种状态时，
等的都是人；轮询只会白白转到超时，而且会把「没人批/没人派」报成「跑得慢」。

退出码口径：第一次 `exp run` 建完计划停下来 → **0**（这一步没有失败，与 `compute plan` 在
`awaiting_approval` 上退 0 同口径）；`exp run --resume` 时仍然没派发 → **1**
（你明确要求接回来，而它接不回来）。

## 六、遗留问题 / 交收口

1. **`ComputeBroker.recover()` 在 W5-2 交付时零生产调用方**（`grep -rn "\.recover(" backend/src` 实核：
   只有 broker 自己那一行）。状态机里「编排进程重启后接回」这条边建好了，却没有任何入口能触发它——
   编排进程一被杀，任务就永远卡在 `running`，人工也没有办法把它推进终态。
   本 lane 补了 `spark-research compute recover <jobId>`（`compute/cli.ts` 在我的足迹内），
   它现在是这条边的生产入口。**但请收口复核这是不是最合适的入口**（也可能该由 `exp run --resume` 顺带触发，
   见下一条）。

2. **【本 lane 修不了，必须交收口】local adapter 的 `AdapterHandle` 在执行期间根本没落盘。**
   `broker.runOn()` 只在 `adapter.run()` **返回时**才把 handle 写进 `job.json`（`settle()` 那一步），
   所以编排进程在执行中途被杀 → `job.json.adapterHandle` 是 null → `recover()` 拿不到 pid，
   `collect()` 也拒绝工作（「没有 adapterHandle，无从收割」）。
   后果：**设计 §1.1.9 的验收路径「本地进程 SIGKILL → 重启 `exp run --resume` 收割」今天走不通**，
   哪怕算例其实已经跑完、产物就躺在 `<jobDir>/workspace` 里。
   修它要在 `RunHooks` 上加一条 `onHandle`（`compute/target.ts`）并让 `adapters/local.ts` 在 spawn 之后
   立刻回调——两个文件都不在本 lane 足迹内（任务书：`adapters/**` 契约已定、只许适配）。
   本 lane 能做的已经做了：把那条路径的**说法**改诚实（原来说「这个任务从未真正派发出去」，
   是假话），并让它走 `transition` 的 `fail` 边，于是 `recoverable=true`，
   `release` 会被 L-4 拦住，不会把唯一一份产物删掉。阴性对照④钉的就是这一条。

3. **HTTP 驱动不了算力实验。** `server/routes/experiments.ts` 只做 `target` 字段透传（任务书就是这么划的）；
   真正的 driver 注入点在 `server/context.ts` 的 `dryLoop()`（lane γ 的文件）。
   现状是：HTTP 建得出 `computeTarget=local` 的实验，但 `POST /:id/run` 会撞到
   `ExperimentLoop` 那条显式报错（「没有接算力驱动」）。**这是有意的**——悄悄退回本机跑等于绕过审批门——
   但收口应该在 `context.ts` 里补上一行 `compute: computeDriverFor(project, …)`。

4. **`CONTRACT_RECORD_PRODUCERS` 没登记 `compute_output`。** 设计 §5.3 提过要加
   `kind:"compute_output" ← compute/broker.ts`，但 `tests/unit/narrative_parity.test.ts` 是 lane β 独占，
   本 lane 不碰。判据形状是现成的（`from: "backend/src/compute/broker"`,
   `kindConst: "COMPUTE_OUTPUT_OBSERVATION_KIND"`, `writer: "backend/src/compute/broker"`）——
   注意写入方与常量在同一个文件，现有 `verifyContractRecordProducer()` 要求写入方 **import** 这个常量，
   同文件的话没有 import 边，判据会误报。收口要么放宽判据（同文件视为通过），要么把常量挪进单独文件。

5. **`llms-full.txt` 越界了一行**（`git status` 会看到）。原因是 `exp_design` 加了 `target` 参数，
   `tests/unit/llms_txt.test.ts` 的幂等门禁当场变红，唯一的修法就是 `bun run gen:llms`。
   diff 只有我自己那段 `exp_design` 描述与 schema，冲突面很窄。

6. **通用算力路径还没有「写结论」的入口。** `ConclusionStore.create()` 只被 `report/export.ts` 读，
   没有 CLI（`conclusion` 只有 list/show/review）。桥路径可以走 `exp run --conclude`，
   通用路径（`compute run` 非实验）目前只能靠 HTTP/程序调用。S2 已经把**评审能不能过**这个死结解开了，
   但「怎么写这张卡」还缺一个 `conclusion new`——不在本 lane 足迹（`conclusion/**`），登记 BACKLOG。

7. **`materializeHarvest()` 的 runId 形如 `<platform>-compute-<jobId>`**，与 `RunStore` 原生的
   `<platform>-<base36>-<uuid8>` 不同形。有意为之（一眼看得出这个 run 来自哪个算力任务），
   但如果将来有人按 runId 的形状做解析，这里要记一笔。
