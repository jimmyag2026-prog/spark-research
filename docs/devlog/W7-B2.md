## 一、B-2a · blended 默认加深每源抓取池

### 1.1 设计

`literature/search.ts` 新增常量 `BLENDED_DEEP_POOL = 30`（旁注释写清出处：
`docs/devlog/W7-B1.md` §四「真实召回核验」——`perSource=10` 浅池下跨源重叠太稀薄，
hits 退化成准被引排序，blended 没有材料可纠偏；`--limit 50` 复现时才看到 V67
描述的病灶真正发作）。

`LiteratureSearcher.search()`：

```ts
const rank = options.rank ?? "hits";
const deepPoolApplied = options.perSource === undefined && rank === "blended";
const perSource = options.perSource ?? (rank === "blended" ? BLENDED_DEEP_POOL : 10);
```

- 调用方显式给 `perSource` 时优先，深池默认不生效。
- `rank !== "blended"`（含类级默认 `"hits"`）时 `perSource` 仍是 10，`--rank hits`
  逐字节不变（既有回归钉子 `v67_ranking.test.ts` 的 `applyRank(..., hits)` 用
  `toBe` 引用相等钉住，未受影响）。
- 深池默认生效时，在每个 `outcome==="ok"` 的源的 `status.note` 上追加
  `深池 30/源（blended 默认）`（AD-12：结果怎么来的要可见；不动 `dedupePapers`/
  `applyRank` 的 `rankNote`，避免影响它们各自的既有断言）。

`server/routes/literature.ts:92`（唯一允许改动的一行）：把

```ts
ctx.searcher().search(query, { sources, perSource: limit, limit, rank: "blended" })
```

改成

```ts
ctx.searcher().search(query, { sources, limit, rank: "blended" })
```

——不再显式传 `perSource`，让 blended 默认深池在 HTTP/Web 检索入口生效
（B-1 devlog 当时明确记录过这处「HTTP 没有享受到 blended 改进」的缺口，
本 lane 补上）。V26 令牌桶未改动，NCBI 系限速不受影响。

下录制的，也就是 `per-page=10`。`server_literature.test.ts` 的用例通过
`makeServer({ searcher: searcherWith(CASSETTES.search, "replay") })` 把这个

生产请求打出 `per-page=30`，cassette 里没有这个 key 的录制记录，回放 miss →

`tests/e2e/workbench.spec.ts` 的许可是这个前提）——是 fixture 精确匹配 miss 导致
彻底 0 结果，调大或调小期望值都掩盖不了它，需要让 fixture 数据本身与新的默认
`perSource` 对齐。

**这 5 个单测文件 + e2e 全部不在本 lane 允许改动的文件列表内**
（`tests/helpers/literature_scenario.ts`、`tests/e2e/fixture_server.ts`、
`tests/fixtures/literature/*.json`、`tests/integration/literature_record.test.ts`
一个都没列在「允许」里），没有去碰它们一行。

**给收口的建议修法**（诊断出的根因 + 一个不需要重新录制网络请求的最小修法）：

在 `tests/helpers/literature_scenario.ts` 的 `searcherWith()` 里，给它返回的
`LiteratureSearcher` 实例的 `.search()` 方法包一层默认 `perSource: PER_SOURCE`
（调用方显式给的仍优先）——测试替身的职责是「让 fixture 数据能被读到」，不需要
真的去练习 `search.ts` 里深池默认这条新逻辑本身（那部分 `v67_deep_pool.test.ts`
已经真实覆盖）。大致形状（未验证过，需要收口实跑）：

```ts
export function searcherWith(cassette: string, mode: FixtureMode): LiteratureSearcher {
  const searcher = new LiteratureSearcher(
    new ConnectorRegistry({ http: fixtureHttp(cassette, mode) }).registerBuiltins(),
  );
  const rawSearch = searcher.search.bind(searcher);
  searcher.search = (query, options = {}) => rawSearch(query, { perSource: PER_SOURCE, ...options });
  return searcher;
}
```

`server_literature.test.ts` 与 `tests/e2e/fixture_server.ts` 的 `DualCassetteSearcher`
都经这一个函数构造 searcher，改一处即可同时修好单测与 e2e 那 6 处失败，不需要
`FIXTURE_MODE=record` 重新打真实网络。如果收口更倾向于让测试替身也吃到新的深池
默认（即验证 fixture 场景下 `per-page=30` 的真实效果），则需要
`FIXTURE_MODE=record bun test tests/integration/literature_record.test.ts`
重新录制 `search-alphafold` 等 cassette——这条路径需要真实网络与
（如果测 aminer 相关 cassette）有效凭据，成本更高，本 lane 判断不是必须。

## 二、B-2b · 中文分词器（jieba，可选依赖，V65 残余）

### 2.1 设计

新 `backend/src/literature/segment.py`（stdin 进原始查询文本 → stdout 出单行 JSON
`{"terms": [...]}` 或 `{"terms": null, "reason": "..."}`）+ `segment.ts`——与
`pdf_text.ts`（pypdf）同一形状：脚本内容静态 `import ... with { type: "text" }`
进二进制，运行期经 `materializeAsset("literature", "segment.py", SEGMENT_PY)` 解包
到真实路径再 `Bun.spawn`（`bun build --compile` 产物里 `import.meta.dir` 是
`/$bunfs/` 虚拟路径，外部 python 读不到，V27/F-c 已踩过这个坑，不重犯）。stdin 传
文本（不走 argv）避免中文经命令行参数传递的 shell/编码坑，做法与 `chem/depict.ts`
传 JSON payload 一致（`proc.stdin.write(...); proc.stdin.end();`）。失败语义：
永不抛，`terms: null` + `reason`。

`segment.ts` 额外导出 `probeSegmenter()`——给 `doctor` 用，真跑一次 `segmentQuery`
判断 jieba 能不能用（复用生产路径本身，不另起一套 `-c "import jieba"` 判断，
避免「两处各判一次」这种本轮反复修的病）。

`search.ts` 拆词入口（`searchOne` 的 AMiner 分支）：

```ts
let terms = query.split(/\s+/).filter(Boolean);
if (terms.length < 2 && containsCJK(query)) {
  const segmented = await this.segmenter(query);
  if (segmented.terms && segmented.terms.length >= 2) {
    terms = segmented.terms;
    segmentedByJieba = true;
  } else {
    segmentFailureReason = segmented.reason ?? "分词结果为空或不足 2 词";
  }
}
```

`containsCJK()` 只判「有没有中文」（基本 CJK 统一表意文字区）。`LiteratureSearcher`
构造函数新增第二个可选参数 `{ segmenter?: Segmenter }`，默认注入真实 `segmentQuery`；
测试注入假实现验证拆词入口判据本身，不依赖真装了 jieba。`status.note`：分词器成功
时标「jieba 分词合并（N 词：...）」，失败/不可用时在 v0.6 原始提示文案后追加
「（分词器不可用，退回空格拆词：原因）」。

`doctor`：`DoctorReport` 新增可选字段 `segmenter?: { available, reason }`（可选
是因为 `tests/unit/doctor.test.ts` 手写了几份 `DoctorReport` 字面量喂
`renderDoctor()`，不在本 lane 足迹内，不强改；真实 `buildDoctorReport()` 路径始终
会填上）；不进 `tiers[]`（`core`/`science`/`lab` 三档，jieba 缺失是「AMiner 拆词
兜底退化」不是「一整档能力不可用」，语义不同，混进去会让 `doctor/cli.ts` 里
「三档」的既有文案变得不准确）。`doctor/cli.ts` 加一行探测输出（`✅/❌ jieba ...`），
只在 `report.segmenter` 存在时渲染。
