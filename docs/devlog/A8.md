### BLOCKER-1 · `originAllowlist` 里的非 loopback 来源能写入与删除凭据（AD-18 ② 不成立）

复现（**必须重启 server，否则复现不出来**——这是它活到 alpha.3 的原因）：

```bash

curl -s -X PUT "http://127.0.0.1:4321/api/settings/general/originAllowlist" \
  -H 'Content-Type: application/json' -H 'Origin: http://127.0.0.1:4321' \
  -d '{"value":"a8-remote.example"}'

# 2. 重启 server（在读到新配置的实例上复现）
bun backend/src/index.ts server 4399

# 3. 带那个 Origin 写凭据
curl -s -i -X PUT "http://127.0.0.1:4399/api/settings/credentials/semanticscholar" \
  -H 'Content-Type: application/json' -H 'Origin: http://a8-remote.example' \
  -d '{"fields":{"api_key":"A8-FAKE-KEY-20260915-REMOTE"}}'
```

输出原文：

```
HTTP/1.1 200 OK
{"panel":"credentials","item":{"key":"semanticscholar",...,"configured":true,...,"fieldsSet":["api_key"],...},
 "meta":{...,"notes":[...,"只接受本机（loopback）来源的写入；配了 originAllowlist 也不会放开这条路径（AD-18 ②）",...]}}
```

落盘核对：`credentials.json` 里 `semanticscholar.api_key` 确实变成了那个 `-REMOTE` 值
（`endsWith -REMOTE: True`，`updatedAt: 2026-09-15T10:14:41.434Z`）。`DELETE` 同样 200 并真的删掉。

对照组证明这不是「allowlist 整体失效」：同一实例、同一 Origin 打非凭据端点 `PUT /api/settings/general/httpTimeoutMs` 也返回 200，
