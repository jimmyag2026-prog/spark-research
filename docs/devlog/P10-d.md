## D-9：状态机无乐观并发控制 → 一次批准并发执行两次

### 根因

改动前 `execute()` 在整个执行期间（`await this.backend.execute(...)` 之前）**没有任何一次
数据库写入**——状态从 approve 那一刻起原地不动，直到后端 resolve 之后才推进到 `collect`/`failed`。
两个并发调用各自的同步前缀（状态检查 → hash 复核）都会读到"看起来能执行"，都会真的调用后端。
在模拟器下是脏数据，接真机就是"一次批准、多次执行"。

### 修法：records.rev（乐观并发）+ execute() 内原子声明执行权

**`backend/src/project/records.ts`**：
- `records` 表加 `rev` 列（`INTEGER NOT NULL DEFAULT 1`），**完全通过运行时迁移加**，
  没有碰 `schema.sql`（那是所有 lane 共用的建表脚本）：`RecordStore.initSchema()` 跑完
  `schema.sql` 之后，`migrateRevColumn()` 用 `PRAGMA table_info(records)` 查有没有 `rev` 列，
  没有就 `ALTER TABLE records ADD COLUMN rev INTEGER NOT NULL DEFAULT 1`。新库和老库走
  同一条路径（新库先被 `CREATE TABLE IF NOT EXISTS` 建出来，同样没有 rev，同样被这行 ALTER
  补上），所以"新库要不要迁移"这个分支根本不存在，减少了一类可能忘记处理的分支。
  老库里已有的行一律从 `rev=1` 起——这是唯一诚实的起点，之前的历史本来就没记录版本号。
- `RecordStore.getRev(id)`：单独读一行的 rev，不进 `ResearchRecord`（那是跨 lane 共用的类型，
  加字段风险面更大，也没必要——只有需要 CAS 的调用方才关心 rev）。
- `RecordStore.update(id, patch, opts?)`：新增**可选**的第三参数 `{ expectedRev?: number }`。
  不传就是原来的行为（无条件覆盖，`rev` 仍然 +1，只是没人核对它）——**完全向后兼容**，
  其他 lane 现有的 `records.update(id, patch)` 调用不用改一个字符。传了就是
  `UPDATE ... WHERE id=? AND rev=?`：影响行数 0 就抛 `RecordConflictError`（不静默覆盖）。

### 修法：WetLabLoop.execute() 的原子声明

`execute()` 在"三道门"（状态必须 approved / 必须有 approval / hash 必须匹配）之后，新增一步：
用 `this.transition(view, "executing", ..., { expectedRev: view.rev })` 把 `approved → executing`
写成一次 CAS。这一步是整个方法里**唯一**发生在 `await this.backend.execute(...)` 之前的写入——
写成功了才真的去碰后端；写失败（rev 冲突）直接抛 `WetExecutionConflictError`，一次都不碰设备。

`transition()` 本身也改了（向后兼容）：新增可选的第五参数 `opts: { expectedRev?: number }`，
不传就是原来"无条件覆盖"的行为，其余七处调用方（design/compile/safetyCheck/approve/reject/
analyze/conclude/iterate）一个字都没改。`transition()` 内部把 `RecordConflictError` 统一转成
`WetExecutionConflictError`（见下）。

### `WetExecutionConflictError` 与 HTTP 409

`WetExecutionConflictError extends WetStateError`。`backend/src/server/routes/lab.ts`（不属于
本 lane，未改动）里已经有 `error instanceof WetStateError → HttpError(409, ...)` 的映射，
所以并发冲突**不需要改任何 HTTP 层代码**就能拿到正确的 409 语义——这是刻意选的继承关系，
不是巧合。

### 验收

`tests/concurrency/approve_once.test.ts`：N=30 次并发 `execute()` 同一份已获批协议，
断言恰好 1 次 `state → collect`，其余 29 次全部拿到 `WetStateError` 系的冲突错误
（至少验证到 `WetExecutionConflictError` 真的出现过），run log / artifact 只有一份。

**诚实说明测试的局限**：Bun 是单线程事件循环，`execute()` 的同步前缀（get → 状态检查 →
hash 复核 → CAS 声明）中间没有 `await`，所以在单进程测试里，"谁先跑完同步前缀"是确定性的
（JS 的 run-to-completion），第 2~30 次调用的同步前缀跑的时候，第 1 次已经把状态写成
`executing` 了——它们会被 `execute()` 开头那个 `if (view.state === "executing") throw` 的
**普通状态检查**挡下来，不一定真的撞上 rev 冲突那条 CAS 分支。也就是说这个测试证明的是
"最终结果正确"（恰好一次执行），但没有、也无法在单进程 Bun 里真正制造出"两个调用同时
读到 rev=N、都尝试写"的硬件级竞态。
CAS 机制本身（rev 对不上就拒绝、不静默覆盖）在 `tests/unit/project.test.ts` 的
`describe("RecordStore · rev 与乐观并发（D-9）")` 里做了确定性的直接验证（两次 `update()`
带同一个过期 `expectedRev`，断言后一次抛 `RecordConflictError` 且数据没被覆盖）——
这套机制存在的意义主要是**防御性**：如果这条执行路径未来变成多进程/多 worker，
或者调用链路前面插入了别的 `await`（比如 HTTP 任务队列的调度），CAS 仍然是保证
"恰好一次"的那一层，不依赖"谁先跑到"的时序巧合；单进程场景下它现在基本是第二道防线。

### 来源校验：绕过状态机直接改 state/approval 会被检测到

评审指出：进程内 `RecordStore.update()` 可以一次性伪造 `state:"wet_run"` + approval +
protocolHash，而 execute() 的 hash 复核对整套伪造必然自洽通过（因为复核是拿**当前**
naturalLanguage 重新编译）。

修法：`WetExperimentMeta` 新增 `integrityHash` 字段。每次合法的 `transition()`（包括
`createRecord()` 建初始 `design` 记录）都对**整份 meta（除这个字段自己）**算一次 sha256
（`computeMetaIntegrityHash`，key 递归排序后再 `JSON.stringify`，保证不受插入顺序影响）
存回去。`WetLabLoop.get(ref)` 是唯一强制关口——所有会改状态的方法都先 `get(ref)`，
`get()` 内部用 `verifyMetaIntegrity()` 重算一遍比对，对不上就抛 `RecordIntegrityError`，
拒绝信任这条记录、拒绝继续任何状态机操作。

`list()` **不**走这道关口（直接调私有的 `toView`，不触发校验）：一条记录的完整性问题
不该让整份清单直接炸掉；`toView` 会把 `integrityOk` 算出来放进 view，供需要的地方查。

`integrityHash === null`（老记录，这个机制上线前建的）视为"暂未纳入保护"而不是"已验证安全"，
放行——这是历史记录能继续被打开的前提，下一次这条记录被合法 transition() 就会补上哈希。

**这不是密码学意义上防有源码访问权限的攻击者**（伪造者理论上可以照抄同一套哈希算法
把伪造做到自洽），防的是"绕过 `WetLabLoop`、直接用通用的 `RecordStore.update()` 部分
patch 几个字段"这类误用/漏洞——不管是有意绕过还是代码 bug 导致的意外覆盖，
都会在下一次 `get()` 被发现，而不是静默生效。

验收：`tests/unit/wet_loop.test.ts` 新增两个测试——
1. 只改 `naturalLanguage` 一个字段（旧测试场景，原来断言 `ApprovalRequiredError`，
   现在断言更早、更严格的 `RecordIntegrityError`，见下"既有测试受影响"）；
2. 一次性伪造 `state:"approved"` + 匹配当前编译产物的 `protocolHash` 的 `approval`
   （更贴近评审描述的场景），同样被 `RecordIntegrityError` 挡下。

## D-10：wet_run 混态 + approval 跨崩溃存活

### 拆状态

`WET_EXPERIMENT_STATES` 从 11 个变成 12 个：`wet_run` 拆成 `approved`（已批准、还没真的
开始跑）与 `executing`（execute() 已经原子声明了执行权，正在跑，或者编排进程在这里崩了）。

```
awaiting_approval --approve()--> approved --execute()内部CAS--> executing --> collect
                                     ↑                              │
                                     └──────────compile()───────────┘（崩溃恢复出口）
```

合法转移从 18 条变成 21 条（`approved: [executing, failed, compile]` 3 条 +
`executing: [collect, failed, compile]` 3 条，比原来单个 `wet_run` 的 3 条多出 3 条）。

`executing → compile` 是刻意留的**崩溃恢复出口**：卡在 `executing` 的实验只能靠人
显式重新编译才能挣脱。`execute()` 自己**不会**主动把 `executing` 判定成 `failed`——
"另一个并发请求正在跑"和"编排进程已经崩了、卡在这"从状态本身分不出来，分不出来就不猜，
一律在 `execute()` 开头判负（`WetExecutionConflictError`），把决定权交给人。

### approval 一次性消费

`WetExperimentMeta` 新增 `consumedApproval: ApprovalRecordMeta | null`。`execute()` 声明
执行权（`approved → executing`）的**同一次** `transition()` 里，把 `approval` 搬进
`consumedApproval` 并置空：

```ts
const claimed = this.transition(view, "executing", "...", (meta) => ({
  ...meta,
  consumedApproval: meta.approval,
  approval: null,
}), { expectedRev: view.rev });
```

这样即使编排进程在 `executing` 期间被 SIGKILL，重启后 `approval` 也已经不在了——免审批
整体重跑不可能。`consumedApproval` 只是审计存档（`renderWetExperiment` 会显示"审批（已消费）"
小节，`ingestRun()` 的产出 provenance 里"审批：谁 @ 何时"也改成优先取 `approval ?? consumedApproval`，
不然执行产出的溯源信息会在 approval 被消费之后变成"?"）。

### 验收：真实 SIGKILL 恢复 e2e

参考仓库里 P5 的 `tests/helpers/experiment_driver.ts` / `tests/unit/experiment_e2e.test.ts`
写法，新增：
- `tests/helpers/wet_driver.ts`：另起一个真实 bun 子进程扮演编排进程。design → compile →
  safety_check → approve，然后 `void loop.execute(id)`（不 await）用一个永不 resolve 的
  假后端，打印握手 JSON 后进程挂起等着挨刀。因为 `execute()` 的同步前缀（含 CAS 声明执行权）
  在第一个 `await` 之前跑完，握手打印出来的时候 `approved → executing` 这次转移必然已经落盘。
- `tests/unit/wet_crash_recovery.test.ts`：SIGKILL 掉 driver 进程，重开项目，断言：
  `state === "executing"`、`approval === null`、`consumedApproval.actor === "driver"`；
  `execute()` 立刻拒绝（`WetExecutionConflictError`，不是"猜它可能还在跑"）；必须显式
  `compile()` 才能挣脱，挣脱后如果不重新 `approve()`，`execute()` 仍然拒绝
  （`ApprovalRequiredError`）；完整走一遍 `compile → safety_check → approve → execute`
  才能真正跑通。

与 P5 的差别：湿实验的执行是同步 await 模型（没有独立的仿真子进程/pid 存活探测那一套），
所以这个 e2e 比 P5 简单——不需要处理"任务被 init 收养继续跑"那个分叉，只需要证明
"编排进程消失后，卡在 executing 的记录无法被免审批地推进"。

## D-8：安全门声明收敛

### 方针（严格遵照要求）：最小实现 + 强制告警，不做完美的 NL 解析

**1. 强制告警（`Protocol.warnings` / `WetExperimentMeta.unconsumedWarnings`）**

`backend/src/lab/protocol.ts` 新增 `scanUnconsumedSignals()`，在编译每个子句时检测：
- **同一子句里出现 ≥2 处体积数值**：`extractVolume`/`mergeContinuation` 结构性地只取
  正则第一个匹配，第二个往后**结构性地**一定被丢——不用猜，直接报，报的是"这句里有几处"
  而不是"哪个字段没对上"（后者需要按每个动作的参数形状单独判断，误报风险高，没做）。
- **子句提到温度/时长，但这句话最终落地的 step.params 里没有对应字段**：说明整句被
  识别成了一个根本不认温度/时长的动作（比如"37°C 孵育 30 分钟后加入 500µL 样品"整句被
  "加入"关键词命中成 addSample，温度/时长静默消失）。这个检测顺手覆盖了评审提到的
  "单句单动作假设静默丢语义"那个例子，**没有改**动作识别本身的逻辑（那是更大的重构，
  没做，见下"仍然空转"）。
- **浓度描述（`10%` / `mol/L` / "浓度为..." 等）、生物安全等级描述（`BSL-2` / "生物安全二级"）**：
  **无条件**报，不判断"有没有被用到"——因为编译器主管线压根不解析这两类字段，
  它们**必然**没被用到（见第 4 点）。

新增的告警在三处强制显示：`backend/src/lab/cli.ts` 的 `compile` 命令输出、
`printView()`（approve/reject/simulate/status 共用）、以及 `wet_models.ts` 的
`renderWetExperiment()`（experiment record 的正文，撕下来也认得出的那份）。

**2. 最小补强（力所能及的部分）**

- `protocol.ts` 的 `REAGENT_PATTERNS` 从 6 个纯中文关键词扩到中文 + 常见英文名 + 分子式
  （NaOH / HCl / ethanol/EtOH / NaClO / H2O2，外加原有的 hydrochloric acid / sulfuric acid /
  sodium hydroxide 等长名）。匹配大小写不敏感。`extractReagents` 返回的 `name` 仍然取
  `keywords[0]`（中文，v0.1 起的对抗测试断言中文名，顺序没动）。
- 修了续句合并会丢试剂的 bug：`mergeContinuation` 从来不处理试剂，"加盐酸50µL，
  其中再补加次氯酸钠10µL"里第二种试剂从没进过 `step.params.reagents`——新增
  `mergeReagents()`，续句里的试剂现在会**追加**（按 reagentId/name 去重）到上一步，
  不是覆盖、也不是丢弃。

**3. 文档口径收敛（必做）**

`backend/src/lab/safety.ts` 顶部新增一段注释，明确写：只有 `volume_capacity` 全程接
编译产物核对；`chemical_compatibility` 认识的是一个**有限**词表；`concentration_limit` /
`biosafety` **在正常调用路径上永远空转**。`renderWetExperiment()` 的安全门表格下面也
固定带一句同样口径的提示（人工审批时能直接看到，不用去翻代码注释）。

**4. 浓度 / BSL 的 NL 解析：明确没做**

`concentrationLimitRule` 需要 `ReagentSpec.concentration`、`biosafetyRule` 需要
`step.params.biosafetyLevel`——`ProtocolCompiler.compile()` 完全不解析、不产生这两个字段。
这两条规则在**自然语言主管线**上是彻底空转的：真实用户写"配制10%次氯酸钠溶液"这种协议，
`concentration_limit` 规则永远看不到那个 `10%`，只会看到一个体积正常的步骤，照样放行。
本次没有实现浓度/BSL 的 NL 解析（工作量评估：需要新的抽取规则 + 单位换算 + 与试剂对象
的绑定关系，且中文"浓度"表达方式多样，容易做出一堆误报或漏报，超出本次"最小实现"的范围）。
**这两条规则在主管线仍然空转**——唯一的缓解是上面第 1 点的 `unconsumed` 告警：写了浓度/BSL
描述的协议会在编译、审批、正文里都看到醒目提示，不会是静默绿灯。

### D-8 验收

  （含大小写不敏感、续句试剂不丢）+ unconsumed 信号（多体积/单动作丢语义/浓度/BSL 都报，

### D-8 收敛后的真实覆盖范围（一句话）

四条规则里只有 `volume_capacity` 全程可信；`chemical_compatibility` 认识一个扩过的
有限试剂词表（中文常见名 + 少量英文名/分子式）；`concentration_limit`/`biosafety` 在
自然语言主管线上完全空转；所有"编译器看到了信号但没有规则消费"的情况现在都会产出
**强制可见**的 `unconsumedWarnings`，而不是静默通过。

## records.db 迁移方案（汇总）

不改 `schema.sql`（跨 lane 共用文件）。`RecordStore.initSchema()` 跑完建表脚本后，
`migrateRevColumn()` 用 `PRAGMA table_info(records)` 检测 `rev` 列存不存在，不存在就
`ALTER TABLE records ADD COLUMN rev INTEGER NOT NULL DEFAULT 1`。新库和老库走同一条
迁移路径（新库的 `CREATE TABLE IF NOT EXISTS` 本来就不含 `rev`）。老记录的 rev 从 1 起，
之后每次 `update()`（不管带不带 `expectedRev`）都 `rev = rev + 1`。验收见
`tests/unit/project.test.ts` 的"老库没有 rev 列也能正常打开"测试：手工建一张不含 `rev`
的旧版 `records` 表插一行数据，用 `RecordStore` 打开、读、CAS 写，全程不报错。
