## V37：改法

### 真因（主会话已定位，本 lane 只是修）

1. `backend/src/index.ts` 有一份手写的 `KEY_NAMES = { kimi: "KIMI_API_KEY",
   openrouter: "OPENROUTER_API_KEY" }`，只列 2 个 provider；而 `doctor`
   （`doctor/index.ts`）、`capabilities`（`capabilities/index.ts`）、
   `onboarding/providers.ts` 三处都从 `PROVIDER_API_KEY_ENV`
   （`llm/providers/registry.ts`，派生自 `llm/router.ts` 的 `ADAPTERS`，真正实现
   了 6 个 provider：openrouter/kimi/anthropic/openai/deepseek/qwen）取数。这是
   P11 收口过的同一类手工副本漂移，第二次在消费方长出来。
2. `auth()` 显示当前配置时打的是 `config[envName] ? "已设置" : "未设置"`——只读
   config 文件，完全不看环境变量。而 `getApiKey()` 自己是 env 优先的。key 只在
   env 时，`getApiKey()` 能拿到，`auth()` 却报「未设置」，与 `config
   list`/`doctor`（两者都 env 优先）矛盾。

### 修法（`backend/src/index.ts`，整个文件归本 lane）

- 删掉 `KEY_NAMES`。新增 `import { PROVIDER_API_KEY_ENV } from
  "./llm/providers/registry"`（真源，只读，未改动该文件）。
- `getApiKey()` 改成遍历 `Object.entries(PROVIDER_API_KEY_ENV)`（env 优先、
  config 兜底），不再限定死 2 个 provider。
- 新增导出 `authStatus(options)`：每个已实装 provider 的 `{provider, envVar,
  configured, source}`，`source` 取 `"env" | "config" | "both" | null`——env
  与 config 文件都看，并显式区分来源。`auth()` 用它渲染「当前配置」小节，展示
  文案分别是「已设置（来源：环境变量）」「已设置（来源：config 文件）」「已设置
  （环境变量优先；config 文件里也存了一份）」「未设置」。
- 交互式选择 provider 的菜单从硬编码的「1. Kimi / 2. OpenRouter」扩成遍历
  `PROVIDER_API_KEY_ENV` 的全部 6 个（用一份纯展示用的 `PROVIDER_LABELS` 给每
  个 provider 一行说明；这不是 provider→env 名映射，值不是 `*_API_KEY` 形状，
  不会被下面的门禁断言误伤）。这是 V37 remedy 的自然延伸：`auth 只认 2 个` 这句
  抱怨既指展示口径也指配置入口，只补前者会留一半问题。
- **已知的行为变化**：`getApiKey()` 遍历顺序从硬编码的 `[kimi, openrouter]` 变
  成 `Object.keys(PROVIDER_API_KEY_ENV)` 的声明顺序（`ADAPTERS` 里 openrouter
  先声明），多个 provider 同时配置时的「优先选中哪个」顺序因此改变。检查过
  `tests/unit/*.test.ts` 没有测试钉死这个具体优先序（只有零参数冒烟测试显式清空
  两个 env 变量），判断为可接受的副作用，如实记在这里。

## V36（ideation 部分）：改法

### 真因

`idea new` 的契约校验失败走 `backend/src/ideation/coexplore.ts` 的
`CoExploreError`（`turn()`/`explore()` 抛出，携带 `validationErrors` 与
`attempts`）。`backend/src/ideation/cli.ts` 的 `runIdeaCommand` 之前在两个地方
接住它：
1. `-m` 单发路径的外层 `catch`——只 `err(❌ ${error.message})`。
2. 交互式多轮共探循环内层 `catch`——同样只打印原始错误。

`error.message` 本身带了校验失败原因（继承自 `validateIdeaCardPayload` 的
`errors`）与模型原始输出截断，**信息量够，但没有「拿到这条错误之后该做什么」**，
外部验收者只能靠猜。

### 修法（`backend/src/ideation/cli.ts`）

样板是 `backend/src/lab/cli.ts` 的 `requireApprovalGate`（V19）：不只说错在哪，
还给出具体能敲的下一步命令。新增 `printCoExploreNextSteps(err, {interactive})`，
不区分「模型调用失败」与「schema 校验失败」两种子情形（两者的具体原因已经在
`error.message` 里），只补三条对两种子情形都成立的下一步：
1. 重试（LLM 结构化输出非确定性，多数情况下重试就过）——`-m` 路径给出完整命令
   `spark-research idea new -m "<同样的思路>"`；交互式路径给出「换个说法把这轮
   重新输入一次」（不建议退出会话）。
2. 反复失败：先确认 API Key 已配置——指向 `spark-research auth` /
   `spark-research doctor`。
3. 反复失败且报错提到库外 key / 给不出反对证据：指向
   `spark-research lit list` / `spark-research lit search "<关键词>" --add`
   （常见诱因是文献库为空或引用了白名单外的 key）。

两处 `catch` 都改成：先 `instanceof CoExploreError` 判断，原始 `error.message`
照常打印，再追加 `printCoExploreNextSteps(...)`；非 `CoExploreError` 的分支
（`ProjectError`、未知子命令等）不受影响。

## 手动验证：三种情况下 `auth` / `config list` / `doctor` 口径一致

用假 key `sk-test-not-a-real-key`（情况③用 `sk-test-env-fake` /
`sk-test-config-fake` 两个不同假值区分来源），真进程跑三条命令，`env -i` 隔离掉
宿主 shell 里真实存在的其它 provider key（跑之前发现宿主 shell 本身带了一个真实
`DEEPSEEK_API_KEY`，会污染「只在 env」这类场景——已用 `env -i PATH="$PATH"
HOME="$HOME" ...` 精确控制注入的变量，不读取也不打印那个真实值）。

### 情况① key 只在 env

```
$ OPENROUTER_API_KEY="sk-test-not-a-real-key" spark-research auth   # 回车跳过交互选择
当前配置:
  OPENROUTER_API_KEY: 已设置（来源：环境变量）
  ...

$ OPENROUTER_API_KEY="sk-test-not-a-real-key" spark-research config list | grep OPENROUTER
OPENROUTER_API_KEY    （已设置）                        env       OpenRouter API key（默认模型走这条路）

$ OPENROUTER_API_KEY="sk-test-not-a-real-key" spark-research doctor --json | jq '.providers[] | select(.id=="openrouter")'
{"id": "openrouter", "envVar": "OPENROUTER_API_KEY", "configured": true}
```

三者一致：`configured: true`，`auth` 标明来源是环境变量。

### 情况② key 只在 config 文件

```
$ spark-research config set OPENROUTER_API_KEY sk-test-not-a-real-key
✅ OPENROUTER_API_KEY 已写入 <dataDir>/config.json

$ spark-research auth   # env 里没有这个变量
当前配置:
  OPENROUTER_API_KEY: 已设置（来源：config 文件）
  ...

$ spark-research config list | grep OPENROUTER
OPENROUTER_API_KEY    （已设置）                        config    OpenRouter API key（默认模型走这条路）

$ spark-research doctor --json | jq '.providers[] | select(.id=="openrouter")'
{"id": "openrouter", "envVar": "OPENROUTER_API_KEY", "configured": true}
```

三者一致：`configured: true`，`auth` 标明来源是 config 文件。

如实说明改动前后的差异：V37 报告的坏场景（`OPENROUTER_API_KEY` 被 `auth` 报成
未配置，而 `config list`/`doctor` 正确显示已配置）对应的是**情况①**（key 只在
env）——改之前 `auth()` 只读 config 文件、看不见 env 里的值，报「未设置」，与
`config list`/`doctor`（两者都 env 优先）矛盾。**情况②改之前 `auth()` 本来就是
对的**（它一直读 config 文件），只是没有标出来源——现在统一按 §三·补.2 的要求
给所有情况都补上来源标注，情况①②③都不再需要用户去猜。

### 情况③ env 与 config 文件都有（不同假值验证不混用）

```
$ spark-research config set OPENROUTER_API_KEY sk-test-config-fake
$ OPENROUTER_API_KEY="sk-test-env-fake" spark-research auth
当前配置:
  OPENROUTER_API_KEY: 已设置（环境变量优先；config 文件里也存了一份）
  ...

$ OPENROUTER_API_KEY="sk-test-env-fake" spark-research config list | grep OPENROUTER
OPENROUTER_API_KEY    （已设置）                        env       OpenRouter API key（默认模型走这条路）

$ OPENROUTER_API_KEY="sk-test-env-fake" spark-research doctor --json | jq '.providers[] | select(.id=="openrouter")'
{"id": "openrouter", "envVar": "OPENROUTER_API_KEY", "configured": true}
```

三者一致：`configured: true`；`auth` 额外标出「两边都有，env 优先生效」，这是
`config list`/`doctor` 目前都不单独区分的一个更细粒度信息（它们只报
`configured` 布尔值，不报「两边都有」），`auth()` 的展示更完整，但三者对
`configured` 这个布尔判据完全一致——这是 V37 要收口的核心。

（真实终端命令已在上面按逐条实测；此处贴的是清洗过 shell 噪音后的关键输出，
完整原始终端会话见本 session 的 bash 记录，未落盘任何真实凭据。）
