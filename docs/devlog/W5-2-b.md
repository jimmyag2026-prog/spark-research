## 二、三条不可让步的纪律，各自落在哪一行

### AD-14：子代理永不自批准

三条动作**不做 MCP tool**，只在 `MCP_WITHHELD` 里有名字。防线有四层，缺一层都能被绕：

| 层 | 位置 | 挡住的是 |
|---|---|---|
| ① 工具面上查无此名 | `MCP_TOOLS` 里没有它们 | 模型「看到有这个工具就去调」 |
| ② 构造期 | `sub_agent.ts:assertNoWithheldGrants`（`WITHHELD_NAMES` 从 `MCP_WITHHELD` 派生） | 有人把名字写进 grants（配置错误/恶意） |
| ③ 运行期 | `runSubAgent()` 里再校验一次，**先于任何 llm 调用** | 手工构造 spec 绕过 ② |
| ④ ToolBus | `AgentToolBus` 对 withheld 名字返回 `denied:"withheld"` | grants 合法但模型自己编出这个名字 |

**关键点：② 与 ④ 是从同一张表派生的，所以我只往 `MCP_WITHHELD` 加了三条，四层防线自动覆盖**——
不需要在别处再写一遍名单（那正是漂移的成因）。

第五层在 HTTP：**`/api/compute` 上根本没有 dispatch / release 端点**。
MCP 工具都是「对同一个 Hono app 的一次 fetch」，所以 HTTP 上不存在的路，MCP 也走不到——
扣留不是靠那张名单自觉，是这一层压根没有路。`tests/unit/compute_http.test.ts` 里有三条
（`run` / `dispatch` / `release` 全部 404 JSON，且任务状态一动没动）钉住这一点。

对抗测试落点：
- `tests/unit/sub_agent.test.ts`：4 条（一条查名，三条逐动作走完 ②③④）
- `tests/unit/compute_mcp.test.ts`：`AD-14 对抗` + 「agent 经 MCP 走不到派发」（把七个工具名全试一遍，任务仍停在 `awaiting_approval`）
- `tests/unit/toolbus.test.ts`：三条塞进 grants 也拿不到（`denied:"withheld"`，`specs()` 为空）

### TTY 门

`compute approve/reject` 与 `lab approve/reject` **共用同一份代码**（`approval/gate.ts`）。
判据、两条分支、四种拒绝理由、bypassNote 的形状**一字未改**，只把三处名词参数化。

旁路 env 名**刻意与 lab 不同**：`SPARK_RESEARCH_COMPUTE_CI_BYPASS_TOKEN`。
配了 CI 能批湿实验的流水线不该顺带获得「花钱跑 GPU」的权限——两把钥匙、两扇门，
`approval_gate.test.ts` 里有两条互测（lab token 旁路不了算力门，反之亦然）。

「piping 必拒」钉在三处：
- `approval_gate.test.ts`「piping 一个 'yes' 进 stdin 也没用」——并断言**交互确认函数一次都没被调用**（非交互分支根本不读 stdin，读到什么都不算数）；
- `approval_gate.test.ts`「默认探测在测试子进程里就是 false」——把「Bash 工具/CI 天然落进非交互分支」从注释变成可核实的事实；
- `compute_cli.test.ts`「非交互 + 未配置 token → 拒绝，且**不落任何 decision record**」——门在落 record 之前，被拒的这一次不留任何审批痕迹。

### 不许为了接线而放宽契约

**接线全程没有需要后门的地方。** 具体说，我预期会卡住的三处都没卡住：

1. **「测试里怎么派发一个不需要人的任务」**——不需要绕。`plan.approvalRequired` 是派生值（L-3），
   `network:"none"` + 不计费 + 无密钥的 plan 自然派生为 `false`，走 lifecycle 的第二条入边。
   `compute_cli.test.ts` 有一条专门验这个：调用方**不能**传 `approvalRequired`，是 plan 内容说了算。
2. **「CLI 要不要一个 `--force`」**——不要。`approve --run` 是「批准之后顺带派发」，
   审批仍然在那一次里被一次性消费；再 `run` 一次会被 `ApprovalRequiredError` 拒（有测试）。
3. **「release 在没收割时过不去」**——这是 L-4 在正常工作，不是障碍。
   正确的出路是 `collect`（把唯一副本变成两份）或 `release --discard "<理由>"`
   （放弃产物是一次**显式的人的决定**，走 α 的 `broker.discard()`），不是给 release 加旁路。

唯一一处我**改了自己的接法而不是契约**的地方：`broker.collect()` 对「还没到终态 / 没有 adapterHandle」
抛的是裸 `Error`（那两条是调用顺序错误，不是状态机转移错误），落到 HTTP 的错误映射里会变成 500。
我没有去改 broker 的异常类型（不是我的文件，也不该为了 HTTP 好写而改语义），
而是在路由里**先 poll 一次**、把这两种情况翻成 409。见 `routes/compute.ts` 的 collect handler。

## 三、几处需要主会话过目的判断

### 3.1 HTTP 面刻意没有 dispatch / release

设计 §1.1.1 列的六个端点里本来就没有它们，我把这条**当成设计而不是遗漏**来实现，并写进
`/api/compute/machine` 的 `httpWithheld` 字段（机器可读，调用方不必试出来）。
后果：Web 工作台点不了「派发」，只能点「批准」，派发要人去终端。
如果主会话认为工作台需要一个派发按钮，那是一次**需要重新论证**的决定（它会同时给 MCP 开路），
不是加个端点就完事。

### 3.2 `computeTargetViews()` 放在 `compute/cli.ts` 里

「执行地可用性」的判定被三个面消费（CLI `targets` / HTTP `/targets` / `capabilities`）。
三处各写一遍就是 V34「默认源」那类漂移的成因，所以只写一份。
但我的文件所有权里，`compute/` 下只有 `cli.ts` 可写（不许新建 `compute/targets_view.ts`），
所以它落在 `cli.ts` 里，`capabilities/index.ts` 从那里 import。
**这不好看**：capabilities 依赖一个叫 `cli.ts` 的文件。收口若要搬到 `compute/targets_view.ts`，
整个函数搬过去 + 改三处 import 即可，没有其他依赖。

### 3.3 「未配置」的四象限

`computeTargetViews()` 对 modal 的判定是（§三·补.7 约束二）：

| adapter 在册？ | 凭据配了？ | availability | 理由 |
|---|---|---|---|
| 否 | 否 | `needs_credential` | **未配置**（能力在，只是没凭据）+ 配置指引 |
| 否 | 是 | `unavailable` | 「凭据已配置，但本版本没有装载 Modal adapter……不要读成『支持 Modal 远端算力』」 |
| 是 | 否 | `needs_credential` | 同第一行 |
| 是 | 是 | `available` | — |

**注册表里没有 adapter 就永远不许报 available**，哪怕凭据配好了。
`narrative_parity.test.ts` 里那条新断言就是对着这一格写的（阴性对照④）。
本分支的默认注册表**只有 local**（`defaultComputeAdapters()`）——modal adapter 是 W5-2 α 的交付，
这里如实反映，α 落地后在那个函数里加一行即可，判定仍然只来自运行期读配置（§三·补.7 约束一）。

## 七、遗留问题与我不确定的地方

1. **`capabilities` 的人类可读渲染没有 compute 段**。`backend/src/capabilities/cli.ts` 不在本 lane 的
   文件所有权里，我只接了 `index.ts`（`capabilities --json` 里 `compute` 段是全的）。
   后果：`spark-research capabilities`（不带 `--json`）的表格里看不到执行地。
   `spark-research compute targets` 能看到，所以不是没有入口，但**自描述面对人不完整**。收口补一段渲染即可。
2. **`doctor` 没接**。任务书提到「你接的 capabilities / doctor 面上 Modal 必须报未配置」，
   但 `backend/src/doctor/**` 不在文件所有权里，而且 `doctor` 目前**不消费** `buildCapabilities()`
   （它自己拼报告）。所以 **doctor 里没有算力这一段**——不是报错了，是压根没有。
   要接的话是 `doctor/index.ts` 加一节，判定可以直接调 `computeTargetViews()`（同一份口径）。
   **我没做，也不声称做了。**
3. **`llms.txt` 的 CLI 一览里没有 `compute`**。那一段是从 README 生成的，README 是收口的所有权。
   MCP 工具那一段已经有四个 `compute_*` 与三条扣留（见 §五 的生成结果）。
4. **`README.md` / `CHANGELOG.md` 没动**（收口的所有权）。发布口径提醒：按 §三·补.7，
   v0.5.0 **不许**宣称「支持 Modal 远端算力」，准确说法是
   「算力抽象层与审批链已落地并有 local 实现；Modal adapter 的契约已立、真实链路未验证」。
   本波的 `capabilities` 输出与 `compute targets` 已经是这个口径。
5. **`READ_ONLY_TOOL_NAMES`（`sub_agent.ts`）没加 `compute_status` / `compute_list`**。
   两者都是 GET，理论上该进那张只读表，这样 `review` 类子代理才可能被授权查算力状态。
   但 `sub_agent.ts` 在本 lane 的所有权里只允许改测试文件，源文件那张表不在清单上，
   而且现在没有任何一类子代理的默认 grants 需要它。**记在这里，不是漏了。**
6. **`daemon/daemon.ts` 里那套 v0.1 遗留的 `ComputeService`/`DefaultCompute` 与 `compute_submit` permit
   仍然在**（异议 X-3）。本波接线之后，仓库里确实有两个「compute」了：
   `daemon` 里的内存假实现，与 `backend/src/compute/**` 的真实现。X-3 说要在收口二选一，
   本波**没有碰它**（不在所有权里，也不该由一条接线 lane 决定删谁）。
   现状不会互相干扰（两者没有任何 import 边），但这是一处真实的命名混淆，收口必须处理。
7. **HTTP 的 `workspaceRoot` 默认落在项目目录**。CLI 默认是当前工作目录（人在哪儿敲就传哪儿），
   HTTP/MCP 默认是**项目目录**——外部调用方不该靠猜一个绝对路径就能把本机任意目录扫进上传清单。
   但调用方**仍然可以显式传** `workspaceRoot` 指向任意路径（deny-list 与双限额还在，
   但目录范围本身没有额外收敛）。本地单用户工具语境下我认为可接受，**但这是我的判断，请主会话过目**。
8. **`compute run` 的日志是同步 tee 到 stdout 的**（非 `--json` 时）。长任务会一直占着终端。
   HTTP 面没有派发所以没有 202/任务句柄那套；CLI 也没做后台化。W5-3 α 接桥的时候
   （`exp run --resume` 走 `broker.poll()`）会碰到同一个问题，届时可能需要一个 `--detach`。
