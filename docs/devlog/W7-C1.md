# W7-C1 · V64 根治：项目指针加锁 + 会话绑定

> worktree `~/Desktop/AI4S/spark-research-C1`，分支 `feat/W7-C1-project-lock`，基线 v0.7.0-alpha.3。

## 问题（BACKLOG V64）

全局 `state.json.currentProject`（以及 `sessions{}`）的读-改-写没有锁：两个并发会话各自
`readState()` → 改一个字段 → `writeState()`，后写的那次用的是自己那份旧快照，会把对方刚写完
的改动整个覆盖掉（lost update）——R1 两个并发零上下文会话互相把论文写进对方项目，双双弃项目
重建。`--project` 显式覆盖（R2-P0）只是防线，本 lane 做根治。

## 交付

1. **`openProjectResolved` 单点四档解析顺序**（`backend/src/project/manager.ts`）：
   `--project` > env `SPARK_RESEARCH_PROJECT` > `state.json.sessions[sessionId]` > 全局
   `currentProject`。签名新增可选第三参 `sessionId?: string`（向后兼容：其余十几个既有
   两参调用点不用改，见下方「如实交代」）。
2. **`state.json.lock` 文件锁**：`ProjectManager` 新增 `acquireStateLock()` /
   `reclaimStaleStateLock()` / `releaseStateLock()` / `withStateLock()`。`O_EXCL`
   （`openSync(file, "wx")`）独占创建，内容写 `{pid, acquiredAtMs}`；过期（>10s）且持锁 pid
   已死（复用 `server/tasks.ts` 导出的 `isProcessAlive`，未再写第二份）即回收；未过期或
   pid 仍存活则 `Bun.sleepSync(15ms)` 忙等重试，硬顶 30s 超时抛 `ProjectError`。
   `setCurrent()` / `bindSession()` / `setStatus()`（归档时清全局指针那段）三处 read-modify-write
   全部套进 `withStateLock()`，且**在锁内重新 `readState()`**（不是复用锁外的旧快照——那正是
   lost update 的成因）。
3. **`project use` 语义拆分**（`backend/src/project/cli.ts`）：`open` 不变（全局指针，向后兼容
   既有测试与文档）；新增独立的 `use` 分支——默认只 `bindSession()`（当前会话绑定），`--global`
   才落到 `setCurrent()`（全局指针，等同 `open`）。帮助文案已更新说明两者区别。
4. **`isProcessAlive` 导出**：`backend/src/server/tasks.ts` 里 C-2 lane 已经是
   `export function isProcessAlive(...)`（第 188 行）——本 lane 未改这个文件，直接复用。

## 如实交代：sessionId 的来源

任务书要求「CLI 现在怎么产生 session id 就用什么」。grep 结果：`index.ts` 只在两处生成
sessionId——`main()` 交互循环的 `cli_${Date.now()}`（L374）与 `chat` 单次命令的
`oneshot_${Date.now()}`（L423），且只喂给 `orch.projectForSession()` / `orch.chat()`，
从未传给 `openProjectResolved`——而实际调用 `openProjectResolved` 的十二个文件
（`literature/cli.ts`、`experiment/cli.ts`、`compute/cli.ts` 等）各自现建
`ProjectManager` 直接两参调用，`index.ts` 又是本 lane 明令禁止改动的收口文件，没有通道
把那个临时 id 传进去。

所以：`openProjectResolved` 的第三个可选参数 `sessionId` 目前只有两条真实消费路径——
① 本 lane 新写的测试直接注入；② 落到 `process.env.SPARK_RESEARCH_SESSION`（当调用方没有
显式传参时）。第②条也是 `project/cli.ts` 的 `project use` 判定「有没有会话身份」时用的
同一套来源（`deps.sessionId ?? process.env.SPARK_RESEARCH_SESSION`）。**这意味着对于
`literature/cli.ts` 等既有十二个调用点，第三档「会话绑定」实际只会在调用方自己钉了
env `SPARK_RESEARCH_SESSION` 时生效**；没钉这个环境变量的裸调用，四档解析会跳过第三档，
落到第四档（全局指针）——这跟根治前的行为是一致的，不是回归，只是没有比 `--project`/env
更强的默认并发隔离。收口/后续 lane 如果要把 `index.ts` 的临时 sessionId 接进来，需要改
`index.ts` 本身（不在本 lane 足迹内）。
